Intuition

A deterministic verifier answers one question without asking a model for its opinion: after this sequence of user actions and this much time, is the program in the state the request implies? Thirteen recent papers build such verifiers for generated web pages, games and 3D scenes. Each reads the program through a different keyhole — pixels, the DOM, a state object the program was told to expose — and each pays for its keyhole somewhere: brittle selectors, a model in the loop, or a spec the program must obey to the letter.

The proposal here is to stop treating GUIs, games and simulations as different things. All three are the same object: a driven process with state, a vocabulary of actions, a clock, a source of randomness, and a picture that is a pure function of state. Front-end engineering settled on exactly this shape years ago — Redux reducers, Elm’s update/view, React Testing Library’s “test like a user” queries, Playwright’s fake clock — and its test tools are the most mature deterministic verifiers of interactive behavior that exist. The verifier below borrows their interaction model and adds what generated code needs: a contract the checker can rely on, rules written from the request before any code exists, and a way to find rules nobody wrote.

1. What makes an interactive artifact hard to verify

Four properties, each of which breaks a familiar tool.

PropertyWhat it breaksExample
It remembers. Correctness is a predicate over sequences of actions, not one input–output pair.unit testsafter setK(2) then reset(), k must be 1 again
It runs on its own. Time and randomness are inputs the tester did not choose.golden outputs, screenshotsa Flappy Bird whose pipes spawn at random; a timer
Its output is a picture. The observable surface is pixels, not data.assertionsa canvas plot — nothing to query
It may be built many ways. The same request admits many correct programs.selector-bound scripts#category-select-id exists in one implementation of ten

Every existing verifier is a choice of which of these four to solve and which to pay for.

Two patterns cut across the families. Requirement-first authorship (WebGrader’s planner never sees the site; WorldCoder’s contracts are hidden) is what keeps a check honest; checks written with the implementation, by the same model (InfiniteWeb), have no independent oracle. And the verifier is rarely verified: only WorldCoder mutation-hardens its contracts, only WebRISE and WebGrader inject faults, only four papers report agreement with humans, and none reports all three.

The gap: nobody writes checks at generation time for an unseen request, validates them, and keeps a model out of the verdict. That is the corner to occupy — but only with a design that beats each family on its own axis.

3. What software testing already solved

The deterministic-verification problem is old in one industry. Its answers:

  • Test like a user, query by meaning. Testing Library’s rule: “your test should resemble how users interact with your code,” and its query priority puts getByRole first and getByTestId last. A control is found by role and accessible name (“slider named k”), never by class or id — the anti-selector principle, made precise.
  • Interaction is an event sequence, not a call. user-event dispatches what a real click dispatches — pointer down, focus, pointer up, click — so wiring bugs surface.
  • Settle before you assert. React’s act() flushes pending updates and effects; Playwright locators auto-wait for actionability (attached, visible, stable, enabled) and its assertions retry. Flakiness is a missing settle step, not fate.
  • Own the clock. Playwright’s page.clock replaces Date, setTimeout, setInterval, requestAnimationFrame and performance, with install, runFor, fastForward, pauseAt, setFixedTime. Games learned the same lesson as fix your timestep and deterministic replay: seed plus input log reproduces the run byte for byte.
  • State changes only through actions. Redux (reducer(state, action) → state') and Elm (update, view = f(model)) make the program a driven process by construction; a test is “dispatch, then assert on state,” and the view is a pure function that can be snapshotted.
  • Generate the sequences from a model. XState’s test model walks a statechart and asserts per state; fast-check commands / Hypothesis rule-based state machines run random command sequences with preconditions against a model and the real system, then shrink a failure to the shortest sequence that reproduces it.
  • When there is no oracle, use relations. Metamorphic testing — doubling the input doubles the peak; reversing the list reverses the result — is how numerical and simulation code is tested.

None of these tools assumes the program was written by a model, so none asks the program to carry a contract or writes the tests from a request. That is the part we add.

4. One interaction model for GUI, game and simulation

Definition — Interactive artifact as a driven process

An artifact is ⟨S,s0,A,step,render⟩\langle S, s_0, A, \mathrm{step}, \mathrm{render} \rangle⟨S,s0​,A,step,render⟩: a state space SSS with initial state s0s_0s0​; a finite vocabulary of named, typed actions AAA; a transition function

s′=step(s,  e,  ω),e∈A∪{tick(Δt)},  ω∼hosts' = \mathrm{step}(s,\; e,\; \omega), \qquad e \in A \cup \{\mathrm{tick}(\Delta t)\},\; \omega \sim \mathrm{host}s′=step(s,e,ω),e∈A∪{tick(Δt)},ω∼host

driven by events from three sources — the user (a∈Aa \in Aa∈A), the clock (tick\mathrm{tick}tick), and the environment (random draws ω\omegaω, supplied by the host); and a pure render render:S→View\mathrm{render}: S \to \mathrm{View}render:S→View. A run is s0→e1s1→e2⋯s_0 \xrightarrow{e_1} s_1 \xrightarrow{e_2} \cdotss0​e1​​s1​e2​​⋯. Every “does it work?” question is a predicate over runs.

A slider-driven plot, a Flappy Bird and a pendulum simulator are all instances: the actions are setK/reset, flap, setLength/pause; the clock drives the plot not at all, the bird every frame, the pendulum every physics step; randomness enters only the game.

The model gives three layers at which the verifier can interact, mirroring how a user, a framework and a device see the program:

LayerWhat it isVerifier uses it forPrecedent
L0 · semantic actionsdispatch("setK", {k: 2}) — what the program means to dorule checks: fast, exact, implementation-neutral by namingRedux actions, GameGen keypoints, WorldCoder’s scripted actions
L1 · user intents on the surface”move the slider named k to 2”, “press Checkout” — resolved by role and accessible namewiring checks: does the user-level path produce the same transition as the semantic action?Testing Library getByRole + user-event
L2 · raw device eventspointer at (x, y), key codeonly where no surface exists (a canvas game), through a declared input mapPlaywright, game input replay

The contract is the set of ports that make the three layers and the three event sources reachable from outside the program:

getState() → data              // observable state, schema-declared
setState(s)                    // injection and restore (preconditions, replay)
actions = [{name, params}]     // the vocabulary; dispatch(name, params)
tick(dt)                       // the host owns time
random()                       // the host owns randomness (seeded)
surface() → {role, name, value, …}   // the queryable rendered tree; on canvas, a declared overlay
render = f(state)              // same state ⇒ same picture (checked by remount + snapshot)

This is state-contract verification with two additions the existing contracts lack: actions by name (WorldCoder scripts raw events; InfiniteWeb reads storage after the fact) and a queryable surface (so wiring can be verified without pixels). Host-owned tick and random generalize WorldCoder’s prompt-prescribed timestep and GameFix’s virtual clock into something the checker controls rather than requests.

5. The verifier built on the model

Rules. Six kinds, all predicates over runs, all written from the request before any candidate exists (WebGrader’s requirement-first principle):

  1. Conformance — the contract is present and schema-valid; every declared action is dispatchable; render is deterministic (remount with the same state, identical snapshot); no wall-clock or Math.random reachable (host shims throw). This is the layer where WorldCoder’s 42.8 % schema drift lands — as a repairable verdict, not a score of zero.
  2. Action rules {P} a {Q} — GameGen’s keypoints: setK(2) ⇒ k = 2 ∧ peak = 2·base.
  3. Invariants over every state of every run — total = Σ price · checked.
  4. Temporal rules over ticks — “after 30 ticks with no input the bird’s y decreases”; debounce and timer behavior become countable.
  5. Metamorphic relations for continuous state, where no exact oracle exists — scaling, symmetry, monotonicity, conservation, idempotence, commutativity of independent actions. No verifier in §2 has these; WorldCoder and GameFix stop at tolerance bands.
  6. Wiring and persistence — every L1 intent equals its L0 action; reload preserves state; reset returns to s0s_0s0​.

Sequences. Three generators, budgeted together: (a) model-based — the rules induce a statechart; cover every transition (WebRISE’s ICG, XState); (b) property-based — seeded random walks over A ∪ {tick} with preconditions, shrunk to the minimal failing sequence (fast-check / Hypothesis); (c) replay — seed + input log reproduces any run exactly.

Rule admission. A rule set is trusted only after it rejects mutants of the first passing candidate — mutation-hardened checks, WorldCoder’s admission criterion turned into a pipeline step. Rules that never fail a mutant are flagged as vacuous.

Determinism. Host clock and seeded randomness; an act()-style settle after every event (flush microtasks, effects, animation frames); fresh instance or setState restore per check; an N-run identical-trajectory gate (GameFix’s zero-flake rule) before a verdict counts.

Verdict. Per rule: PASS · FAIL · SKIPPED (precondition unreachable — an upstream defect, counted once, as in WebRISE) · UNSUPPORTED (action not declared). A FAIL carries the shrunk sequence and the state diff, which names the action whose post-state first diverged — the handler to fix. A verdict is a localizer, not a score band.

Rules nobody wrote. Generate several candidates; where all pass the rules but diverge under the same sequence, the rules are silent — differential testing adds the rule or asks the user. This is the only mechanism in the table that can extend an incomplete rule set; GameGen’s recall 1.0 against raters who share its blind spots shows why one is needed.

7. Decisions to make together

  1. Action granularity. Coarse semantic actions (setK) or fine ones (dragStart, dragMove)? Who fixes the vocabulary — the rule-writer from the request, or the generator?
  2. Canvas surfaces. Require a declared semantic overlay (hit regions with roles) so L1 wiring checks work on games and plots, or accept L2 + input map only? The former costs generation quality — WorldCoder’s schema-drift rate is the warning.
  3. What stays outside. Aesthetics and layout taste are not rules; render = f(state) plus snapshot equality is all the verifier says about pictures. Agree, or keep a separate visual judge outside the loop?
  4. How much host control a platform will accept. Shimming the clock and randomness is a runtime change; Artifacts-style platforms already dictate the framework, so it is realistic there — is it acceptable everywhere we want to evaluate?
  5. Mutation operators for UI/game/sim code: stale-state, swapped handler, wrong sign, dropped redraw, off-by-one tick — which set makes admission meaningful without being tailored to our own bugs?
  6. The metamorphic library. Which relations generalize across plots, games and simulations, and how does the rule-writer pick them from a request?
  7. Budget split between model-based coverage and random walks, and the shrinking cost.
  8. Accessibility as a requirement. L1 needs roles and names on controls. Requiring them of generated code is a constraint — and an accessibility win. Do we require or reward it?
  9. Localization heuristic. “First action whose post-state violates a rule” versus delta debugging over the sequence.
  10. The testbed. Computable Canvas components already expose getState/setState; the contract adds actions/dispatch, tick/random, and surface. Which come first?

Pitfalls / open questions

  • A contract shifts failure from “wrong behavior” to “wrong interface”; a verifier that only scores conformance has moved the problem, not solved it. The harness must repair conformance.
  • Rules written from an ambiguous request are ambiguous rules; differential testing exposes the gap but cannot resolve it without the user.
  • Metamorphic relations can be vacuously true (a plot that ignores k satisfies “doubling k doubles the peak” if the peak is 0). Mutation admission is the guard.
  • Deterministic replay hides timing bugs that only wall-clock scheduling produces; report it as a scope limit, not a solved problem.
