Intuition

A deterministic verifier answers one question without asking a model for its opinion: after this sequence of user actions and this much time, is the program in the state the request implies? Thirteen recent papers build such verifiers for generated web pages, games and 3D scenes. Each reads the program through a different keyhole — pixels, the DOM, a state object the program was told to expose — and each pays for its keyhole somewhere: brittle selectors, a model in the loop, or a spec the program must obey to the letter.

This page stops treating GUIs, games and simulations as different things. All three are the same object: a driven process with state, a vocabulary of actions, a clock, a source of randomness, and a picture that is a pure function of state. Front-end engineering settled on that shape years ago — Redux reducers, Elm’s update/view, Testing Library’s role queries, Playwright’s fake clock — and its test tools are the most mature deterministic verifiers of interactive behavior in existence. The design below borrows their interaction model and adds what generated code needs: a contract the checker can rely on, rules written from the request before any code exists, and — because the same agent writes the code and the checks — mechanisms that keep those checks honest.

Every existing verifier chooses which of the four to solve and which to pay for.

Two patterns cut across the families. Requirement-first authorship — WebGrader’s planner never sees the site, WorldCoder’s contracts are hidden — is what keeps a check honest; checks written with the implementation by the same model (InfiniteWeb) have no independent oracle. And the verifier is rarely verified: only WorldCoder mutation-hardens its contracts, only WebRISE and WebGrader inject faults, only four papers report agreement with humans, none does all three.

The gap: nobody writes checks at generation time for an unseen request, validates them, and keeps a model out of the verdict. That corner is empty — but it is only worth occupying with a design that beats each family on its own axis (§6).

3. What software testing already solved

  • Test like a user, query by meaning. Testing Library’s rule — “your test should resemble how users interact with your code” — puts getByRole first and getByTestId last: a control is found by role and accessible name (“the slider named k”), never by class or id.
  • An interaction is an event sequence, not a call. user-event dispatches what a real click dispatches — pointer down, focus, pointer up, click — so wiring bugs surface.
  • Settle before you assert. React’s act() flushes pending updates; Playwright locators auto-wait for actionability and its assertions retry. Flakiness is a missing settle step.
  • Own the clock. Playwright’s page.clock replaces Date, timers, requestAnimationFrame and performance (install, runFor, fastForward, pauseAt). Games learned the same lesson as fix your timestep and deterministic replay: seed + input log reproduces a run.
  • State changes only through actions. Redux (reducer(state, action) → state') and Elm (update, view = f(model)) make a program a driven process by construction; a test is “dispatch, then assert on state”, and the view can be snapshotted.
  • Generate sequences from a model. XState’s test model walks a statechart; fast-check commands and Hypothesis rule-based state machines run random command sequences with preconditions and shrink a failure to the shortest sequence that reproduces it.
  • Without an oracle, use relations. Metamorphic testing — doubling the input doubles the peak — is how numerical and simulation code is tested.

None of these assumes the program was written by a model, so none asks it to carry a contract or derives the tests from a request. That is what we add.

4. One interaction model for GUI, game and simulation

Definition — Interactive artifact as a driven process

An artifact is ⟨S,s0,A,step,render⟩\langle S, s_0, A, \mathrm{step}, \mathrm{render} \rangle⟨S,s0​,A,step,render⟩: a state space SSS with initial state s0s_0s0​; a finite vocabulary of named, typed actions AAA; a transition function

A run is s0→e1s1→e2⋯s_0 \xrightarrow{e_1} s_1 \xrightarrow{e_2} \cdotss0​e1​​s1​e2​​⋯; every “does it work?” question is a predicate over runs.

Generality comes from the ports, not from the artifact type. The verifier touches nothing but the ports below, so a GUI, a game and a simulation differ only in how each port is bound to its runtime — one verifier, three bindings:

The contract is the set of ports that make the layers and the three event sources reachable from outside:

getState() → data              // observable state, schema-declared (may be partial, coverage declared)
setState(s)                    // injection and restore: preconditions, replay
actions = [{name, params}]     // the vocabulary; dispatch(name, params)
tick(dt)                       // the host owns time
random()                       // the host owns randomness (seeded)
surface() → {role, name, value, …}   // the queryable rendered tree; on canvas, a declared overlay
render = f(state)              // same state ⇒ same picture (remount + snapshot)

The ports do not all cost the generator the same. tick and random are imposed: host shims replace Date, timers, requestAnimationFrame and Math.random, as Playwright’s clock does, so a program cannot drift from them — WorldCoder’s clock.getDelta() failure becomes impossible rather than penalized. surface and render are free on the DOM. Only getState/setState and actions/dispatch need the program’s cooperation, and because the agent writes the program against this SDK, conformance is the first rule it runs and repairs — not a hidden schema it is scored against once (the fix for WorldCoder’s 42.8 % schema drift). A wrapped library — a physics engine, GeoGebra — may not expose every internal: the contract admits partial state with declared coverage, and rules may quantify only over declared fields. This is state-contract verification with two ports existing contracts lack, actions by name and a queryable surface.

5. The verifier built on the model

Rules. Six kinds, all predicates over runs, all written from the request before any candidate exists:

  1. Conformance — the contract is present and schema-valid; every declared action is dispatchable; render is deterministic (remount with the same state, identical snapshot); no wall clock or Math.random is reachable.
  2. Action rules {P} a {Q} — GameGen’s keypoints: setK(2) ⇒ k = 2 ∧ peak = 2·base.
  3. Invariants over every state of every run — total = Σ price · checked.
  4. Temporal rules over ticks — “after 30 ticks with no input the bird’s y decreases”.
  5. Metamorphic relations for continuous state, where no exact oracle exists — scaling, symmetry, monotonicity, conservation, idempotence, commutativity of independent actions. No verifier in §2 has these; WorldCoder and GameFix stop at tolerance bands.
  6. Wiring and persistence — every L1 intent equals its L0 action; reload preserves state; reset returns to s0s_0s0​.

Sequences. Three generators on one budget: model-based — the rules induce a statechart; cover every transition (WebRISE’s ICG, XState); property-based — seeded random walks over A ∪ {tick} with preconditions, shrunk to the minimal failing sequence; replay — seed + input log reproduces any run exactly.

Determinism. Host clock and seeded randomness; an act()-style settle after every event; fresh instance or setState restore per check; an N-run identical-trajectory gate (GameFix’s zero-flake rule) before a verdict counts.

Verdict. Per rule: PASS · FAIL · SKIPPED (precondition unreachable — an upstream defect, counted once, as in WebRISE) · UNSUPPORTED (action or field not declared). A FAIL carries the shrunk sequence and the state diff, which names the action whose post-state first diverged — the handler to fix. A verdict is a localizer, not a score band.

Rules nobody wrote. Generate several candidates; where all pass the rules but diverge under the same sequence, the rules are silent — differential testing adds the rule or asks the user. It is the only mechanism in §2 that can extend an incomplete rule set; GameGen’s recall of 1.0 against raters who share its blind spots is why one is needed.

Keeping same-author checks honest

The agent writes the program and the checks, so it can always satisfy the interface — and could always satisfy the checks by writing weak ones, or by exposing a getState() that reports what the rules want. That is InfiniteWeb’s situation: evaluators and site by the same model, no independent oracle. Four mechanisms make same-author checks trustworthy; they, not the bindings, are the design.

  1. Separation in time and context. Rules are derived from the request before any code exists, in a context that never sees the implementation (WebGrader’s requirement-first principle). The code-writer may read the rules — that is test-driven development — but cannot edit them.
  2. The state cannot lie. render = f(state) is enforced by remount-and-compare, and the wiring check ties the surface to the state. Take the broken slider: dispatch(setK, 2) then getState().k == 2 passes — but the live frame was drawn from a stale variable, so it differs from render(remount(getState())), and the bug is caught although getState reported the right number. Where a rule can be grounded in an observable — the rendered peak, the displayed total — it is; state is a trusted proxy only once purity and wiring hold.
  3. Mutation admission. A rule set is trusted only after it rejects mutants of the first passing candidate — mutation-hardened checks, WorldCoder’s admission criterion turned into a pipeline step and the guard against weak tests. Rules that never fail a mutant are flagged as vacuous.
  4. Differential testing. A second, independently generated implementation is the one oracle a single author cannot fake.

None of the four depends on whether the artifact is a GUI, a game or a simulation — which is why they are the design and the binding table is not.

7. Decisions that change the mechanism

How a port is bound on a canvas, how coarse an action is, which roles to require — those are bindings and implementation. Only choices that alter the verifier belong here.

  1. How strict is authorship separation? Same model in a separate context (cheap, weaker) or a different model family for the rule-writer (stronger, costlier)? May the repair step ever propose a rule change, or only flag one for the user?
  2. When is state trusted? Which rule kinds must be grounded in surface() and render observables, and which may read getState() once purity and wiring have passed?
  3. Which mutation operators make admission meaningful without being tailored to our own bugs — stale state, swapped handler, wrong sign, dropped redraw, off-by-one tick, missing reset?
  4. What does partial coverage cost? For a wrapped library that declares 60 % of its state, are rules over undeclared fields UNSUPPORTED (honest, lower coverage) or approximated through observables?

Scope, fixed: the verifier decides behavioral correctness. Layout taste and aesthetics are a different question with a different judge, kept outside the loop; the verifier’s only statement about pictures is render = f(state).

Pitfalls / open questions

  • A contract shifts failure from “wrong behavior” to “wrong interface”; a verifier that only scores conformance has moved the problem. The harness must repair conformance.
  • Rules written from an ambiguous request are ambiguous rules; differential testing exposes the gap but cannot resolve it without the user.
  • Metamorphic relations can be vacuously true (a plot that ignores k satisfies “doubling k doubles the peak” when the peak is 0). Mutation admission is the guard.
  • Deterministic replay hides timing bugs that only wall-clock scheduling produces; a scope limit to report, not a solved problem.
