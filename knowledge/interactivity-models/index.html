Interactivity Models

Intuition

Before designing a contract and a test harness for AI-generated interactive artifacts, it pays to ask how five older traditions already model interactivity: formal reactive-systems theory, the timed/simulation world, UI architecture lineages, software testing frameworks, and deterministic-simulation engineering. Each tradition answers two questions we care about: what an interactive program is (contract inspiration) and how one tests it (framework inspiration).

The punchline, argued in detail below: every component of the contract-and-rules design already exists somewhere with decades of production use behind it — Moore machines, logical ticks, runtime-owned effects, command sequences with postconditions, replay from inputs plus seed. What no tradition provides is the assembly where both sides are synthesized on the fly: the program generated onto the platform, and the model/rules compiled from a plain-language request. That assembly is the open move.

Running example throughout: a plot of k·sin(x) with a slider for k. Classic works are cited by name and year for orientation, not as a bibliography; verify venue and year before any of them enters the paper library as an entry.

Details

1. Formal roots: programs whose meaning is a run

Reactive vs transformational systems (Harel & Pnueli 1985). A transformational program maps one input to one output and stops; a reactive program maintains an ongoing interaction with its environment, and its correctness is a property of runs, not of any input→output pair. The slider is reactive: “drag k, watch the curve follow” has no final output to grade.

Mealy/Moore machines. Finite states, inputs, transition function; output either on transitions (Mealy) or from states (Moore). A verification contract wants the artifact Moore-shaped: render reads the state, never the action. That is the formal backbone of “check the state, trust the picture” — in a Mealy-shaped UI (output produced inside event handlers) the picture can say things the state does not.

I/O automata (Lynch & Tuttle 1987) contribute input-enabledness: input actions must be accepted in every state, because the environment may do anything at any time. Translated: dispatch(name) should be total — setK mid-animation or reset twice in a row is always legal, and the artifact decides what it means. This kills the “test script crashed the app by clicking too early” class of flakiness by definition, and doubles as a free universal rule.

Statecharts (Harel 1987; today UML state machines, SCXML, XState). Flat FSMs explode; statecharts add hierarchy, orthogonal regions, and event broadcast. Lesson for the rule language: a generated artifact’s state is naturally a tree of mostly independent regions (the slider region, the pause/play region), and rules usually constrain one region while quantifying over the rest (“whatever else happens, reset() puts k at 1”).

Temporal properties. Model checking splits properties over runs into safety (“nothing bad ever”: k never NaN) and response/liveness (“something good follows”: after setK(2) the peak doubles within one render). A bounded runner cannot check true liveness, but the taxonomy structures the rule language into invariants, action postconditions, and response-within-k-ticks rules — and rule-writers can be prompted, and coverage reported, per category.

2. Time and chance: synchronous and simulation traditions

Synchronous languages (Esterel, Lustre; SCADE in certified avionics). Their founding move is to replace wall-clock time with logical ticks: the program is a deterministic function from input streams to output streams. tick(dt) as a host-fed input is this move retrofitted onto web artifacts.

Game loops and the fixed timestep (“Fix Your Timestep”, Gaffer On Games 2004). update(dt) and render are separated; physics integrates at fixed dt regardless of frame rate. Two lessons: the game industry already writes interactive programs in the contract’s shape, and a test runner should tick at fixed dt so runs are comparable across candidates.

Lockstep determinism and replay files. RTS games ship replays as input streams plus RNG seed; the whole match re-simulates bit-identically (same for Doom demos and TAS files). Strong cultural proof that (inputs + seed) → identical run is achievable in real interactive software at scale — and it is exactly the right evidence bundle: a failing artifact ships with its action script and seed, and anyone replays the bug.

DEVS (Zeigler 1976). An atomic model has state, an external transition (input event arrives), an internal transition (scheduled by a time-advance function), and an output function. The external/internal split is the cleanest phrasing of the contract: user actions (external) and tick (internal) are the only two doors into the state; behavior not reachable through those doors is untestable and therefore forbidden.

3. UI architecture lineages: the contract already half-exists

MVC → Seeheim/Arch → functional core, imperative shell. Since Smalltalk MVC and the Seeheim model (1985), UI architecture has separated the functional core from presentation. The contract is that separation with a wire format: the core must be reachable as data (getState) and drivable by name (dispatch).

The Elm Architecture / MVU (Elm ~2012; Redux 2015). Model, Msg, update : Msg → Model → Model, view : Model → Html. Two details matter beyond the famous purity. First, effects are runtime-owned: an Elm program cannot read the clock or roll dice; it requests effects and the runtime performs them and feeds results back as messages — the imposed-ports design (host-owned tick and seeded random) with a decade of production use. Second, the vocabulary is standard: Redux literally names its API store.getState() and store.dispatch(action). A contract asking generated code for this interface asks for something a large fraction of human-written frontends already has.

Redux DevTools time travel. Because state is a fold over an action log, sessions rewind and replay against the same log. Precedent that the action log is the debugging artifact; a repair loop’s “failing rule + state diff at action t” feedback is a mechanized DevTools session.

Signals, hooks, fine-grained reactivity (React, Solid, Svelte, Rx). Below-the-contract implementation detail: however the artifact propagates changes internally, the contract speaks only at the boundary. Worth one sentence in any paper to preempt “modern frameworks don’t work like Elm.”

Immediate-mode GUIs (Dear ImGui). The UI is redrawn every frame from program state; there is no retained widget tree to query. More evidence that render = f(state) is a native pattern — and a warning that for canvas-style artifacts, surface testing has nothing at all to attach to.

4. How testing traditions model the thing they test

Surface drivers (Selenium/WebDriver → Playwright, Cypress). Interactivity = locate an element, act, wait for the page to settle, read the DOM. Everything hard about them is a retrofit for what the page hides: auto-waiting heuristics, fake timers (cy.clock, Jest/Sinon) as bolted-on tick, network stubbing as bolted-on determinism, retry-until-timeout assertions as bolted-on “eventually.” The existence of fake timers is the ecosystem admitting that time must be an input. And every script is written against one page’s selectors, which is why none of it transfers across generated artifacts — the root reason evaluation fell back to AI judges.

Testing Library’s counter-philosophy (“the more your tests resemble the way your software is used, the more confidence they give”). The principled objection to state-based testing: users see pixels, not state. The two-part answer a paper must state: render purity plus a remount-and-compare check ties the picture to the state, so state assertions do speak for the screen; the residue — whether the rendering is good — is visual quality, explicitly out of scope.

Model-based testing and conformance (Spec Explorer, GraphWalker, XState’s test tooling; ioco theory, Tretmans 1996). Write a model FSM; the tool generates input sequences covering its paths; conformance means observable behavior matches the model. Two thefts: path coverage over the rule set’s implied transition graph answers “how many action scripts are enough,” and ioco’s asymmetry (the implementation may do more than the model, but nothing the model forbids) is the right conformance notion when rules are deliberately partial — candidates may differ freely where rules are silent, and that silence is what differential comparison then interrogates.

Stateful property-based testing (QuickCheck — Claessen & Hughes 2000; Quviq’s state-machine testing — Hughes; Hypothesis RuleBasedStateMachine; fast-check model-based commands). The closest existing framework shape to a contract runner. A command has a precondition, an action on the real system, and a postcondition against a model; the tool generates random command sequences and — the crown jewel — shrinks a failing sequence to a minimal one. Direct adoptions: rules ≈ postconditions + invariants; generated action scripts ≈ precondition-guarded command sequences; shrinking belongs in the runner because “3 actions reproduce it” is a far better repair prompt than a 200-action log. Their practice also warns that the model is where bugs hide — motivating mutation admission of rule sets (see mutation-hardened-checks).

Deterministic simulation testing (FoundationDB’s simulator; Antithesis as productized descendant; rr record-replay; rrweb session replay). The whole system runs under a simulated, seeded scheduler and clock; any failure replays exactly from its seed. The architectural lesson: determinism is a platform property you buy once — own every nondeterminism source at the boundary, and testing becomes search plus replay. A contract host is a per-artifact simulator of this kind; seeds × action scripts are the search space.

Monkey testing / GUI fuzzing (Android Monkey; Sapienz). Random event storms with only a crash oracle — a reminder that a cheap tier zero of universal rules exists below any compiled rules: no exceptions, no NaN in state, state serializable, render idempotent. These run on every artifact with zero rule-writing.

TodoMVC. One spec, dozens of framework implementations: cultural precedent for the differential setting (many artifacts of one request, compared behaviorally) — and a warning that the spec is the hard part.

5. Design moves worth stealing

  1. Moore discipline: render reads state only; cite Moore machines when defending “state cannot lie.”
  2. Input-enabled dispatch (I/O automata): every action legal in every state; also a free universal rule.
  3. Rule taxonomy from temporal logic: invariants / action postconditions / response-within-k-ticks; prompt and report coverage per category.
  4. Logical time, fixed dt (synchronous languages, game loops): wall clock never enters the runner.
  5. External/internal event split (DEVS): actions and tick are the only doors into state — the contract in one sentence.
  6. Runtime-owned effects (Elm): the artifact never reads clock or RNG; the host delivers them.
  7. Action log + seed as evidence (RTS replays, Redux DevTools, FoundationDB): every verdict ships with a re-runnable witness.
  8. Command formalism with shrinking (stateful PBT): minimal failing sequences as repair feedback.
  9. ioco-style partial conformance (MBT): rules are partial by design; silence is filled by differential comparison.
  10. Tier-zero universal rules (fuzzing): crash-freedom, state sanity, render idempotence for free on every artifact.
  11. Name the objection, then the remount check (Testing Library): “tests should see what users see” is the reviewer’s objection; render purity + remount-and-compare is the answer, visual quality the declared residue.

6. What none of them gives us

Every tradition above assumes somebody already has the model, the spec, or the platform: model-based testing needs a hand-written model, stateful PBT needs hand-written commands and postconditions, simulation testing needs a system built on the simulator from day one, Elm needs a human writing Elm. The open move is the assembly where both sides are synthesized on the fly: the artifact is generated onto the platform (the contract), and the model/rules are compiled from the request by an isolated writer, admitted by mutation, and completed by differential comparison. The traditions supply every component; none of them assembles this loop, because none of them had to test a program that did not exist a minute ago.
