Intuition

State-contract verification checks a program by reading its internal state before and after each action, against an agreed interface, instead of judging pixels. Picture a generated basketball mini-game: the checker presses the launch key and does not ask a vision model whether the ball “looks like it flew”. It reads phase, ballVelocity, and score from a global the program was told to expose, and asserts that the phase went idle to charging to flying to scored-or-missed, that the velocity matches the requested launch angle, and that the score and the on-screen counter agree. Correctness becomes a set of numeric assertions over state deltas, which are cheap, deterministic, and hard to fake with a pretty frame.

Details

Why this is needed for canvas programs and not for ordinary pages: an HTML page keeps its state in the DOM, which the browser maintains and any test can query or subscribe to. A canvas or WebGL program draws into one element and keeps every object, velocity, and phase inside JavaScript variables the browser never sees. The DOM shows only peripheral buttons and labels. So either you look at pixels, or you ask the program to publish its state through a contract.

Definition — Behavioral state contract

A contract for task τ\tauτ is a tuple Cτ=(Σ,A,Φ)C_\tau = (\Sigma, A, \Phi)Cτ​=(Σ,A,Φ): a state interface schema Σ\SigmaΣ (which variables must be readable, e.g. a global object), a scripted action sequence A=(a1,…,an)A = (a_1, \dots, a_n)A=(a1​,…,an​), and assertions Φ={ϕi}\Phi = \{\phi_i\}Φ={ϕi​} over snapshots. The checker records sbefores_{\text{before}}sbefore​, applies aia_iai​, records safters_{\text{after}}safter​, and evaluates each ϕi(sbefore,safter)\phi_i(s_{\text{before}}, s_{\text{after}})ϕi​(sbefore​,safter​). Each assertion is a Hoare triple {P} a {Q}\{P\}\, a\, \{Q\}{P}a{Q} with PPP and QQQ written over the exposed state. Only Σ\SigmaΣ is shown to the generator; AAA and Φ\PhiΦ stay hidden.

Three design points make it work. The schema is public but the assertions are hidden, so the generator cannot special-case the test. Actions include a “physics-step” command and the task demands a fixed timestep, so trajectories are reproducible frame by frame rather than tied to wall-clock timing. And the contract itself must be validated, otherwise a lax assertion passes anything; that is mutation-hardened-checks.

Two variants bracket a spectrum. A requirement-side contract describes observable states and transitions without naming implementation details, so one contract applies to any implementation; an implementation-side contract requires the program to conform to a named interface. A third move, state injection, treats the interface as writable as well as readable.

In the papers

WorldCoder-Bench is the implementation-side instance for Three.js worlds. Each program must expose a global such as window.__3D_STATE__ reporting coordinates, velocities, modes, counters, and interaction flags (§3.3); StateProbe runs the page in headless Chromium, checks that a WebGL context and render loop exist, then applies deterministic scripted actions, snapshotting state before and after each and checking hidden assertions over the delta (§3.3). The schema is visible, the contract hidden (Fig. 5); outcomes are RUNTIME_CRASH, CHECK_FAIL, or CHECK_PASS (§3.4). Against this ground truth, DOM-only inspection correlates at Kendall tau-b of minus 0.021, screenshot plus VLM at minus 0.068, and an 8-step agent at +0.111 while passing 45.6% of low-coverage outputs. (Tab. 2) 83.6% of transition failures are state-schema drift (42.8%) or broken interaction chains (40.8%), not missing scene elements. (§4.5) The case study in App. D makes the timestep point concrete: a model advanced physics with clock.getDelta() instead of the prescribed fixed 1/60 s step, so the hoop-pass assertion fired at the wrong moment while the frame looked right (Fig. 10).

GameGen-Verifier adds injection. A keypoint is a natural-language Hoare-style triple (P,a,Q)(P, a, Q)(P,a,Q) that must be constructible, bounded, and verifiable (§4.1); it is grounded into a unit (sk,ik,yk)(s_k, i_k, y_k)(sk​,ik​,yk​) whose state sks_ksk​ is synthesized from the game’s parameter structure and patched into the runtime, turning a reachability problem into a configuration problem (§4.2). The injection contract needs only two capabilities: control which entities exist and what values they hold. Verdicts come from a VLM judge plus programmatic assertions over exposed state and logs (§4.1).

WebRISE is the requirement-side instance: its Interaction Contract Graph Gτ=(Sτ,Tτ,Φτ,Mτ)G_\tau = (S_\tau, T_\tau, \Phi_\tau, M_\tau)Gτ​=(Sτ​,Tτ​,Φτ​,Mτ​) (Eq. 3) defines states as requirement-relevant observable configurations, not DOM snapshots, and each transition carries preconditions, DOM assertions, and visual postconditions (Eq. 4); see model-based-gui-testing. WebGrader derives per-request executable Flow Contracts and collects DOM, visual, response, and persistent-state evidence along one browser trajectory, issuing Pass only after the requested transition is observed (Abstract).

Pitfalls / open questions

  • A readable interface is also forgeable: a program can write the expected values into the global without rendering them. WorldCoder pairs state probes with a live-WebGL check; stronger pairing with visual evidence is open.
  • “Schema drift” counts as failure: fair for a benchmark, but a repair loop should separate “wrong behavior” from “ignored the interface”.
  • Hidden contracts cannot be handed to the generator for self-repair. What a public, mutation-hardened subset of the contract would do to generation quality is untested.
  • Injection needs white-box access and a parameter structure the verifier can read; obfuscated or engine-native state resists it (GameGen-Verifier §6).

Glossary

  • DOM — the browser’s live element tree, queryable by scripts and test tools.
  • Canvas — a single element the program paints pixels into; its contents are opaque to the browser.
  • WebGL — the browser’s GPU rendering API; Three.js scenes render through it into one canvas.
  • State interface / schema — the set of runtime variables a program must expose (e.g. a global object).
  • Behavioral contract — schema plus hidden action sequence plus assertions over before/after state.
  • Hoare triple — if precondition P holds and action a runs, postcondition Q holds afterwards.
  • State delta — the difference between the state snapshot before and after an action.
  • Fixed timestep — advancing simulation by a constant step per tick so trajectories do not depend on frame rate.
  • State injection — writing a constructed state into the running program so a check can start from its precondition.
  • State-schema drift — the program’s exposed state deviates from the required schema.
