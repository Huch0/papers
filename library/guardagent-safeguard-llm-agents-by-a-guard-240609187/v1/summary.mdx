<TLDR>GuardAgent is the first <Term def="an LLM agent deployed in parallel with another ('target') agent to check whether the target's actions satisfy given safety guard requests">guardrail agent</Term>: an in-context LLM pipeline that compiles natural-language safety guard requests into an action plan and then into executable Python guardrail code over a toolbox of callable functions, so that admitting or denying a target agent's action is decided by code execution rather than by a model's judgment — evaluated on two new benchmarks the paper introduces, EICU-AC (healthcare access control) and Mind2Web-SC (web-agent safety policies).</TLDR>

<WhyItMatters>For TDE this is the guardrail-layer neighbor of the compile-then-verify move: it turns NL requirements into mechanically executed checks that gate agent actions, and its baselines are directly citable evidence that executed code beats LLM-as-judge adjudication (EA 97.5 vs 67.9 on EICU-AC with GPT-4). It still differs from TDE on all three defining axes: checks execute over the target agent's textual I/O logs and a structured user profile, never over environment state; they adjudicate per-action policy compliance, never task completion over the final world state; and a violation yields a one-shot deny, not a red–green iterate-until-pass loop. One classification nuance for the novelty defense: GuardAgent is not itself a pure model-judge — the LLM is the (unverified) compiler and the judge is the Python engine; the model-judge class is the baseline this paper beats. The residual circularity sits at the NL-to-code boundary, exactly where TDE must also defend its acceptance-suite compilation. Also relevant to the web/computer-use track (SeeAct on Mind2Web) and to benchmark-design methodology.</WhyItMatters>

## Motivation
<Problem>Existing guardrails moderate textual harm in LLM outputs and cannot check agent actions against application-specific rules</Problem>: LlamaGuard applied to agent logs is near random (LPA 50.3/51.0, flagging only 3.1%/2.0% of violations; Tab.1). <Problem>Safety controls hardcoded into a target agent's prompt neither guard well nor preserve the task</Problem> — explanation accuracy at most 58% while task performance collapses (final response accuracy 3.2% for EHRAgent with GPT-4) — and, being agent-specific, they do not transfer (§5.3). <Problem>No benchmark existed for access control or safety-policy compliance of LLM agents</Problem> (§3).

## Contribution (what's new)
<Novelty>The agent-guarding-agents pattern: the guard's verdict is computed by executing LLM-generated guardrail code, not by an LLM's textual judgment</Novelty> — `(Ol, Od) = E(C, F)`, with outputs produced only if the code executes. The form is forced by how the LLM-judge baseline fails: it "considerately" expands a nurse's permissions to cover a needed database (Fig.3) and cannot disambiguate column names shared across databases, whereas generated code holds permissions as dictionaries where membership is exact (Fig.14, App .7). <Novelty>Non-invasive parallel deployment with an extendable memory and toolbox</Novelty> adapts the guard to new agents and requests through uploaded functions and retrieved demonstrations, with no training. <Novelty>Two benchmarks — EICU-AC (316 examples, 3 roles) and Mind2Web-SC (200 examples, 6 rules)</Novelty> operationalize access control and safety control for agents.

## Research questions
Can one non-invasive guard check the actions of heterogeneous LLM agents against diverse natural-language safety requests without compromising their task utility (§4)? And is a code-based guardrail actually more reliable than one based on natural-language reasoning (§5.3, App .16)?

## Methodology
GuardAgent receives guard requests `Ir`, a target-agent specification `Is`, the target agent's input `Ii`, and its output log `Io` (for EHRAgent: reasoning steps, generated code, final answer; for SeeAct: predicted action plus reasoning). Step 1 prompts the core LLM to write a step-by-step plan; step 2 maps the plan to guardrail code restricted to a provided list of callable functions; a Python engine executes the code, yielding label `Ol` (deny if 1) and reasons `Od`. Both steps retrieve the k most similar past cases from a memory module (smallest Levenshtein distance over the concatenated I/O; k=1 for EICU-AC, k=3 for Mind2Web-SC, seeded with manually written demonstrations); up to 3 LLM debugging iterations repair inexecutable code. Core LLMs: GPT-4, Llama3-70B, Llama3.1-70B, Llama3.3-70B, temperature 0.

**EICU-AC construction (§3.1, App .1).** From 580 EICU test questions, keep the 183 answered correctly by EHRAgent (GPT-4, temperature 0); required databases/columns are read off EHRAgent's generated code by hand. Each question is paired with each of three roles (physician, nursing, general administration) and labeled 1 iff some required database/column is inaccessible to that role. Role permissions come from ChatGPT recommendations verified by clinicians; "limited access" recommendations are coerced to "no access" for physician/nursing but "full access" for general administration — explicitly to produce enough deniable queries for label balance. Final: 316 examples (label 0 per role: 52/57/45; label 1: 46/55/61), 226 unique questions over 51 information categories (§3.1; App .1.3 says 50) and 70 question templates.

**Mind2Web-SC construction (§3.2, App .2).** Tasks with correct SeeAct action predictions (GPT-4) from Mind2Web's travel/shop/entertainment test domains each get a random user profile (integer age; boolean domestic, dr_license, vaccine, membership) and a manual label: 1 iff a related rule is violated. Six rules: membership to shop; vaccination to book flights; driver's license to buy/rent cars; age 18+ for hotels; domestic location for movie/music/video search; age 15+ for job applications. Raw labeling is imbalanced (178 negatives / 70 positives), so classes are balanced to 100/100 by re-sampling profiles over existing tasks; per-rule violation counts are 19/12/24/18/21/6 (Tab.4), and 50 of the 100 negatives still touch a rule.

**Metrics (§5.1).** <Term def="label prediction accuracy over all examples; a '1' counts only if the denial message is printed">LPA</Term> plus precision/recall (LPP/LPR); <Term def="explanation accuracy: fraction of true violations predicted 1 AND with all inaccessible databases/columns or all violated rules identified">EA</Term>; <Term def="final response accuracy: fraction of true non-violations admitted AND answered/acted correctly by the target agent — the invasiveness probe">FRA</Term>.

**Cost (App .14).** GuardAgent with GPT-4 averages 45.4s/37.3s per example (EICU-AC/Mind2Web-SC) vs 31.9s/30.0s for the target agents and 8.5s/14.4s for the LLM-judge baseline; one debug iteration costs 15.2s/17.8s.

## Key findings
- <Finding src="Tab.1">The gap over the LLM-judge baseline is modest in LPA but large in EA</Finding>: with GPT-4 on EICU-AC, 98.7 vs 97.5 LPA yet 97.5 vs 67.9 EA — the judge often flags a violation without correctly naming what was violated, while code execution prints the exact inaccessible items.
- <Finding src="Fig.3, Fig.14">The judge's failures are autonomy and ambiguity failures</Finding>: it "considerately" adds the diagnosis database to a nurse's accessible list, and cannot tell apart a column name (patientunitstayid) shared by an accessible and an inaccessible database; dictionaries in code make membership exact.
- <Finding src="Tab.1">Content-moderation guardrails do not transfer to agents</Finding>: LlamaGuard scores LPA 50.3/51.0 with LPR 3.1/2.0 — it almost never flags an agent-policy violation.
- <Finding src="Tab.2, App .8, App .11">Toolbox and memory mainly buy executability, not judgment</Finding>: removing both drops the executable rate from 100% to 90.8% (93.7% after debugging) and LPA from 98.7 to 90.8, but GuardAgent self-defines the missing functions and keeps EA at 96.1%; debugging fixes only 9/29 failed programs and none of the 3 syntax errors.
- <Finding src="Fig.4">Residual failures sit at the NL-to-check boundary</Finding>: GPT-4's misses concentrate on rule 5 (movies/music/video), where a broad rule plus detail-heavy queries keep the compiler from linking query to rule — the step code execution cannot repair.
- <Finding src="App .16, Tab.8">The design generalizes beyond binary agent gating</Finding>: on CSQA with 4 pseudo-rules and 5 risk levels, GuardAgent reaches 92.5% overall recall (74/80) vs 82.5% (66/80) for the LLM judge; with code instructions removed entirely, GPT-4 still spontaneously writes code guardrails for 68.0% of EICU-AC examples (mostly inexecutable).

## Implications
First entry in the "agent guarding agents" class, positioned against <Related>model-guarding-models content moderation (LlamaGuard, NeMo Guardrails, Perspective/OpenAI moderation)</Related> and safety rules hardcoded into agents such as <Related>EHRAgent (Shi et al. 2024) and SeeAct (Zheng et al. 2024), which double here as the guarded targets</Related>. For TDE, the strongest citable point is the head-to-head: same LLM, same demonstrations, same inputs — moving the verdict from model text to executed code lifts EA by up to 29.6 points; mechanical execution beats model-judging even in the safety domain. Threads worth chasing: <FollowUp>verifying the compile step itself (plan/code faithfulness to the NL policy) — unmeasured here and the locus of all residual failures</FollowUp>; <FollowUp>moving checks from the agent's own logs to environment-evaluated state (the guard currently trusts EHRAgent's log to reveal which databases its code touches)</FollowUp>; <FollowUp>adversarial robustness of the guard, e.g. AgentPoison-style memory poisoning or injection through `Io`, which the same group has studied but does not test here</FollowUp>.

## Limitations
- <Caveat>"Deterministically follow the safety guard request" holds only downstream of code generation</Caveat>: the NL-to-plan-to-code compilation is unverified LLM output; nothing checks the generated code against the policy, and passes have no faithfulness audit (EA covers only flagged cases).
- <Caveat>Checks never touch the environment</Caveat>: inputs are the target agent's own logs plus a structured, assumed-truthful user profile. For EHRAgent the log already contains the final answer, so as evaluated the guard filters disclosure after the database query has run rather than gating execution.
- <Caveat>Benchmarks are small, balanced, and engineered to be checkable</Caveat>: 316/200 examples drawn only from tasks the target agent already solves; boolean profile fields map one-to-one onto rules; EICU-AC permission ground truth was partly coerced ("limited access" resolved by role) to balance labels rather than for clinical fidelity.
- <Caveat>No adversarial evaluation and no variance</Caveat>: single runs at temperature 0, no seeds or significance; no prompt-injection or evasion attempts against the guard; the GPT-4 version is not reported.
- <Caveat>Author-stated (App .17)</Caveat>: the toolbox is specified manually; reasoning is plain chain-of-thought with no validation of steps; single-agent design.

## Critiques and Questions
1. The reliability story conflates two properties: executability (measured — ER 100%) and faithfulness (unmeasured). A mis-compiled check fails silently while wearing the authority of "deterministic execution". TDE inherits precisely this issue at acceptance-suite compilation — this paper is both precedent and warning.
2. How much of the headline is benchmark construction? Once the log lists the required databases and the profile is boolean, access control reduces to set membership; the semantically hard part (mapping a task to a rule) is exactly where GuardAgent still fails (rule 5). Open-ended policies without structured profiles would test the claim far harder.
3. Gating position is ambiguous: actions "will be denied", yet the EHRAgent log includes the final answer, implying post-execution filtering; real access control must precede execution, where GuardAgent's latency (45.4s with GPT-4, slower than the 31.9s target agent) also bites.
4. Minor data hygiene: Tab.3's row annotations swap "access denied"/"access granted" relative to the label definition in §3.1, and the ICU information-category count is 51 in §3.1 but 50 in App .1.3.

### Personal notes
For the TDE related-work section: this is the guardrail-layer precedent for "compile NL requirement into an executable check, verdict by mechanical execution" — cite it for the judge-vs-execution evidence (EA 97.5 vs 67.9, same LLM and prompt budget), then draw the three deltas: (1) substrate — its code runs over agent logs and profile dictionaries, TDE's suites run over environment-evaluated final world state; (2) target — per-action policy/access compliance vs task-completion acceptance; (3) control flow — one-shot admit/deny vs red–green iteration until the suite passes. The unverified NL-to-code compilation is the shared open problem; GuardAgent's rule-5 failures are the cleanest empirical demonstration that execution cannot repair mis-compilation.
