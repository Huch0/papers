<TLDR>We make design-to-code behavioral and execution-checked — from before/after screenshots of one interaction an MLLM must emit a page whose tagged element, clicked by a webdriver, reproduces the after-state — and on 127 real webpages / 374 interactions every model does worse on the interaction than on the static page, failing in ten catalogued ways.</TLDR>

<WhyItMatters>The closest existing harness to execution-grounded synthesis of stateful visual components: browser replay, changed-region diff, and human usability, plus a failure taxonomy that reads like a repair-loop dispatch table.</WhyItMatters>

## Motivation
Take the product page in Fig.1(a): a row of size buttons and a quantity stepper. A static screenshot of it is what every <Term def="Generating HTML/CSS(/JS) that reproduces a UI from a static screenshot or mock-up; also called UI2Code">design-to-code</Term> benchmark (<Related>WebSight, Vision2UI, Design2Code, DesignBench — Tab.I</Related>) hands to a model, and a generated page in which clicking "M" does nothing scores perfectly. <Problem>Existing benchmarks grade how a page looks and are silent on whether anything works</Problem> — no corner case, since interactive elements are 50% (code) to 96% (music) of all elements on 10 random real pages (Fig.1b). <Problem>MLLM UI-code methods (Design2Code, DCGen, DeclarUI) therefore optimize the static half of a page with no signal on the dynamic half</Problem>; nobody had defined the task or catalogued the failures.

## Contribution (what's new)
<Novelty>An interaction can be specified purely visually as a before/after screenshot pair and graded by execution: the model must tag its interactive element with a known id, so a webdriver can click it, screenshot, and diff the changed region against the reference after-state</Novelty>. Each part is forced: without the after-screenshot there is no ground truth for the click; without the id, no deterministic trigger; without region-level diffing, the unchanged page dominates the score and hides the interaction. On top: human failure annotations and four fixes derived from them.

## Research questions
1. How well do closed and open MLLMs generate the interactive part of a page, relative to its static appearance?
2. How do they fail, and what does each failure type cost in usability?
3. Do visual saliency of the interaction area and the modality of the description drive the failures?
4. Do cheap fixes aimed at those causes (highlighting, failure-aware prompting, cropping, adding text) recover performance, and do they stack?

## Methodology
Running example: the size selector of Fig.7(b), where clicking "M" changes the displayed size; the <Term def="A functional model of a UI that lets users simulate interactions; here, the pair of screenshots before and after one interaction">interactive prototype</Term> is that before/after pair. The model gets both images plus the Direct prompt (Fig.5) and must return one HTML/CSS/JS file with `id="interact1"` on the M button. Selenium loads the file, clicks `#interact1`, screenshots, and compares twice: whole page against reference, and the changed region against the reference's changed region. Four PhD annotators then click M themselves and ask: does the behavior precisely match the prototype?

Why each piece: the selector is a few hundred pixels, so a page-level score is dominated by content that never changed. The after-screenshot is the only ground truth for the click, and designers already produce it. Humans sit on top because pixel similarity cannot tell "the size label changed for the right reason" from "something nearby redrew", and three of our ten failure types leave the static page pixel-identical. Comparing against the real site is [differential testing](../../knowledge/differential-testing/); the replay is one-edge [model-based GUI testing](../../knowledge/model-based-gui-testing/).

<Definition term="Interaction-part extraction and metrics">
Region (Alg.1, p.4): if <M tex="\dim(A)=\dim(B)" />, the bounding box of <M tex="C=\{(x,y)\mid |A-B|(x,y)\neq 0\}" />; else the extremal rows/columns flagged by git-diff of <M tex="A,B" /> and <M tex="A^{T},B^{T}" />. On the regions: CLIP score, SSIM, OCR-then-BLEU. With normalized region centres <M tex="(x_o,y_o),(x_g,y_g)\in[0,1]^2" />:
<MathBlock>{`P(I_o,I_g)=1-\\max(|x_o-x_g|,\\,|y_o-y_g|),\\qquad \\mathrm{IR}=\\frac{N(\\text{implemented})}{N(\\text{implemented})+N(\\text{unimplemented})},\\qquad \\mathrm{UR}=\\frac{N(\\text{usable})}{N(\\text{usable})+N(\\text{unusable})}`}</MathBlock>
Implemented iff the webdriver can detect the interaction; usable iff a human judges it to precisely match the prototype's behavior (§III-C, §V-A2).
</Definition>

<Definition term="Visual saliency of an interaction">
<MathBlock>{`\\mathrm{VS}(I)=\\frac{\\mathrm{area}(I)}{\\mathrm{area}(S_I)}`}</MathBlock>

## Key findings
- <Finding src="Tab.IV, Fig.6a">Drawing boxes on the interaction beats reasoning about it, and CoT is not free</Finding>: Gemini's interaction CLIP goes 0.4737 → 0.5093 (<Term def="Chain-of-thought prompt: 'think step by step' through analyze effect, locate element, implement">CoT</Term>) → 0.5194 (<Term def="Prompt whose input screenshots carry red bounding boxes around the interactive element and its effect">Mark</Term>), IR 0.6738 → 0.7112 → 0.7326; Mark lifts Claude's usability 11 points. But GPT-4o's IR falls under CoT (0.7754 → 0.7273) and Qwen-3B collapses (0.3449 → 0.1979); "both improve" holds on average, not per model.
- <Finding src="Tab.V, Fig.9">Ten failure types, three causes, and only the behavioral ones are fatal</Finding>: missing element 0% usable, wrong function 0%, no interaction 6.93%, effect on wrong element 44.44%, versus 92.31–98.41% for wrong element / type / position. Fig.7(b) is our size selector with the M button rendered but inert — a top-frequency failure whose static screenshot matches a correct page.
- <Finding src="Tab.VI">Failure-aware prompting helps the four large models and hurts the small ones</Finding>: on the 1/3 held-out split IR rises for Gemini 0.7636 → 0.8182, GPT-4o 0.7636 → 0.8364, Qwen-72B 0.6545 → 0.7636; Qwen-3B drops on 7 of 8 metrics (IR 0.4727 → 0.3818). We wrote "improves on all models"; the table disagrees for 3B and 7B.
- <Finding src="Fig.10, Fig.11, Tab.VII">Visually subtle interactions fail, and cropping rescues them</Finding>: binned by <Term def="Pixel area of the interaction region divided by the area of the after-screenshot">visual saliency</Term>, Gemini's SSIM and position similarity rise monotonically from bin `[0, 0.025)` to `[0.2, 1)`. On 10 failure pages all metrics are 0 at 1x magnification and CLIP/SSIM approach 0.8 at 3x, with the stitched full page flat (CLIP 0.826–0.843).
- <Finding src="Tab.VIII, Tab.IX">One human sentence beats the screenshots, and the four fixes stack</Finding>: GPT-4o Direct position similarity 0.3951 (visual) / 0.4293 (text) / 0.7157 (both); with all four fixes CLIP/SSIM/Text/Position go 0.5700/0.4891/0.3652/0.5802 → 0.6937/0.6251/0.5187/0.7371, and removing any one lowers every metric.

## Implications
Behavior, not appearance, is the bottleneck: the fatal failures are the ones similarity cannot see, so <FollowUp>a behavioral oracle — replay the event and diff state, not pixels — should drive training or repair</FollowUp>. The three failure causes (spatial, type, behavioral) are separable sub-skills, so <FollowUp>a repair loop could dispatch on which cluster the execution diff reveals</FollowUp>. Screenshot pairs underspecify the transition (toggle vs. open-modal); the V+T result says a one-line behavioral spec is the cheapest fix — treat the after-state as a contract, as in [state-contract verification](../../knowledge/state-contract-verification/). Prompting alone works at 72B and not below, so <FollowUp>execution-feedback fine-tuning on small open models</FollowUp> is the open slot. Lineage: extends <Related>Design2Code and DCGen (static UI2Code)</Related> and our own <Related>DesignBench, MRWeb, EfficientUICoder</Related>; the harness (id tagging + Selenium + region diff) is a reusable oracle for stateful component generation.

## Limitations
- <Caveat>We know the ground truth is one click and one after-screenshot</Caveat>: multi-step or toggling interactions collapse to one transition, "partial implementation" (select but not unselect, Fig.8i) is caught only by humans, and backend-dependent interactions (login, search) cannot be verified (§VI).
- <Caveat>We did not report evaluator agreement</Caveat>: the dataset builders also judge usability and failures with no inter-annotator agreement; "consistent with the automatic metrics" (§V-A2) is rank-level, no correlation coefficient; every number is a single temperature-0 run (variance Not reported); and we did not test an [LLM-as-a-judge](../../knowledge/llm-as-a-judge/) as a replacement.
- <Caveat>Our fixes are measured on small, non-comparable slices with oracle help</Caveat>: FAP on a 1/3 split whose Claude Direct IR (0.6364, Tab.VI) is far below the full benchmark's (0.7914, Tab.IV); VSE and V+T on 10 failure pages; Mark and V+T rely on human-drawn boxes and human-written descriptions — upper bounds for any automatic pipeline.
- <Caveat>Some metrics measure the wrong thing</Caveat>: position similarity uses centres only; the region extractor breaks on incidental change (animations, ads); widget similarity is 0.0185–0.0533 for every model (Tab.IV) because GUIPilot's detector targets mobile screens; and "implemented iff detectable by the webdriver" leaves Unclear whether an inert tagged button counts.

## Critiques and Questions
1. Contamination: BLEU of 0.12–0.14 against the original HTML (Tab.III) rules out recitation, not familiarity. The 27 GitHub projects (average 13k stars) are public source almost certainly in code-pretraining corpora, and the C4 pages are live sites that HTML-bearing crawls also cover; "C4 is text-only" describes one corpus, not what the models saw. A behavior-level contamination test is Not reported.
2. Aging: the models are Gemini-1.5-flash, GPT-4o-20240806, Claude-3.5-Sonnet-20240620, Qwen2.5-VL (Pixtral untested, §VI). Frozen screenshots keep tasks stable, but the top setting already reaches IR 0.8128 / 81% usable, so headroom is thin; the taxonomy and harness outlive the leaderboard.
3. The headline gap conflates region size with behavior: small regions make pixel metrics noisier (Fig.10 shows SSIM and position track saliency). IR and UR isolate the behavioral gap better.
4. Tab.IX's base row equals GPT-4o Direct in Tab.VI (0.5700 / 0.4891 / 0.3652), so the ablation runs on the 1/3 split — yet textual descriptions were written for 10 pages (§V-D). Their source for the whole split is Unclear.

<SelfCheck q="A generated page renders the M size button with id='interact1', Selenium clicks it, and nothing changes. What do IR, the interaction-part metrics, and the human judgment each say, and why does the benchmark need all three?" a="The webdriver locates and clicks the id, so IR may count it as implemented (we define 'implemented' as 'detectable by webdriver' without saying whether an inert element counts). The interaction-part metrics see no changed region, so they are 0 — as in the 1x magnification case of Fig.11. The annotator clicks M, sees no size change, and marks it unusable: failure type (b) 'no interaction', 6.93% usable (Tab.V). IR alone over-credits, region metrics alone cannot say what changed for the wrong reason, and only the human ties the after-state to the intended behavior." />

<SelfCheck q="Why does the benchmark score the extracted interaction region separately from the full page, and what would be lost by scoring only the full page?" a="The size selector is a small fraction of the page; full-page CLIP/SSIM are dominated by the header, product image, and text that never change, so a page whose M button does nothing scores nearly as well as a correct one. Tab.IV shows exactly this: every model's full-page scores exceed its interaction-part scores (Claude Direct CLIP 0.7172 vs 0.5674), and Fig.10 shows the region metrics fall further as the region gets smaller. Scoring only the full page would reproduce the blind spot of static design-to-code benchmarks." />

## Glossary
- <Term def="Multimodal Large Language Model: an LLM that accepts images (here, screenshots) alongside text">MLLM</Term>
- <Term def="Fraction of generated interactions the Selenium webdriver can locate (by id) and trigger">Implement Rate (IR)</Term>
- <Term def="Fraction of generated interactions human annotators judge to precisely match the prototype's behavior">Usability Rate (UR)</Term>
- <Term def="Prompt that lists the ten annotated failure types and tells the model to avoid them">Failure-aware Prompting (FAP)</Term>
- <Term def="Cropping the input screenshots so the interaction region occupies a larger share of the image, then generating the cut-off remainder separately and stitching">Visual Saliency Enhancement (VSE)</Term>
- <Term def="Colossal Clean Crawled Corpus, a text corpus from CommonCrawl whose validation split supplies 100 of the 127 pages">C4</Term>
- <Term def="A consistency-based mobile GUI testing tool whose widget detector supplies the Widget Similarity (WS) and Widget Match Rate (WMR) metrics">GUIPilot</Term>
- <Term def="Structural Similarity Index Measure, a pixel-structure similarity between two images">SSIM</Term>
- <Term def="Cosine similarity between CLIP image embeddings of two screenshots">CLIP score</Term>
