<TLDR>A GUI program that runs without an exception can still be unplayable, so we make a vision-language agent (<Term def="Our screenshot-driven GUI testing agent: VisualObserver + Test Manager + ActionExecutor">PlayTester</Term>) play the generated app, turn its verdict into a metric (<Term def="Fraction of problems where at least one of k samples passes unit tests and then survives an interactive playthrough with no logic violations">Play@k</Term>) and a benchmark (<Term def="Our repository-aware benchmark: 43 GUI apps in Python/JS/TS across six categories, each task a function to re-implement inside a checked-out repo">PlayEval</Term>), and feed its diagnostics into a repair loop (PlayCoder) that doubles Python Play@3 on the same backbone, 9.9% to 20.3%.</TLDR>

<WhyItMatters>If you build repair loops for interactive programs, Tab. 5 is the ablation you would otherwise run yourself: compile/run/unit-test feedback buys executability, only play-based feedback buys behavioral correctness — and an open-weight backbone (Qwen3-Coder) is among the best.</WhyItMatters>

## Motivation
Fig. 1 is why we built this. We asked GPT-4o-mini for a Flappy Bird. It runs without one runtime error — and the bird flies straight through the pipes, so the game never ends. <Problem>Compilation success and unit tests cannot see this silent failure</Problem>: nothing raises, and the broken property ("a collision must end the game") is temporal, over pipes spawned at random coordinates, so there is no fixed input–output pair to assert on (§2.1); our source repos' own tests cover only 47.2% of lines and 32.1% of branches (§3.1.3). <Problem>Code benchmarks score GUI programs by tests alone, and GUI testers (Selenium, GPTDroid, LLMDroid, VETL) need a DOM or accessibility tree that canvas-rendered desktop apps such as Pygame games do not expose</Problem> (§2.1). The best base model, Claude-Sonnet-4, drops from 18.6% <Term def="Fraction of problems where at least one of k samples runs without syntax, import, or runtime errors">Exec@3</Term> to 9.9% Play@3 on Python (Tab. 2).

## Contribution (what's new)
<Novelty>The only oracle that can see a stateful, pixel-rendered logic bug is one that plays the app — so we make a vision-language agent the oracle, then reuse that same agent as the repair signal</Novelty>. Everything else is forced: Play@k sits strictly inside <Term def="Fraction of problems where at least one of k samples passes all unit tests">Pass@k</Term> so the syntactic-vs-behavioral gap is measurable (§3.1.4); PlayTester works from screenshots because canvas games expose no DOM (§2.1); PlayRefiner consumes screenshots-plus-actions instead of a fixed test suite because the Fig. 1 bug has no fixed input to assert on (§1).

## Research questions
- Preliminaries: is a <Term def="Vision-language model: an LLM that also takes images as input">VLM</Term> tester a reliable oracle (§3.5), and how far does playability fall below executability (§3.6)?
- RQ-1: does closed-loop repair from visual, interactive feedback beat prompting and multi-agent baselines on the same backbone? RQ-2: at what token cost? RQ-3: which of <Term def="Automated program repair: generating a patch from a failure signal">APR</Term>, GUI feedback and context retrieval carries the gain? (§5)

## Methodology
**The task.** One function to re-implement inside a checked-out repository, given signature, requirement docstring and repository context (Fig. 2) — for Flappy Bird the game loop or an event handler, since we keep only functions of at least 28 non-docstring lines (§3.1.1). Three nested gates follow (§3.4):

<Definition term="Exec@k, Pass@k, Play@k (PlayEval scoring rule)">

With <M tex="n" /> samples per problem, <M tex="c_{\text{succeed}}" /> meeting the stage criterion:

<MathBlock>{`[\\mathrm{Exec},\\mathrm{Pass},\\mathrm{Play}]@k := \\mathbb{E}_{\\text{problems}}\\left[1 - \\frac{\\binom{n-c_{\\text{succeed}}}{k}}{\\binom{n}{k}}\\right]`}</MathBlock>

where Exec: no syntax, import or runtime error; Pass: Exec and all unit tests; Play: Pass and no PlayTester violation, plus hard constraints ("did the game crash?") on logs and the final screenshot. So <M tex="\mathrm{Play}@k \le \mathrm{Pass}@k \le \mathrm{Exec}@k" />.

</Definition>

**Playing Flappy Bird (§3.3).** PlayTester launches the app, screenshots it one second after each action (three frames kept to detect motion), then writes a test strategy. Games get a goal-driven strategy (reach the terminal state; success and failure criteria), tool-like apps a coverage-driven one, since "winning" a text editor means nothing (§3.3.3). Then one action per step from `click / type / hotkey / press / scroll / wait / finish`: `press` to flap, screenshot, compare. Bird overlaps a pipe, no game-over: the failure criterion fires and `finish(failure)` ends the run. This is [agent-as-a-verifier](../../knowledge/agent-as-a-verifier/), not [model-based GUI testing](../../knowledge/model-based-gui-testing/): only pixels, no widget tree.

**Closing the loop (§4).** PlayCoder runs generate → play-test → diagnose → patch → re-test. <Term def="Our repository-aware generation agent: few-shot prompting plus grep/file/bash tools">PlayDeveloper</Term> writes the function with grep-based repository retrieval; <Term def="Our APR agent: diagnoses from compiler, runtime and PlayTester reports, patches, re-validates">PlayRefiner</Term> folds compiler output, runtime logs and the behavioral report (screenshots, action trace, and the violation; for Fig. 1: "Collision detection error, APR required", Fig. 4) into a typed failure summary and routes on it: compile errors to the Validator, undefined symbols to the ContextSearcher, wrong physics to a logic edit (§2.2, §4.3). The typing makes feedback actionable: a bare failed screenshot would send the refiner back to fixing imports while the bug is in the collision test. The loop stops when all checks pass or after `T=6` rounds (§4.1.1), capped because each round is a full launch-and-play with a VLM call per step (testing is already ~22% of our tokens, §5.2) and an uncapped loop would void Tab. 4's cost comparison; the cap is untuned (Not reported).

<Pass title="Method details">
**Benchmark construction (§3.1).** Repositories: commits in the last 12 months at selection time, or at least 6 months of sustained history; mostly over 100 GitHub stars; complete GUI workflows; framework diversity (PyQt, PySide, Tkinter, Pygame). Categories (Tab. 1): Game Emulation (1 repo, PyBoy, 26,699 LOC), Classic Games (6 repos, 2,605 LOC: 2048, Snake, Flappy Bird, Sudoku, Chrome Dragon, Solitaire, Chess variants), Game Engine (1, Jupylet), Standalone Applications (24, 123,442 LOC), Desktop Widgets (9, 21,420 LOC), MMORPG (2 TypeScript games with over 1000 stars: CyberCodeOnline, biomes-game). Totals: 637 files, 188,432 LOC, 4,497 functions, 595 classes, 2,104 test cases; average cyclomatic complexity 10.2 per file, 30.4 control-flow structures per kLOC. Requirements: GPT-4o-mini docstrings generated from the original function body, about 10% verified by 3 developer experts, over 95.6% judged high quality by vote. Unit tests: the original repo tests (47.2% line / 32.1% branch coverage) plus an LLM-generated suite of unit, integration, functional and edge-case tests. Repository state is fixed with `git checkout` so PlayCoder sees the same context a human developer would. Fig. 2 lists 4,159 instances, 35 repositories, 578 classes and 2,072 test cases, which does not match Tab. 1.

**PlayTester internals (§3.3).** VisualObserver: pyautogui + PIL screenshots, region capture, window detection via AppleScript (macOS) and Win32; Windows, macOS and X11 Linux only — Wayland blocks cross-window capture and input injection. ActionExecutor: `click(x, y)`, `type(text)`, `hotkey(keys)`, `press(key)`, `scroll(x, y, direction)`, `wait(duration)`, `finish(success/failure)`, with coordinate bounds checks, a failsafe cursor and an action history; actions are parsed from structured `Thought:` / `Action:` output. Test Manager: three prompt phases — GUI analysis (type, screen, UI elements with position/size/color/text/purpose, controls, objective), test-strategy formulation (primary objective, success criteria, failure criteria; launch, functionality and UI tests), action decision — with one template per phase except strategy, which has a game and a non-game template. Tests are reusable across consistent screen resolutions. Worked 2048 trace (Fig. 3): the observer reads `r3c1=2, r3c4=2, r4c4=4, score=8`; the planner chooses a rightward swipe because it both advances a corner strategy (merging into a 4 at r3c4) and exercises swipe responsiveness, merge logic and score update in one move, while watching for invalid moves, freezes and wrong termination.

**Evaluator validation (§3.5).** 100 PlayTester successes and 100 failures, randomly selected and shown in random order to 3 engineers with over 5 years of GUI experience, human judgment as ground truth: 16% false-negative rate, 5% false-positive rate, Krippendorff's α = 0.790, Kendall's τ-b = 0.795.

<Definition term="Efficiency@k">

<MathBlock>{`\\mathrm{Efficiency}@k := \\frac{\\mathrm{Play}@k}{AT_k}, \\qquad AT_k := \\frac{\\mathrm{Token}_k}{N\\cdot 10^{3}}`}</MathBlock>

where <M tex="\mathrm{Token}_k" /> is the total token usage over all <M tex="N" /> problems when generating <M tex="k" /> samples each, and <M tex="AT_k" /> is the average tokens per problem in thousands. For <M tex="k=1" /> it reduces to <M tex="\mathrm{Efficiency}@1 = \mathrm{Succeed}_1 / \mathrm{Token}_1" /> (Eq. 2–3).

</Definition>

**PlayCoder agents (§4.2–4.3).**

  { title: "Behavioral testing", body: "PlayTester runs the app and records screenshots, actions, violations, compiler and runtime logs into an AgentTrajectory log; execution is sandboxed with deterministic seeding and controlled timing." },

**Baselines and statistical protocol (§3.2, §5).** Ten base LLMs: GPT-5, GPT-5-mini, GPT-4o, GPT-4o-mini, Claude-Sonnet-4, Claude-Sonnet-3.7, Grok-3-mini (closed); Qwen3-Coder 480B, GLM-4.5 355B, DeepSeek-V3 671B (open). Five enhanced methods run with their official configuration on three shared backbones (GPT-5-mini, Claude-Sonnet-3.7, Qwen3-Coder). Every number is a mean over 5 runs, each with a distinct fixed seed, temperature 0.3, identical prompts, tools and database state reset before each run; 95% CIs from the Student's t-distribution. Ablation rows (Tab. 5): full, no-APR, no-GUI, no-APR-no-GUI (context only), no-agent. Note that the abstract's headline pair — 38.1% Exec@3 (Qwen3-Coder, Tab. 3) and 20.3% Play@3 (Claude-Sonnet-4, Tab. 6) — comes from two different backbones, not one run.

**Case studies (§5.4).** Success: MetaGPT's 2048 drew white digits on a white background; unit tests passed, the game was unplayable, PlayTester flagged the absence of visible change, and the rendering was repaired. Failure: bugs that need high-frequency feedback (only above 60 FPS) or long-duration survival (a crash after 2 minutes of Flappy Bird) defeat all methods; 4 of 43 projects, concentrated in fast arcade games (Flappy Bird, Snake) and real-time physics.
</Pass>

## Main result
Same backbone, roughly double the behavioral correctness of the strongest baseline: <Finding src="Tab.3">GPT-5-mini: PlayCoder 26.8% Exec@3 / 9.8% Play@3 (Python) vs DeepCode 17.9% / 6.4%</Finding>; <Finding src="Tab.3">Qwen3-Coder: 38.1% / 18.9% vs 37.6% / 9.8%</Finding>; DeepCode already matches us on executability there, so the whole gain is behavioral: Flappy Birds that end when the bird hits a pipe. <Finding src="Tab.6">Best overall is Claude-Sonnet-4: 36.8% / 20.3% on Python, 44.5% / 24.6% on JavaScript</Finding>.

## Key findings
- <Finding src="Tab.5, §5.3">GUI feedback buys playability; APR buys executability</Finding>: GPT-5-mini, Python: no GUI feedback leaves Exec@3 at 24.1% but drops Play@3 9.8% → 5.3%; no APR drops Exec@3 26.8% → 18.3% but Play@3 only to 7.9%. APR-only Play@3 sits at the no-agent 4.9%, and for Claude-Sonnet-3.7 falls below it (6.9% vs 7.6%): compile/run/test signals fix crashes, not a bird flying through pipes.
- <Finding src="Tab.5">Stronger backbones lose more without APR</Finding>: Claude-Sonnet-3.7 −14.1pp Python Exec@3 (35.6% → 21.5%). <Finding src="Tab.5">Context retrieval alone does nothing</Finding>: context-only equals no-agent (14.3% Exec@3 / 4.9% Play@3 in both).
- <Finding src="Tab.4">PlayCoder spends 164K tokens (5,480 per function) vs 128K bare and 252K for DeepCode, with the highest <Term def="Play@k divided by average tokens per problem in thousands, Eq. 2">Efficiency@1</Term> (1.51 vs 1.01 bare); testing is ~22% of tokens</Finding>.
- <Finding src="Tab.2, Tab.6, §5.3">JavaScript ≥ Python > TypeScript for every model and method</Finding> (Qwen3-Coder Exec@3: 31.0% TS vs 38.1% Py), which we attribute to the two MMORPG repos being TypeScript (§5.1). <Finding src="Tab.2, Tab.6">All 10 backbones improve; open-weight Qwen3-Coder is second only to Claude-Sonnet-4 on Python Play@3 (18.9% vs 20.3%)</Finding>.
- <Finding src="§5.4">Bugs needing high-frequency or long-horizon observation (a glitch only above 60 FPS, a crash after two minutes of Flappy Bird) defeat every method including ours: 4 of 43 projects (about 9%)</Finding>.

## Implications
Tab. 5 is the design rule for repair loops on interactive programs: compile/run/unit-test feedback moves executability; only an oracle that drives and watches the program moves playability. <Related>Lineage: Self-Refine / Self-Debug repair with textual feedback, crossed with LLM GUI testers and agentic coders such as DeepCode; closest sibling "You Don't Know Until You Click" (Bian et al. 2025)</Related>. <FollowUp>PlayTester verdicts as a training reward — we only prompt, and a 16% miss rate looks tolerable for RL or rejection sampling</FollowUp>. <FollowUp>[State-contract verification](../../knowledge/state-contract-verification/) or instrumented state dumps as a second oracle for the ~9% that 1 Hz screenshots miss</FollowUp>.

## Limitations
- <Caveat>We know Play@k rests on a VLM judge with 16% false-negative / 5% false-positive rates (§3.5), and the evaluator's default backbone is Not reported — only that a Claude-Sonnet-3.7 swap moved Play@3 by 0.9–3.7% (§5.1)</Caveat>.
- <Caveat>We know 1 Hz polling misses frame-rate and long-horizon bugs (about 9% of projects, unsolvable by construction) and did not try faster capture (§5.4, §7)</Caveat>.
- <Caveat>Task construction is partly LLM-made: GPT-4o-mini requirements and tests, about 10% human-checked; one regenerated function per instance, so "playable" means the app still plays after one replacement; Fig. 2's instance and repo counts disagree with Tab. 1 (§3.1)</Caveat>.
- <Caveat>We did not address contamination or aging: the Classic Games and PyBoy are famous public repos whose reference code is likely in training data, and PlayEval has no refresh policy although we cite LiveCodeBench for exactly that (§6.1); PlayTester also runs only on Windows, macOS and X11 (§3.3.1)</Caveat>.

## Critiques and Questions
1. Contamination: famous games from public repos, with the requirement docstring generated from the reference body, so a memorizing model can pass Exec@k and Pass@k by recall. Base Play@3 near zero suggests recall does not buy playability, yet PlayEval cannot separate "recalls Flappy Bird" from "understands collision"; no decontamination or held-out split is reported, and nothing guards against aging: a fixed set of ten backbones, a 12-month-activity rule, no versioning.
2. Oracle and feedback are the same agent: six rounds against PlayTester, then scoring with PlayTester, optimizes toward its blind spots, the [LLM-as-a-judge](../../knowledge/llm-as-a-judge/) bias §5.1 acknowledges. PlayCoder's outputs were never human re-checked; planting known logic bugs ([mutation-hardened checks](../../knowledge/mutation-hardened-checks/)) would show whether the 16% miss rate concentrates on the physics bugs the loop targets.
3. Fairness is partial: baselines ran in their official configuration (§3) without a GUI oracle, so Tab. 3 shows what a play-tester adds, not what DeepCode would do with one; token cost is matched only for GPT-5-mini (Tab. 4), and "164K tokens for 30 functions" suggests a subset, so the Efficiency@k basis is Unclear. What the six rounds actually change (violation and patch taxonomy, gain per iteration) is Not reported.
