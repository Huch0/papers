<TLDR>We built WebDevJudge — 654 human-preference pairs over deployed web apps, each labelled against a verifiable rubric tree — and found that the best LLM judge agrees with our experts 70.3% of the time versus 84.6% expert–expert agreement, a gap that neither screenshots, rubrics, nor a GUI agent closes.</TLDR>

<WhyItMatters>The cleanest measurement so far of how far an AI judge sits from a human on interactive web artifacts, plus a reusable protocol — rubric-guided agreement and a feasibility unit set — for scoring any checker, programmatic ones included, against ground truth.</WhyItMatters>

## Motivation
Take one arena query: *"Create a modern notebook grading app, with categories and the teacher will use a star like system to grade each category. The app should show total score, reset button."* Two models returned React pages; a crowd user picked one (Fig.9, Fig.10). Can a model be trusted to make that call instead? [LLM-as-a-judge](../../knowledge/llm-as-a-judge/) has only been validated where the grader reads a finished, static thing. <Problem>A web app is not static: whether the grading app works is decided by what happens when you click a star and whether the total updates, and there is no reference answer to diff against.</Problem> Existing <Term def="a benchmark that scores an evaluator by how well its verdicts match human or ground-truth labels">meta-evaluation</Term> sets grade text (MT-Bench, LLMBar, JudgeBench), pre-scripted trajectories (AgentRewardBench), or visual effects without user-triggered state changes (ArtifactsBench) (§2).

The second problem is the ground truth. <Problem>When two of us re-annotated 100 arena pairs on the deployed pages unguided, we agreed with each other only 65.0% of the time (counting ties) and with the crowd only 53.0%</Problem> (Tab.1, §3.2). A judge scored against those labels is scored against noise, so first we had to make two people agree about the grading app.

## Contribution (what's new)
<Novelty>A query-grounded <Term def="a hierarchy derived from the user request — intention → static elements → dynamic behavior — whose every leaf is a binary, verifiable check">rubric tree</Term> turns "is this grading app better?" into about 30 yes/no questions two people answer the same way</Novelty>: agreement rises from 65.0% to 92.0% with human-written trees and 90.0% with LLM-generated ones (Tab.1), and LLM generation is what makes 654 pairs affordable. Because every pair is deployed, one pair can be judged from code, a screenshot, or a live page — which is what makes agentic judges testable at all. <Novelty>WebDevJudge-Unit isolates one sub-skill, <Term def="deciding whether a specified interaction can actually be performed on the deployed page">feasibility verification</Term>, in 502 labelled tasks</Novelty> (App.D).

## Research questions
(1) Can an LLM judge stand in for human preference on open-ended, interactive web development? (2) Which levers move agreement — paradigm, guidance, observation modality, agency (§4)?

## Methodology
**Building the ground truth.** From <Term def="a public 10,501-pair dataset of web-development queries, two model-generated implementations each, and a crowd preference (Vichare et al., 2025)">webdev-arena-preference-10k</Term> we dedupe (10,501 → 6,730), have gemini-2.5-pro drop unsafe, unclear, and low-interaction queries (2,460), deploy everything in one Next.js sandbox and drop non-200 or blank pages (1,713), sample 700, and hand-filter to 654 (Tab.8). Both filters are forced: without the interaction filter the benchmark rewards reading static HTML; without deployment there is nothing to click. For the grading-app pair, gemini-2.5-pro writes the rubric tree (Fig.9, right): intention *"a web application for teachers to grade student notebooks"*; static leaves *"a text label displaying 'Organization'"*, *"a set of star icons"*, *"a 'Reset' button"*, and dynamic leaves *"user can click on a star in the 'Organization' category"* (basic) and *"selecting a star recalculates the total score"* (complex). Two of us (software-engineering backgrounds) open both deployed pages, work through the leaves, and label A / B / tie under six guidelines: functionality before aesthetics, a verdict over a tie, and <Term def="two implementations satisfy the same requirement despite different labels, text, or structure">functional equivalence</Term> over literal wording (App.B.2).

<Definition term="Agreement rate">
For two annotators, or a judge and the human label, the fraction of instances whose labels coincide:
<MathBlock>{`\\mathrm{AR} = \\frac{1}{N}\\sum_{i=1}^{N} \\mathbb{1}\\big[\\hat{l}_i = l_i\\big],\\qquad l_i \\in \\{a,\\ b,\\ \\text{tie}\\}`}</MathBlock>
"w/o tie" recomputes it on the subset whose reference label is not a tie (App.B.2, Tab.1, Tab.14).
</Definition>

**Judging.** 17 (M)LLMs — 11 non-reasoning, 6 reasoning — judge the same pair under <Term def="the judge sees both implementations and outputs A, B, or tie">pairwise comparison</Term> and <Term def="the judge scores each implementation alone; the preference is derived by comparing the two scores">single-answer grading</Term>, with guidance direct, a four-dimension <Term def="a multi-point ordinal rating scale; here 1–5 per sub-criterion">Likert</Term> scale, or the rubric tree scored as a weighted leaf pass rate (weights 1 : 3 : 2, App.C.2; formal below), and observation code, an initial screenshot, or both. The agentic judge follows Eq.1: the rubric tree is the plan, <Term def="ByteDance's end-to-end GUI agent that emits a thought then a click/type/scroll action from a screenshot (ReAct-style)">UI-TARS-1.5</Term> executes each leaf on the live page — "find the Organization row and the Reset button", then "click a star and check the total changes" — and a summarizer turns pass rates into the verdict. Everything is single-pass at temperature 0.0, no swap-debiasing: bias counts as a flaw of the judge (§4.3, App.E.1).

Deployment is a standardized Next.js environment with the most common packages pre-installed; implementations needing niche libraries are discarded.

**Why not the crowd labels.** The arena labels are single-pass, unverified, and include a "tie (bothbad)" category that hides cases where one flawed page is clearly better (App.B.1). Tab.9 shows two: an apple.com clone the crowd gave to B where A is the more accurate restoration, and a 4×8 game of 2048 labelled bothbad where B is clearly closer to the query.

**Annotators and the validation ladder (§3.2, App.B.2).** The annotators are two of us, with computer-science and software-engineering backgrounds. The ladder: (i) 100 pairs re-annotated with no rubric — 65.0% inter-annotator, 53.0% vs the original labels (91.3% / 77.4% without ties); (ii) 50 pairs with hand-written trees — 92.0% (95.5% without ties); (iii) a third annotator using LLM-generated trees on the same pairs — 90.0% (95.1%); (iv) the remaining data annotated with generated trees, with a final 89.7% agreement measured on a sampled subset. A hand-written rubric costs an estimated 20 minutes excluding research time, which is why generation is forced at 654 pairs. Generated trees average 29.9 leaves (3.6 intention / 15.6 static / 10.6 dynamic) and height 5.0 (Tab.10). The six annotation guidelines are on p.20; guideline 6 is functional equivalence.

**Topic mix (Tab.2, Fig.2).** Digital Design 34.0%, Game and App Development 34.4%, Web and Specialized Technologies 31.6%; the largest sub-categories are Website Design 17.6%, UI Design 16.4%, Game Development 16.2%, Clone Development 14.8%. Sub-categories were assigned by GPT-4o from the original topic names and manually consolidated (App.B.3).

**Contamination risk.** The source dataset is public and the judged models are 2025 API and open-weight releases; we do not test whether any judge saw the pairs or the crowd preferences — Not reported. Two facts bound the damage: our labels agree with the crowd's only 53.0% (77.4% without ties, Tab.1), so a judge that memorized the crowd verdicts could not reproduce our ground truth; and rubric trees were generated after the fact by gemini-2.5-pro, which no judge could have trained on — though gemini-2.5-pro is itself a judged model (65.75% pairwise, Tab.3).

**Aging.** 17 vanilla judges (App.C.1: OpenAI, Anthropic, Google, Qwen, DeepSeek, Moonshot, ZAI), commercial ones via Azure and Vertex AI, open ones via vLLM/SGLang, temperature 0.0 for non-reasoning models. API drift and model deprecation are not addressed; there is no frozen-judge control. Not reported.

**WebDevJudge-Unit (App.D).** Sample 105 queries from WebDevJudge; gemini-2.5-pro writes up to five verification tasks each with an expected result; we generate HTML for each query, deploy it, and annotate feasibility by interacting with the live page, recording an error type for infeasible tasks. 502 tasks: 279 feasible, 223 infeasible. Infeasible causes (Tab.12): non-functional element 35.9%, missing element 30.9%, prerequisite not met 15.2%, loading issue 9.0%, unreasonable outcome 5.4%, ambiguous input 2.2%, overly detailed task 0.9%, missing animation 0.5%.
</Pass>

<Pass title="Judging paradigms, rubric scoring, and the agentic pipeline (formal)">
<Definition term="Rubric-tree score (single-answer and pairwise)">
For dimension <M tex="d \in \{\text{int}, \text{sta}, \text{dyn}\}" /> with leaf set <M tex="L_d" />, the judge marks each leaf pass/fail and the score is a weighted pass rate with weights intention : static : dynamic = 1 : 3 : 2:
<MathBlock>{`S(W) = \\sum_{d} w_d \\cdot \\frac{1}{|L_d|}\\sum_{\\ell \\in L_d} \\mathbb{1}[\\ell \\text{ passes on } W],\\qquad (w_{\\text{int}}, w_{\\text{sta}}, w_{\\text{dyn}}) = (1,\\,3,\\,2)`}</MathBlock>
Pairwise, each leaf is labelled A / B / tie, the per-dimension win rate replaces the pass rate, and the higher weighted score wins (App.C.2). Unclear: how exactly equal rubric scores are resolved.
</Definition>

<Definition term="Judging paradigms">
Pairwise: the evaluator maps the query and both observations to a label,
<MathBlock>{`E_{\\text{pair}}(Q, O(W_a), O(W_b)) \\in \\{a,\\ b,\\ \\text{tie}\\}.`}</MathBlock>
Single-answer: the evaluator scores each implementation alone and the preference is derived from the two scores,
<MathBlock>{`\\hat{l} = \\operatorname{cmp}\\big(E_{\\text{single}}(Q, O(W_a)),\\ E_{\\text{single}}(Q, O(W_b))\\big).`}</MathBlock>
Under Likert guidance, each of 13 sub-criteria in four dimensions (functional correctness, UI quality, code quality, interactivity; App.C.2) gets a score in <M tex="\{1,\dots,5\}" /> and <M tex="S" /> is their sum; in pairwise Likert a preference is declared only if <M tex="|S_a - S_b| > 1" />, otherwise tie (App.C.2). Under direct guidance the model emits the label with no criteria. The tie rule for single-answer Likert sums is Unclear.
</Definition>

<Definition term="Agentic evaluator (Eq.1) and gated ensemble (Eq.2)">
<MathBlock>{`Q \\xrightarrow{\\ \\text{Planner}\\ } \\text{Plan with test cases} \\xrightarrow{\\ \\text{Executor}\\ } \\text{Results} \\xrightarrow{\\ \\text{Summarizer}\\ } \\text{Judge} \\qquad (1)`}</MathBlock>
The plan is the generated rubric tree; the executor is UI-TARS-1.5 driving the deployed page through pyautogui; the summarizer computes per-dimension pass rates and the same 1 : 3 : 2 weighted score as single-answer rubric grading (App.C.3). The gated ensemble keeps the LLM's verdict on intention and static leaves and, on dynamic leaves, passes a leaf if either component passes it:
<MathBlock>{`\\mathrm{Res}_{\\text{dynamic}} = \\text{Agent} \\lor \\text{LLM} \\qquad (2)`}</MathBlock>
</Definition>

**Agent settings (Tab.11).** Static: input is the list of rubric elements, output the list found, max 6 steps. Dynamic: each leaf is a task; output feasibility and conclusion; 5 steps for basic, 15 for complex. Intention: intention description → feasibility conclusion, 15 steps. Action space: click, double/right click, drag, hotkey, type, scroll, wait (5 s), finished (App.C.3).

## Main result

## Key findings
- <Finding src="§4.1, Fig.5–6">Pairwise beats single-answer by more than 8 points on average and is more stable: inter-model consistency exceeds 75% pairwise versus 50–65% single-answer.</Finding> Relative judgment needs no calibrated absolute scale, which models lack.
- <Finding src="Fig.3, Tab.14">Pairwise, guidance barely matters — direct, Likert and rubric all land near 70%, reasoning models slightly better with no rubric — but single-answer, a binary rubric clearly beats Likert (GPT-4.1 65.6% vs 60.9%; 74.5% vs 69.72% without ties).</Finding>
- <Finding src="Tab.4">Code carries the judgment: withholding it costs Claude-4-Sonnet 10.7 points pairwise (59.48% vs 70.18%), withholding the screenshot at most 2.6.</Finding>
- <Finding src="§4.1, Tab.6, Tab.7">The agentic judge loses because errors compound — brittle plans, then an executor that misreads pages — and feasibility checking splits into complementary failures: code-only GPT-4.1 has high recall, low precision (P 72.1 / R 90.0); UI-TARS-1.5 the reverse (P 82.4 / R 70.3), calling feasible tasks infeasible after its own navigation failures (Fig.11); gating dynamic leaves as agent OR LLM adds only 1.2–1.3 points.</Finding>
- <Finding src="Tab.5, Tab.13">Positional bias survives explicit instructions — GPT-4.1 prefers the second slot 15.8% of the time under direct judgment — is not concentrated in ties, and swap-debiasing does not raise agreement.</Finding>
- <Finding src="Fig.4, Fig.10">Judges miss functional equivalence: the grading page labels a row "Presentation" where the rubric says "Organization"; the humans and GPT-4.1 pass it, DeepSeek-R1-0528 and UI-TARS-1.5 fail it despite an explicit instruction to accept equivalents.</Finding>

## Implications
For anyone using an AI judge as a reward or gate on generated interactive programs, the instrument sits roughly 15 points below a human (§1), and giving it hands makes it worse until the executor is reliable. <Related>Lineage: MT-Bench → LLMBar / JudgeBench → AgentRewardBench and ArtifactsBench; the agentic judge borrows Bian et al.'s planner–executor–summarizer and Gou et al.'s rubric-tree judge agent (§2, §4.1).</Related> The precision/recall split is the general [agent-as-a-verifier](../../knowledge/agent-as-a-verifier/) trade-off: static reading over-approximates, a GUI driver under-approximates. <FollowUp>Reuse two pieces for a programmatic checker: the rubric-guided agreement protocol (with and without ties) as yardstick, and WebDevJudge-Unit's 279 feasible / 223 infeasible labels as ground truth for its precision and recall on dynamic leaves.</FollowUp> <FollowUp>The equivalence failure is label matching; a check over exposed state — "does a rating row exist, does the total update on click?" — sidesteps it by construction ([state-contract verification](../../knowledge/state-contract-verification/)), and [model-based GUI testing](../../knowledge/model-based-gui-testing/) replaces the executor's blind navigation with an explicit state model.</FollowUp>

## Limitations
<Caveat>We know the ground truth is two of us: 89.7% is within-team agreement on a sampled subset, the 84.56% "human" row is agreement rather than accuracy, and preference stays subjective by construction (App.A, App.B.2).</Caveat> <Caveat>We did not optimize the agentic workflow — one executor (UI-TARS-1.5), step budgets of 6 / 5 / 15, no retries (§5, Tab.11) — so "agents are worse" is a claim about this pipeline only.</Caveat> <Caveat>Every number is one pass over 654 React/Next.js pairs from one arena, commercial models via Azure/Vertex APIs (App.C.1); we report no variance, and API drift will move these numbers.</Caveat> <Caveat>We did not test whether any judge had seen the public arena pairs or crowd labels (Not reported); mitigating this, our labels agree with the crowd's only 53.0% (77.4% without ties, Tab.1), so memorized crowd verdicts would not reproduce our ground truth.</Caveat>

## Critiques and Questions
1. gemini-2.5-pro writes both the rubric trees and the Unit tasks and is itself judged (65.75% pairwise, Tab.3). The rubric invented an "Organization" category for a query that only said "categories" (Fig.9, right), so some "equivalence failures" are rubric-specificity failures the annotators were told to read past.
2. Fig.4 and Fig.10 show what looks like the same grading page, with required label "Demonstration" in one and "Organization" in the other, "LLM: false" in Fig.4 but GPT-4.1 passing in Fig.10 — which is canonical?
3. "Human-level" is slippery: rubric-guided experts agree with the crowd only 77.4% without ties (Tab.1), while GPT-4.1 agrees with those experts 83.49% (Tab.14). The gap is against one rubric-trained pair, not a universal human.
4. Single-pass, no intervals: the 70.34 / 70.18 / 68.96 ordering atop Tab.3 is within plausible sampling noise on 654 items; a bootstrap would have cost nothing.
