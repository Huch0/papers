<TLDR>We make website generation self-supervising: at every step of our agent a VLM grades the landing-page screenshot (0–5) and a GUI agent clicks through the requirements and is graded (1–5), and the sum of those two grades drives repair, backtracking, select-best, and a per-step GRPO advantage — lifting Claude-3.5-Sonnet from 26.4% to 51.9% and Qwen2.5-Coder-7B from 38.9% to 45.4% on WebGen-Bench.</TLDR>

<WhyItMatters>The closest existing template for my thesis: render-and-interact feedback on interactive web artifacts turned into a dense reward for an open 7B/8B engine, with an honest audit of where the [agent-as-a-verifier](../../knowledge/agent-as-a-verifier/) signal is noisy and where functional fixes break appearance.</WhyItMatters>

## Motivation
Take the request we carry through this summary (Fig.9): "a multi-company dashboard that collects and displays financial data from each company, provides consolidated reports, and supports cross-company comparisons; mint cream background, teal components." A code agent must turn that paragraph into a multi-file Vite + React project. <Problem>Every code agent we compare against — OpenHands, Aider, <Term def="Open-source chat-based website builder running in WebContainer; the previous state of the art on WebGen-Bench and the source of our system prompt">Bolt.diy</Term> — verifies it by code execution alone: dependencies install, the dev server prints ready, feedback stops (§1)</Problem>. Execution output cannot see that the comparison view is buried behind repeated clicks, that components overlap, or that a button does nothing. On <Term def="101 natural-language website-generation instructions with 647 GUI-agent test cases; accuracy = share of test cases a GUI agent passes, appearance = GPT-4o appearance grade (Lu et al. 2025b)">WebGen-Bench</Term>, even Claude-3.5-Sonnet inside Bolt.diy passes only 26.4% of test cases (Tab.1). Underneath: <Problem>we want a cheap 7B–8B open engine, but such models lag far behind, and the RL recipes that could close the gap either reward only the final outcome (sparse) or need step-level ground truth that does not exist for websites (§2.2, §4)</Problem>.

## Contribution (what's new)
<Novelty>The two things a website must be — good-looking and working — are both measurable at every step by machinery already in the loop: a VLM grading the landing-page screenshot 0–5, and a VLM-driven GUI agent exercising the requirements, graded 1–5. Their sum is simultaneously a repair signal, a selection criterion for backtracking and select-best, and a dense per-step reward for GRPO</Novelty>. The form is forced: looks need a picture, function needs clicks, and because each score measures the codebase at that step, the advantage must be per-step and non-cumulative.

## Research questions
1. Does screenshot + GUI-agent feedback, with backtracking and select-best, beat execution-only feedback across many engine LLMs?
2. Can the scores produced inside that loop train 7B–8B engines as step-level rewards, and which advantage design matters?
3. Is a small open VLM a good enough judge, and can it replace the coding LLM?

## Methodology
One <Term def="Our agent: an iterative loop of code edit → execute → screenshot feedback → GUI-agent testing, with backtracking and select-best">WebGen-Agent</Term> step is edit → execute → gather feedback (Fig.1). For the dashboard, the coding LLM (behind a Bolt.diy-style prompt inside <Term def="StackBlitz's in-browser Node.js runtime; the sandbox in which the generated site is installed and served">WebContainer</Term>) writes the Vite + React files; dependencies install, the dev server starts. A <Term def="Vision-language model: an LLM that also takes images as input; here Qwen2.5-VL-32B-Instruct">VLM</Term> sees the landing-page screenshot and returns a description (teal header titled Financial Dashboard, a search bar, four equal-sized cards), an appearance grade, and suggestions (Fig.4–5). This [LLM-as-a-judge](../../knowledge/llm-as-a-judge/) on pixels is not enough alone: the page grades 4 and looks finished, yet the cross-company comparison is unreachable. So once the agent emits `screenshot_validated`, it writes a test instruction for a <Term def="A VLM-driven browser agent that clicks, types, and scrolls through the site following a natural-language instruction; here it doubles as our functional evaluator">GUI agent</Term> — verify the colours, browse company data, view consolidated reports, perform comparisons (Fig.6) — which clicks through the site; its trajectory is graded 1–5 with fix suggestions (Fig.7). First pass: `shot=4, gui=2`, "critical features are hidden behind repetitive interactions; add drill-down options". The next edit adds a comparison mode, financial ratios, and export; second pass `shot=4, gui=5`, `finish` (Fig.9). Because a later edit sometimes makes the site worse, after five consecutive execution errors we <Term def="Restoring the codebase and trajectory to the best earlier stored step after 5 consecutive execution errors">backtrack</Term> to the best stored step, and at termination we <Term def="Returning the stored step with the highest GUI score (tie-break: screenshot score, then latest) instead of the last step">select-best</Term> (§2.1, Alg.1–2).

A 7B engine needs two training stages. First a light <Term def="Supervised fine-tuning on ~700 WebGen-Agent trajectories generated by DeepSeek-V3, one epoch">SFT</Term> warm start — not optional: raw Qwen2.5-Coder-7B-Instruct fails to even start the site on 24.3% of test cases (Tab.1), and a rollout group in which every site fails yields identical rewards, hence zero advantage, so <Term def="Group Relative Policy Optimization: policy-gradient RL that normalises rewards within a group of rollouts for the same prompt; no value network">GRPO</Term> has nothing to climb. Then <Term def="Our RL method: GRPO where the tokens of each step get their own advantage from that step's screenshot + GUI score, not one trajectory-level advantage">Step-GRPO</Term> on 500 <Term def="A pool of website-generation instructions from which we sample the 500 RL prompts (§3.1); its overlap with WebGen-Bench is Not reported">WebGen-Instruct</Term> prompts, 5 rollouts each, one epoch (§3.1). In the dashboard rollout, step 1 earns <M tex="r_1 = 4 + 2 = 6" />, step 2 earns <M tex="r_2 = 4 + 5 = 9" />; each step's edit tokens get their own advantage, normalised against every step reward of all five rollouts. We do not fold future rewards into earlier steps: the score at step <M tex="j" /> already measures the codebase at step <M tex="j" />. Outcome-only reward would give both steps the same credit; cumulative credit would drag step 1 up on step 2's success — both lose in Tab.3.

<Pass title="Method details and formal definitions">
<Definition term="Agent trajectory (§2.1)">
<MathBlock>{`T = [\\,I,\\ \\Delta C_1, O_1, F_1,\\ \\dots,\\ \\Delta C_K, O_K, F_K\\,],\\qquad F_k = [F_{\\mathrm{shot},k},\\ F_{\\mathrm{gui},k}]`}</MathBlock>
<M tex="I" /> is the system prompt concatenated with the user request; <M tex="\Delta C_k" /> is the edit that produces codebase <M tex="C_k" />; <M tex="O_k" /> is the stdout/stderr of dependency installation and service start. Maximum 20 iterations, temperature 0.5 (§3.1).
</Definition>

<Definition term="Screenshot feedback and appearance grade (Eq.1, Fig.5)">
<MathBlock>{`F_{\\mathrm{shot}} = \\big(\\text{Description},\\ \\text{Score}_{\\mathrm{shot}},\\ \\text{Suggestions}_{\\mathrm{shot}}\\big),\\qquad \\text{Score}_{\\mathrm{shot}} \\in \\{0,1,\\dots,5\\}`}</MathBlock>
Scale: 0 blank page or only an error message; 1 major rendering issues; 2 partial rendering with noticeable errors; 3 mostly rendered, unremarkable; 4 rendered well, harmonious, modern; 5 flawless. Criteria: successful rendering, content relevance, layout harmony, modernness and beauty. Fig.4 is a separate pass that returns `is_error`, an error message, the description, and suggestions.
</Definition>

<Definition term="GUI-agent feedback and functional grade (Eq.2, Fig.7)">
<MathBlock>{`F_{\\mathrm{gui}} = \\big(\\text{Score}_{\\mathrm{gui}},\\ \\text{Suggestions}_{\\mathrm{gui}}\\big),\\qquad \\text{Score}_{\\mathrm{gui}} \\in \\{1,\\dots,5\\}`}</MathBlock>
1: the vast majority of tested functions fail; 2: many fail, few work; 3: about half work; 4: most work, minor issues; 5: all tested functions work exactly as expected. The judge also emits `test_passed` and, on failure, improvement suggestions. The test instruction is generated by the coding LLM from a one-shot prompt that asks it to turn every requirement into concrete checks (Fig.6).
</Definition>

<Definition term="Best-step selection (Alg.2) and backtracking (Alg.1, Alg.3)">
Every step that reaches GUI testing stores <M tex="\langle t, C, \text{score}_{\mathrm{shot}}, \text{score}_{\mathrm{gui}} \rangle" />. With <M tex="g_{\max} = \max_s \text{score}_{\mathrm{gui}}" /> and <M tex="S_g = \{ s : \text{score}_{\mathrm{gui}} = g_{\max} \}" />, the selected step is <M tex="\arg\max_{s \in S_g} \text{score}_{\mathrm{shot}}" />, the latest one on a tie. After five consecutive execution errors the codebase is restored to that step and the trajectory truncated to end just after its feedback (Alg.3); Fig.10 shows this firing on a mismatched JSX tag. At termination the same selector returns the final codebase.
</Definition>

<Definition term="Step-GRPO objective and step-level advantage (Eq.3–4)">
<MathBlock>{`\\mathcal{J}(\\theta) = \\mathbb{E}\\Big[\\tfrac{1}{G}\\sum_{i=1}^{G} \\tfrac{1}{|o_i|}\\sum_{t=1}^{|o_i|} \\min\\!\\Big(\\rho_{i,t}\\hat A_{i,t},\\ \\mathrm{clip}(\\rho_{i,t},\\,1-\\epsilon,\\,1+\\epsilon)\\,\\hat A_{i,t}\\Big)\\Big],\\qquad \\rho_{i,t} = \\frac{\\pi_\\theta(o_{i,t}\\mid q, o_{i,<t})}{\\pi_{\\theta_{\\mathrm{old}}}(o_{i,t}\\mid q, o_{i,<t})}`}</MathBlock>
<MathBlock>{`r^{(i)}_j = \\text{Score}^{(i)}_{\\mathrm{shot},j} + \\text{Score}^{(i)}_{\\mathrm{gui},j},\\qquad \\hat A^{(i)}_j = \\frac{r^{(i)}_j - \\mathrm{mean}(R)}{\\mathrm{std}(R)},\\qquad R = \\big\\{\\{r^{(1)}_1,\\dots,r^{(1)}_{K_1}\\},\\dots,\\{r^{(G)}_1,\\dots,r^{(G)}_{K_G}\\}\\big\\}`}</MathBlock>
<M tex="q" /> is the instruction, <M tex="\{o_i\}_{i=1}^{G}" /> the group of <M tex="G=5" /> trajectories. The loss is applied only to the model's edit tokens <M tex="\Delta C_1,\dots,\Delta C_K" />; every token of step <M tex="j" /> receives <M tex="\hat A^{(i)}_j" />; there is no KL term (following Qian et al. 2025). The two ablated alternatives: naive outcome GRPO uses <M tex="\max_j r^{(i)}_j" /> as a single trajectory reward; cumulative advantage sums the normalised rewards of all subsequent steps (Shao et al. 2024).
</Definition>

<Definition term="WebGen-Bench metrics (§3.1, Tab.1)">
Each of the 647 test cases is executed by a GUI agent driven by Qwen2.5-VL-32B-Instruct and judged Yes, Partial, or No, or counted as Start failed if the site does not serve. Accuracy is the share of test cases passed; the Tab.1 rows are consistent with Yes + ½·Partial (22.6 + 7.6/2 = 26.4), the weighting inherited from Lu et al. 2025b. Appearance score is GPT-4o's appearance grade (§3.1); its scale and aggregation are inherited from Lu et al. 2025b and not restated here. Both judges are the benchmark's, not ours.
</Definition>

**Training details (§3.1, App.A).** SFT: learning rate 4e-5, batch 32, one epoch, on approximately 700 DeepSeek-V3 trajectories collected with rejection sampling. Step-GRPO: learning rate 1e-6, batch 16, 5 samples per instruction, 500 WebGen-Instruct instructions randomly sampled and manually filtered for ambiguity, one epoch, no KL term; more than 24 hours on 16 A800 GPUs. Training on more samples "does not yield noticeable gains" (no numbers given). The same recipe is applied to Qwen3-8B.

  { title: "Screenshot feedback", body: "The VLM describes the landing page, grades it 0–5, suggests fixes; the agent decides whether to iterate on looks or emit screenshot_validated." },
  { title: "GUI-agent testing", body: "The coding LLM writes a test instruction; the GUI agent browses; the trajectory is graded 1–5 with fix suggestions; pass means finish." },
  { title: "Select best", body: "Restore the step with the highest GUI score, then highest screenshot score, then the latest." },

## Main result
Same engine, different scaffold: <Finding src="Tab.1">Claude-3.5-Sonnet goes from 26.4% / 3.0 (Bolt.diy) to 51.9% / 3.9 in WebGen-Agent; DeepSeek-V3 from 20.8% / 2.0 to 52.6% / 3.8; DeepSeek-R1 from 27.8% / 2.5 to 46.4% / 3.8</Finding>. The best engine is open-weight: <Finding src="Tab.1">Qwen3-Coder-480B-A35B reaches 58.2% / 4.3 and Qwen3-Coder-30B-A3B 52.8% / 4.0</Finding>. For the small engines we train, <Finding src="Tab.1">Qwen2.5-Coder-7B-Instruct goes 12.4% → 38.9% (SFT) → 45.4% (Step-GRPO) with appearance 1.6 → 3.4 → 3.7, and Qwen3-8B goes 34.1% → 38.6% → 43.4% (3.2 → 3.4 → 3.6)</Finding>. The dashboard's tested requirements — browse, report, compare — are the functional test cases accuracy counts and a screenshot cannot certify.

## Key findings
- <Finding src="Tab.2">The workflow pieces pull in different directions: execution-only 45.9% / 3.0 → +screenshot 46.6% / 3.6 → +GUI-agent 49.9% / 3.4 → +backtrack 51.2% / 3.7 → +select-best 52.6% / 3.8 (DeepSeek-V3)</Finding>. GUI testing is the largest accuracy lever (+3.3) but costs 0.2 appearance because functional edits break layout; backtracking and select-best recover it.
- <Finding src="Tab.3">Same reward, different advantage: naive outcome GRPO 42.5%, cumulative-advantage Step-GRPO 38.7% (below the SFT baseline of 38.9%), per-step non-accumulated advantage 45.4%; a second SFT epoch is flat at 39.3%</Finding>. Folding future steps into the current one adds noise to a state measurement.
- <Finding src="Tab.3">Both reward halves are necessary: screenshot-only 40.2% / 3.5, GUI-only 40.4% / 3.4, the sum 45.4% / 3.7</Finding>.
- <Finding src="Tab.4">The judge can be small, the coder cannot: swapping Qwen2.5-VL-32B for GPT-4o as feedback VLM moves DeepSeek-V3 from 52.6% / 3.8 to 52.1% / 3.6, while using Qwen2.5-VL-32B as the coding LLM collapses to 5.6% / 1.3</Finding>.
- <Finding src="Tab.5, Tab.6">Human audit: screenshot scores agree with annotators 93.6–95.6% and GUI-agent scores 89.6–92.2% (standard errors 0.20–0.26 and 0.31–0.44); 98.3% of generated GUI test instructions cover at least 75% of the requirements and 77.2% cover roughly all of them</Finding>. The functional half still carries a one-in-ten error that RL can exploit.
- <Finding src="Tab.7">Step-GRPO's gain over SFT on the 7B model lands where interaction is tested: User Interaction 33.5% → 41.1%, Data Management 33.8% → 47.8%, Functional Testing 23.5% → 30.7%, while Content Presentation slips 53.4% → 51.1%</Finding>. The reward taught the model to make things work, not to write more content.

## Implications
We closed <Related>the WebGen-Bench line (Lu et al. 2025b) and Bolt.diy-style scaffolds</Related> into an RL loop with no human labels, between execution-reward code RL (<Related>RLEF, SWE-RL-style outcome rewards</Related>) and process-reward methods that need ground-truth steps. Lessons for interactive component synthesis: keep the appearance judge and the behaviour judge separate and sum them; make the advantage per-step and non-cumulative when the reward is a state measurement; keep a select-best snapshot because repair edits regress. <FollowUp>Whether the recipe holds for a single stateful component (a colour picker, a sortable table) where the tester must check state transitions</FollowUp>. <FollowUp>Whether the one-in-ten GUI-score error becomes reward hacking at larger RL budgets than our one epoch on 500 prompts, and whether [mutation-hardened checks](../../knowledge/mutation-hardened-checks/) would close it</FollowUp>. <FollowUp>Replacing the VLM tester with deterministic checks derived from the instruction ([model-based GUI testing](../../knowledge/model-based-gui-testing/)) to remove judge noise</FollowUp>.

## Limitations
- <Caveat>We know our in-loop GUI judge is the same VLM WebGen-Bench uses for functional testing (Qwen2.5-VL-32B-Instruct, §3.1), so the loop partly optimises against the benchmark's own grader; only the appearance judge (GPT-4o) differs</Caveat>.
- <Caveat>We did not run seeds or report confidence intervals; every number is one run, and several ablation deltas (0.7–1.5 points) sit inside the ±1-point jitter across iteration budgets in Tab.8</Caveat>.
- <Caveat>We trained only 7B/8B models because Step-GRPO takes over 24 hours on 16 A800s (App.A); scaling to 30B–72B is future work, our SFT data is distilled from DeepSeek-V3 so raw-model → RL without SFT is untested, and per-task cost is Not reported</Caveat>.
- <Caveat>We grade only the landing-page screenshot and ignore response speed, network conditions, and multi-page appearance (§2.1, App.A); we did not check overlap between the 500 RL prompts and the 101 test instructions</Caveat>.

## Critiques and Questions
1. The advantage normalises each step against the pool of all steps of all rollouts, so an early `4+2` step and a final `4+2` step earn the same credit; the model is rewarded for being in a good state, never for improving one. A delta reward (gain over the previous step) is untested.
2. The GUI test instruction is written by the coding LLM (Fig.6), so during RL the policy partly controls its own test; coverage was audited only on untrained engines (Tab.6). And §2.1 says the engine LLM grades the GUI trajectory while §3.1 and App.E credit the feedback VLM — Unclear which model produces the reward.
3. Much of the weak-engine gain is the Start-failed column (raw Qwen2.5-Coder-7B: 24.3%, Tab.1): part of the SFT jump is learning the Bolt artifact format, and nothing separates that from website skill.
4. Accuracy is judged by a GUI agent that agrees with humans nine times in ten (Tab.5); nothing bounds how much of the 45.4% survives a human pass.
