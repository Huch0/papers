<TLDR>WebRISE compiles each web-generation task into an Interaction Contract Graph (states, user-intent transitions, DOM/visual assertions) and scores a generated page by how many requirement-induced transitions it actually executes correctly in a browser, not by how it looks; across 442 tasks and 14 MLLMs the best model passes only 65.6% of transitions.</TLDR>

<WhyItMatters>This is the most direct benchmark to date for the "does the interactive component actually work" question: an implementation-agnostic, execution-grounded oracle for stateful UI behavior, with explicit vs. implicit (product-level) requirements split out. Its ICG + adaptive-agent + dual-oracle loop is essentially the verifier one would want inside an execution-grounded synthesis/repair loop, and its results show open-weight models (Kimi-K2.6, Qwen3.6-27B) are competitive.</WhyItMatters>

## Motivation
I am given a spec ("build a shopping cart page: users can check items, totals update, checkout is disabled when nothing is checked") and an MLLM hands me a single HTML file. When is that file *usable*? <Problem>A page can render every expected control and still be broken: the filter runs but the list does not change, the cart checkbox toggles but the total and the checkout button stay stale (Fig.7).</Problem> The interaction-aware benchmarks that exist (<Related>ArtifactsBench's dynamic screenshots + MLLM checklists, FrontendBench's scripts, WebGen-Bench's navigation-agent checkpoints, IWR-Bench's video trajectories</Related>) all made interaction *observable*, but they judge it through **local evidence**. Two things break as a consequence (§1): (i) <Problem>event-centric evaluation verifies that an action produces *a* response but never enumerates which requirement-induced states and transitions must be covered</Problem>; (ii) <Problem>the state-consistency gap: a local check passes even when the page violates cross-component, cross-view, or cross-step constraints such as filter–pagination synchronization, count updates after deletion, or draft preservation across navigation</Problem>. Scripts add a further problem: <Problem>selector-based scripts only run against the implementation the script author had in mind, so a differently-structured but correct page fails</Problem>. And nobody separated what the user *said* from what any competent product must *also* do (Tab.1: no prior benchmark has an implicit-requirement column).

## Contribution (what's new)
The insight is to treat a requirement set as inducing a **finite, observable state machine**, and to grade a page by *conformance* to that machine under browser execution. Concretely: <Novelty>each task's requirements are compiled into an <Term def="A per-task graph G=(S,T,Φ,M): stable UI states S, user-intent transitions T, DOM/visual predicates Φ, and a coverage mapping M from requirements to the transitions and assertions that verify them.">Interaction Contract Graph (ICG)</Term>, where states are requirement-relevant UI configurations (not DOM snapshots), transitions are user *goals* (not click sequences), and every transition carries DOM and visual assertions traced back to a named requirement</Novelty>. The form is forced by the failures above. If states were DOM snapshots, the contract could only match one implementation, so states are described behaviorally and a <Novelty>contract-guided agent re-plans each transition on the live page from an indexed DOM observation whose indices are regenerated after every action</Novelty>: no fixed selectors survive. If transient effects (spinners, toasts, debounce) were states, the graph would explode and become unreplayable, so they are <Novelty>pushed into `[CHANGE]` DOM assertions on the transition</Novelty>, while `[AFTER]` assertions and visual postconditions check the settled outcome. If a broken upstream transition made every downstream one fail, one bug would be counted ten times, so <Novelty>source states are restored by replaying previously *passed* trajectories, and unreachable states yield SKIPPED rather than FAIL</Novelty>. And because the mapping M links every assertion to a requirement, the same run yields separate <Term def="Coverage of user-stated functional affordances (search, sort, drag, navigate).">Re%</Term> (explicit) and <Term def="Coverage of unstated product-level constraints: state synchronization, boundary feedback, pagination reset, loading feedback, stale-state removal.">Ri%</Term> (implicit) scores. The <Term def="Requirement-induced state evaluation: the paper's name for scoring by transition conformance rather than local action success.">WebRISE</Term> benchmark itself is 442 expert-sourced tasks, each instantiated under five input modalities sharing one ICG.

## Research questions
1. If interaction is graded as requirement-induced state-transition conformance rather than local action success, how far are current MLLMs from usable web artifacts?
2. Which input modality (Text, Markdown, Sketch, Image, Video) best conveys *interactive* behavior, and does visual fidelity track behavioral correctness?
3. Are implicit, product-level constraints a distinct bottleneck from explicit functions?
4. Does an ICG-based evaluator actually detect state defects that checkpoint-style evaluation misses?

## Methodology
Running example (the paper's Fig.7): a cart page with one checked item. Requirement: unchecking the last item zeroes the totals and disables checkout. The ICG has a state S_k ("one item checked, totals shown"), a transition "uncheck the only checked item" to S_k+1, a DOM assertion `[AFTER] the Proceed-to-Checkout control is disabled`, and a visual postcondition "checked subtotal shows zero and dependent values reflect no checked items". The agent, seeing `[7] <input type=checkbox checked>`, issues `Uncheck [7]`; after a settle delay the DOM log and the pre/post screenshots go to two LLM judges. The failing page (Fig.7) returns `checkout-btn ... disabled:false` and a subtotal still at ¥398, so both assertions are NO, the transition is FAIL, and via M the implicit requirement "dependent totals synchronize" is marked unsatisfied, while the explicit "user can uncheck items" is still satisfied. That attribution is the whole point.

<Pass title="Method details: contract construction, execution loop, oracles, metrics">
**Contract construction (§3.3, four steps).** (1) Anonymous industry practitioners fill collection templates with domain-grounded requirements, interaction goals, and data assumptions (8 domains, 35 scenarios, Fig.3; Productivity Tools 23.76%, Commerce 16.97%). (2) Requirements are normalized into explicit + implicit sets R_τ. (3) An LLM derives a <Term def="Minimal functional-readiness spec for first load (initial data, filters, navigation entries) that deliberately does not fix layout, DOM hierarchy, style, or element counts.">Test Data Contract</Term> and implementation-neutral test items (prompts in Fig.15–16; rule 5 of the TDC prompt forbids leaking implicit requirements into the spec the model sees). (4) ICG compilation (Fig.17): stable configurations become states, behaviors become transitions with `[CHANGE]`/`[AFTER]` DOM assertions and unprefixed visual postconditions; preconditions are allowed only on T1; independent features fan out from a shared source state; compound transitions may chain 2–3 operations only to test state interference. Every ICG is validated by a ground-truth HTML page generated from the *full* requirement set: a task survives only if GT page, ICG, and evaluator form a stable executable loop (§3.4). The GT page also supplies the Image/Video specs but is not a reference implementation.

**Modalities (Tab.6).** Text = scenario + explicit requirements + TDC; Markdown = Text + symbolic layout regions; Sketch = low-fidelity wireframe with content stripped; Image = high-fidelity screenshot with visually-inferable explicit requirements *removed from the text*; Video = interaction demonstration rendered from a validated ICG transition chain. Same task, same contract, 2,210 task–modality instances.

**Deterministic tie-breaks in the DOM judge (§B.2).** Non-interactivity is checked as `pointer-events: none` → native `disabled`/`aria-disabled` → class tokens; selection as `aria-selected/pressed/checked` → class tokens; ambiguous element localization returns UNCERTAIN rather than guessing.

**Metrics (§4.4).** Per task: <M tex="S\% = |S^{reach}|/|S|" />, <M tex="T\% = |T^{pass}|/|T|" />, and requirement coverage

<MathBlock>{`C(\\hat R) = \\frac{1}{|\\hat R|}\\sum_{r\\in\\hat R} \\mathrm{sat}(r)\\times 100,\\qquad \\mathrm{sat}(r)=1 \\iff \\text{all checks mapped to } r \\text{ pass}`}</MathBlock>

applied to explicit, implicit, and all requirements gives Re%, Ri%, R%. Everything is macro-averaged over tasks (Eq.8). The leaderboard "Overall" is the auxiliary <M tex="O(\theta)=\frac{1}{|M|}\sum_m \frac{T+R+V}{3}" /> (Eq.10), where V is a modality-specific visual score (layout blocks + WCAG contrast + a Gemini-3-Flash-Preview aesthetics judge, §B.5). Safety/robustness rules R1–R7 (CSRF, XSS-prone DOM APIs, input constraints, debounce guards, loading states) are a separate auxiliary pass rate (Tab.3, Tab.15–16).

**Reliability checks (§A.3, §C.1).** On 300 stratified interaction cases, requirement-to-ICG construction reaches 0.86 accuracy / κ=0.78 vs. human majority and the functional evaluator 0.84 / κ=0.74, against human–human 0.88 / κ=0.81 (Tab.7). Visual evaluator: 0.81 / κ=0.69 vs. human–human 0.85 / κ=0.77 (Tab.8). GPT-5-mini as transition judge detects 95/100 GT-vs-defect pairs vs. 97/100 for GPT-5.4 (Tab.10).
</Pass>

## Key findings
- <Finding src="Tab.2, §5.2">Visual quality is not a proxy for behavior</Finding>: Qwen3.6-35B-A3B scores V=80.8 on Markdown while T=15.5 and R=19.2; at the modality level, Sketch has the highest average V (81.4) but trails Image and Video on every interaction metric (Tab.11). Visual scores also cluster tightly (Fig.4) whereas T spans 15–66, so V barely discriminates models.
- <Finding src="Tab.11, §C.2">Video is the strongest modality for interaction, and it specifically helps *implicit* behavior</Finding>: averaged over models, Video vs. Text improves T by 8.8 (54.8 vs 46.0), R by 8.3 (57.2 vs 48.9), and Ri by 10.6 points (53.6 vs 43.0), and shrinks the explicit–implicit gap Δ=Re−Ri from 13.5 to 7.7. Image wins on *explicit* coverage (Re=62.8) by showing the visible components; the temporal channel is what transmits state changes.
- <Finding src="Tab.13, Fig.8">Video's advantage concentrates on hard tasks</Finding>: on the Hard50 split (lowest model-averaged R) Video beats Image by 4.9 T / 6.1 Ri / 4.8 R, but only 1.6 / 1.7 / 1.4 on Easy50. Hard50 is really hard (T 22–37 vs 69–76 on Easy50) and shows more Availability (13.9% vs 6.0%) and Feedback-and-Boundary (21.6% vs 17.9%) failures, i.e. missing affordances and missing edge-state feedback.
- <Finding src="Fig.6, §5.3.5">Failures happen *after* the control exists</Finding>: for both GPT-5.5 and Kimi-K2.6, State-and-Logic errors are 57.2% / 59.7% of failed transitions and Feedback-and-Boundary 24.6% / 23.5%; Availability is only 12.1% / 11.0% and Execution 6.2% / 5.8%. The bottleneck is maintaining state updates, result logic, validation, and boundary feedback under user actions, not rendering the widget.
- <Finding src="Tab.4, Tab.14, §C.5">ICG scoring catches state corruption that checkpoint-style scoring passes</Finding>: on 25 defects injected into GT-validated pages, ICG detects 16/25 (64%) vs. 8/25 under a broad WebGen-Bench criterion (any non-YES) and 1/25 under a strict one (≥1 NO). The 13 ICG-only cases are long-range constraints: record loss under repeated operations (4), cross-feature side effects (5), draft loss across navigation (2), missing explicit-action gating (1), pre/post inconsistency (1). Checkpoints ask "did the target appear done?"; the ICG follows the chain and checks invariants.
- <Finding src="Fig.5, §5.3.3">Scaling has a knee</Finding>: within Qwen3.5, Overall is flat from 27B (51.7) to 122B-A10B (51.1) and jumps at 397B-A17B (57.6), with the largest gains under Text and Markdown where layout, logic, and state must all be inferred from thin specs. Note the middle model is a sparse MoE with 10B active parameters, so "flat" partly reflects active-parameter count.
- <Finding src="Tab.3, Tab.15–16">Safety and robustness are uniformly poor and not fixed by model strength or richer input</Finding>: GPT-5.5 passes 41.3% of checks, most models 25–32%. For GPT-5.5 the weakest rule families are async/interaction robustness (20.5%), DOM-rendering safety (25.5%), and request security (26.4%); missing input constraints pass only 2.9% of 2,956 checks and repeated-click guards 1.8%.
- <Finding src="Tab.7–8">The pipeline's automatic pieces are near human agreement</Finding>: κ=0.78 for requirement-to-ICG construction and κ=0.74 for the functional evaluator vs. human–human κ=0.81; the visual judge is weaker (κ=0.69 vs 0.77).

## Implications
The result that matters for anyone building generators is the decomposition: models mostly *can* expose the control (Availability + Execution under 20% of failures) and mostly *cannot* keep dependent state coherent. That points optimization at state logic, not layout. The ICG machinery is reusable as a reward or repair signal: it is implementation-agnostic (no selectors), it localizes failures to a transition and a requirement with an evidence bundle, and it explicitly distinguishes SKIPPED/BLOCKED from FAIL, which is exactly what a repair loop needs to avoid chasing downstream symptoms. <FollowUp>Turning ICG transition verdicts into per-transition rewards for RL or into structured repair prompts (the evidence bundle already contains the failed assertion and the contradicting DOM fragment) is the obvious next step; the paper does not attempt it.</FollowUp> <FollowUp>The Video finding suggests that a demonstration of the *target behavior* is a far better spec than a screenshot for stateful components; synthetically rendering such demos from a contract (as WebRISE does from the GT page) is a cheap data-generation route.</FollowUp> <Related>WebRISE sits downstream of WebGen-Bench (checkpoints via navigation agent), FrontendBench (scripted assertions), ArtifactsBench (dynamic screenshots + MLLM checklist), IWR-Bench (video to interactive page), Interaction2Code, and the agentic-verification line of WebVia; it is closest in spirit to model-based GUI testing, applied as a benchmark oracle.</Related> <FollowUp>Kimi-K2.6 and Qwen3.6-27B beating several proprietary systems, and Kimi-K2.6 nearly matching GPT-5.5 on Video T (63.7 vs 65.6), means open-weight models are a credible base for execution-grounded fine-tuning on this task.</FollowUp>

## Limitations
- <Caveat>Self-contained single-file HTML in a controlled browser: no back end, auth, external APIs, persistent DB, concurrency, or long sessions (Limitations §). Scores measure front-end interaction conformance, not deployment readiness.</Caveat>
- <Caveat>Coverage is bounded by what the LLM-generated test items and ICG enumerate. The paper itself notes the 9/25 missed injected defects show the evaluator is "not yet exhaustive" (§5.3.4).</Caveat>
- <Caveat>The judges are LLMs: GPT-5-mini for DOM/visual assertions, Gemini-3-Flash-Preview for visual quality; the authors say scores should be read as rank orderings, not absolute values, because of prompt sensitivity and API drift (Ethics §).</Caveat>
- <Caveat>Contributors come primarily from one region, so "implicit product-level constraints" encode that region's product conventions (Ethics §).</Caveat>
- <Caveat>Single run per model–task–modality; no variance, seeds, or confidence intervals are reported anywhere, and several Overall gaps are under 1 point (Qwen3.6-27B 62.5 vs Qwen3.6-Plus 62.5 vs Gemini 3.1 Pro 61.9).</Caveat>
- <Caveat>Generation prompts, decoding settings, and whether models were allowed multiple attempts or tool use are not reported in the main text (deferred to Sec. A.2 / Appendix D, which lists only the evaluation-side prompts).</Caveat>
- <Caveat>Code and data are promised "upon acceptance"; nothing is released at v1 (§E).</Caveat>

## Critiques and Questions
1. **Circularity between ICG and GT page.** Tasks are kept only when a GT page generated from the full requirements passes the ICG (§3.4). This filters out contracts that are hard to satisfy or ambiguous, and the *same* LLM family that writes the ICG writes the GT. The κ=0.78 construction agreement is reassuring but is measured on a 300-case sample after filtering. Unclear how many tasks were discarded.
2. **The Video modality is rendered from the GT page's ICG chain.** So Video literally shows the model the transitions it will be tested on; its +10.6 Ri advantage may partly be "the test was demonstrated" rather than "temporal evidence is informative". The Hard50 result (Video helps most where behavior is non-trivial) is consistent with both readings.
3. **T% penalizes BLOCKED and SKIPPED equally with FAIL.** Only PASS counts (§4.4). A page whose first transition is unreachable gets near-zero T regardless of the rest. S% would separate these, but the main table (Tab.2) hides S; Tab.12 shows S tracks T within ~5 points, so it is not distorting rankings, but per-model BLOCKED/SKIPPED rates are not reported.
4. **Judge agreement is decent, not high.** κ=0.74 for the functional evaluator means a non-trivial fraction of the ~5,495 × 14 × 5 transition verdicts are noisy; with single runs and no CIs, the 1–2 point differences the text discusses (e.g. Qwen3.6-27B vs Qwen3.6-Plus) should not be read as rankings.
5. **The defect-injection comparison is against a re-implementation of WebGen-Bench criteria**, not against WebGen-Bench's own pipeline; 25 injected defects is small, and how they were chosen is not described (selection toward state-consistency defects would favor ICG by construction).
6. **The "scaling knee" is three points on a family that mixes dense and MoE models** (27B dense, 122B-A10B, 397B-A17B); active-parameter count is roughly 27B → 10B → 17B, so the curve is not a clean scale sweep.
7. **The Overall score mixes V in at one-third weight**, contradicting the paper's own argument that V is a poor proxy; for the paper's thesis, T and R alone are the leaderboard.

## Glossary
- <Term def="Multimodal large language model: an LLM that accepts images/video as well as text.">MLLM</Term>
- <Term def="A single self-contained HTML file (HTML+CSS+JS) that must run in a browser with no backend or prepared runtime state.">web artifact</Term>
- <Term def="A behavior the user asked for explicitly, e.g. search, filter, sort, drag, navigate.">explicit requirement</Term>
- <Term def="A product-level constraint not stated by the user but expected of any working page: state sync across components, boundary feedback, pagination reset, loading feedback, stale-state removal.">implicit requirement</Term>
- <Term def="DOM assertion that must hold at some point during the transition's event timeline; used for transient signals (loading, saving, debounce, temporary disabled).">[CHANGE]</Term>
- <Term def="DOM assertion that must hold in the final stable DOM after the transition; used for persistent outcomes.">[AFTER]</Term>
- <Term def="A behavioral (not pixel) condition judged from before/after screenshots, e.g. 'the list is sorted by price'.">visual postcondition</Term>
- <Term def="Serialized view of the live page listing only interaction-relevant elements with ephemeral indices [N] that are regenerated after each action.">indexed DOM observation</Term>
- <Term def="Transition outcomes: PASS (all checks hold), FAIL (executable but an assertion fails), BLOCKED (agent cannot complete within budget), SKIPPED (source state unrestorable).">PASS/FAIL/BLOCKED/SKIPPED</Term>
- <Term def="State reachability: fraction of ICG states reached via passed transitions.">S%</Term>
- <Term def="Transition validity: fraction of ICG transitions with outcome PASS.">T%</Term>
- <Term def="Overall requirement coverage: fraction of requirements whose mapped checks all pass; Re%/Ri% restrict to explicit/implicit.">R%</Term>
- <Term def="Auxiliary 0–100 visual-quality score from layout modeling, WCAG contrast, and a VLM aesthetics judge, with modality-specific weighting.">V</Term>
- <Term def="The 50 tasks with lowest / highest model-averaged R; used to compare failure profiles.">Hard50 / Easy50</Term>
- <Term def="Prior benchmark (Lu et al. 2026) that scores generated sites by having a navigation agent verify expected-result checkpoints; used here as the checkpoint-style baseline in defect injection.">WebGen-Bench</Term>
- <Term def="Cohen's kappa: chance-corrected agreement between two raters on categorical labels.">κ</Term>
