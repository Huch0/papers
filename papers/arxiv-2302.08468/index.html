Curated byChiyeong Heo

Rerank programs sampled from a frozen code LLM with a small learned verifier (about 0.5% of the generator’s size) that reads the NL input, the candidate program, and its actual execution result — multiplying verification probability with generation probability and marginalizing over samples that execute to the same result — for then-new SOTA execution accuracy on Spider, WikiTQ, GSM8k, and MBPP (ICML 2023).

The canonical execution-grounded-but-learned contrast for TDE (survey cat. B, confirmed by the paper): LEVER shares TDE’s premise that the executed outcome — values, types, errors — carries the correctness signal, but its adjudicator is a trained soft classifier reranking one-shot samples: no acceptance suite compiled from the instruction, no red–green iteration, no gating, and the top-ranked program ships even if every candidate scores low. Its own failure analysis (wrong programs whose results share type and range with the correct one blind the verifier) is precisely the ambiguity a decidable, environment-computed suite would remove.

Motivation

Few-shot code LLMs lack precision, yet when enough samples are drawn the correct program is usually somewhere in the set — so selection, not generation, becomes the bottleneck, and finetuning generator-scale models is costly enough that improving a frozen LLM is the attractive path (§1). Existing selectors are blunt: filtering by test cases assumes test cases exist, which many real language-to-code applications lack, and execution-consistency heuristics — error pruning, majority voting — cannot read the semantic features of an execution result (data type, value range, content) that often indicate whether a program is correct (§1). Meanwhile, trained verifiers had only been shown for natural-language math/commonsense solutions (Cobbe et al. 2021; Shen et al. 2021; Li et al. 2022b), leaving open whether verification works for programs, where an executable artifact and an observable result are available.

Contribution (what’s new)

Cast sample selection as learned verification conditioned on execution: a small binary classifier scores P(v=1 | NL, program, execution result), and the reranking score multiplies verification probability with the LLM’s generation probability, then marginalizes over programs that execute to the same result (§2.2). The form is forced by how the baselines fail: error pruning only discards crashes, likelihood ranks fluency rather than correctness, and voting counts results without judging them — the untapped signal lives in the executed output, which only a trained reader can exploit. Labels are mechanical — v = 1(ẑ = z*), positive iff the sample’s execution result equals the gold one (all test cases for MBPP) — so training needs no human judgment and works weakly supervised. The authors position this as the first comprehensive execution-based learned verification across language-to-code tasks (§6).

Research questions

  1. Does a learned, execution-conditioned verifier beat execution heuristics — greedy, likelihood, EP+ML, voting — across domains (SQL, math, Python) and LLMs?
  2. Which ingredients carry the gain: the execution result, gold programs, result aggregation, verifier size?
  3. How much training data and sampling budget does verification need, and does a verifier transfer across LLMs?

Methodology

Three inference steps (Fig.1): sample k programs (20–100 per input, Tab.1) from the code LLM by few-shot prompting with temperature sampling and deduplicate; execute every candidate; score each with the verifier and rerank by generation × verification probability, summing over candidates with identical execution results and emitting a program from the top-scoring result (ties broken randomly). Training data comes from running the same sampling on the training set and labeling each sample by executing it against the gold result. Benchmarks: Spider (text-to-SQL), WikiTQ (table QA via SQL), GSM8k (math via Python; inherently weakly supervised — no gold programs exist), MBPP (basic Python with 3 test cases); generators: code-davinci-002, InCoder-6B, CodeGen-16B-multi; metric: execution accuracy.

Method details
  1. Sample and deduplicate (§2.2, App.A) — Few-shot prompt the frozen LLM (8 fixed exemplars; 3 for MBPP; only 2 fit InCoder/CodeGen on Spider) and draw k samples at temperature 0.6 (Codex) or 0.8 (InCoder/CodeGen); deduplicate to n unique candidates. Sampling replaces beam search, which degenerates on code and is unavailable for Codex.
  2. Execute and represent (§3.4) — Run every candidate. Verifier input = concatenation of the NL input, the program, and a textual rendering of the result: linearized result tables (Spider/WikiTQ), the final value of the variable named 'answer' (GSM8k), the returned type and value per test input (MBPP); failures become 'ERROR: [reason]', e.g. 'ERROR: Time out'.
  3. Verify (§2.3, §3.4) — A small LM scores P(v=1 | x, program, result): T5 emits a yes/no token whose 'yes' probability is the verification score; RoBERTa-large uses a classification head. Per-dataset choice: T5-base (Spider), T5-large (WikiTQ, MBPP), RoBERTa-large (GSM8k). Trained with NLL normalized by candidate count (Eq.4, so many-candidate examples don't dominate), with per-epoch down-sampling for GPU memory; the gold program is appended as an extra positive where the dataset has one.
  4. Rerank with aggregation (§2.2) — Multiply generation and verification probabilities (Eq.3), sum over candidates with identical execution results, output a program from the argmax result; ties broken randomly.

Training-data statistics (Tab.7): the positive-label rate — also the accuracy of picking a sample at random — is 47.6–68.0% for Codex but only 2.2–9.2% for InCoder/CodeGen, which is why selection has more headroom for weak LLMs; deduplication keeps only ~30% of Codex’s SQL samples versus 90%+ elsewhere. Verifier-size ablation (Tab.9): spread across T5-base/large/3B and RoBERTa-large is at most 2.0 points per dataset. Prompting the code LLM itself as a few-shot verifier was tried and underperformed EP+ML (fn.6).

Main result

With code-davinci-002, LEVER beats the strongest execution heuristic on every benchmark — +4.6 (Spider dev) to +11.9 (GSM8k test) execution accuracy over EP+ML on the primary splits; the abstract quotes 4.6–10.9% (Tab.2–5) — and sets then-new SOTA on all four datasets, over finetuned task-specific models (RASAT on Spider) and prompting methods (Binder on WikiTQ, PoT-SC/DiVeRSe on GSM8k, Coder-Reviewer on MBPP) (Tab.2–5), holding under the stricter official WikiTQ evaluator (62.9 test vs Binder’s 61.9, Tab.10). Gains are larger for weaker generators: on Spider dev, LEVER lifts InCoder-6B from 41.2 (EP+ML) to 54.1 and CodeGen-16B from 37.7 to 51.0 — up to +30.0 over greedy on Spider and +15.0 on GSM8k (Tab.6).

Key findings

  • The execution result is the load-bearing verifier input (§4.2, Fig.2): removing it costs 6.6 (WikiTQ), 5.6 (MBPP), 3.0 (Spider), 1.2 (GSM8k) points with Codex and up to 8.7 with weaker LLMs (CodeGen GSM8k 22.1→13.4, Tab.6); datasets whose samples contain more execution errors benefit most.
  • Result aggregation helps Python but can hurt SQL (§4.2, Tab.6): removing it raises Spider dev for InCoder (54.1→54.7) and CodeGen (51.0→51.6) while lowering GSM8k (11.9→10.6, 22.1→18.3) — incorrect SQL often executes to trivial results (empty table, 0) that accumulate probability mass once merged.
  • Verification is cheap to train (Fig.2, Fig.3, Tab.8, §5.1): dropping gold programs costs at most 1.1 points (weakly-supervised setting); 250 training examples still improve base LLMs by 1.7–10.0 points; at 500 examples a T5-base verifier on InCoder/CodeGen beats a finetuned T5-3B generator by ~7 points; and verifiers partially transfer across LLMs — best when source/target positive-label rates are close, though transferring into Codex on GSM8k goes negative (−2.1 from InCoder).
  • Sampling budget matters at test time, not train time (Fig.4): cutting inference samples from 50 to 10 costs 1.8 (Spider) to 5.2 (WikiTQ) points, while varying verifier-training samples changes results by under 1 point.
  • Verifier and generator are complementary in calibration (Fig.5): the verifier is well calibrated in the low percentiles (spotting obviously wrong programs) but poorly calibrated among top-ranked candidates on 3 of 4 datasets, where the generator is better; their product is the best-calibrated score on all four — the empirical justification for mixing probabilities (Eq.3) rather than rejecting on the verifier alone.
  • Failure is dominated by the sampler, then by uninformative executions (Fig.6, Tab.6): the most common failure is that no correct program exists among the samples — the oracle ceiling (InCoder GSM8k oracle 48.0 vs LEVER 11.9) — and the second is a wrong program whose result has the same type and range as the correct one, where execution gives the verifier nothing to grip.

Implications

LEVER carried learned verification from NL math solutions (Cobbe et al. 2021; Shen et al. 2021; DiVeRSe) into executable programs, and marks the “learned adjudication over executions” pole against training-free execution consistency (MBR-Exec, Coder-Reviewer) and test-generation approaches (CodeT, AlphaCode); it is an ancestor of the outcome-verifier/reranker stage in today’s code and agent pipelines. The TDE-relevant reading: LEVER’s training labels are mechanical (match gold execution, pass all tests), but that mechanical grader exists only at training time — LEVER distills it into a soft judge that must generalize at inference. TDE inverts this: synthesize the decidable check at runtime, so verification stays mechanical and can act as a completion gate driving red–green iteration, rather than a one-shot argmax over samples. Whether modern LLM judges beat small finetuned verifiers — in 2023, few-shot self-verification by the code LLM lost to EP+ML (fn.6); verifier-gated abstention or repair loops instead of always emitting the argmax.

Limitations

  • Execution requires at least one input set and an execution context (databases, function arguments), which many applications don’t provide, and model-generated code is not always safe to execute — author-stated (§7), with no sandboxing discussion.
  • Evaluated with PASS@1 only; pass@k / n@k views for general programming are left open (§7).
  • Per-task, per-LLM verifier training on thousands of executed samples; cross-LLM transfer is only partial and can hurt (Tab.8).
  • Reranking is bounded by the sample set: oracle gaps are huge for weak LLMs (GSM8k oracle 48.0/61.4 vs LEVER 11.9/22.1, Tab.6).
  • Spider is reported dev-only, and MBPP model selection used a 90-example dev set with a 6.5-point dev→test drop (75.4→68.9).

Critiques and Questions

  1. Number bookkeeping is loose: the abstract’s “4.6% to 10.9%” understates the GSM8k-test delta over EP+ML (+11.9, Tab.4), and §4.1 attributes a “17.3%” greedy-gap to WikiTQ when 17.3 matches the GSM8k test gap (WikiTQ’s is 12.8 test / 15.0 dev). Likewise §B.2 says the best verifier base LM was selected, yet Tab.9 shows T5-3B ahead on Spider (83.1 vs the chosen T5-base’s 82.0). Cosmetic, but text and tables don’t fully reconcile.
  2. The motivating claim is that “test cases are hard to obtain”, yet every training label requires gold execution results or full test suites — the oracle is not removed, it is front-loaded into training; on genuinely new tasks at inference, the verifier only guesses.
  3. No abstention: LEVER always emits its top-ranked program even when the verifier scores every candidate near zero — the verification probability is never used as a gate on declaring the task done.
  4. What the verifier actually learned is probed only categorically (error/type/range buckets in Fig.6); whether it reads program semantics beyond surface-plus-result correlations is untested, and the “others” success category is explained only by hypothesis (§5.4).
Why does LEVER multiply the verifier's probability with the LLM's generation probability instead of ranking by the verifier alone?
Calibration analysis (Fig.5) shows the verifier is well calibrated in the low percentiles — it reliably spots obviously wrong programs, especially ones with execution errors — but poorly calibrated among top-ranked candidates on 3 of 4 datasets, where the generator is the better-calibrated scorer. Their product is the best-calibrated score on all four benchmarks; on GSM8k the joint probability is well calibrated even though both factors individually are poor.

Personal notes

For the TDE novelty defense, the crisp one-liners: (a) LEVER’s verification probability is a reranking feature, never a gate — the argmax ships regardless of how low every candidate scores; (b) the mechanical grader (gold results / test suites) exists only at training time and is distilled into a soft judge, whereas TDE keeps the mechanical check at runtime; (c) selection-time, single-shot — no repair or iteration conditioned on failed checks. Fig.6b’s failure mode (wrong result with same type/range as the right one) is the exact ambiguity a decidable acceptance suite dissolves.
