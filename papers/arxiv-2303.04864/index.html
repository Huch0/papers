Curated byChiyeong Heo

nl2spec pairs an LLM with a human-in-the-loop web tool to translate unstructured natural-language requirements into LTL, decomposing every translation into editable sub-translations so users repair ambiguity and errors locally instead of redrafting the whole formula — lifting accuracy on a 36-instance expert benchmark from 44.4% one-shot to 86.11% interactive.

For TDE this is the NL→spec compiler studied in isolation: it shares the move of compiling unstructured natural language into a decidable, machine-checkable artifact, its sub-translation editing is a concrete mechanism for pinning scope/precedence binding, and its ≥25% ambiguity rate among expert-written one-sentence requirements is quotable evidence that instruction→suite compilation needs an explicit disambiguation step. It differs on every runtime axis TDE cares about: the loop terminates on human approval rather than a mechanically evaluated red–green gate, its confidence scores are LLM self-consistency votes rather than environment-computed verdicts, and the output is an LTL property destined for model checking a system design — no agent, no actions, no conditions over world state.

Motivation

Verification tasks — model checking, synthesis, runtime verification — presuppose a formal specification, but writing formal specifications is an error-prone, time-consuming manual task reserved for experts, which limits the reach of verification itself (§1). Prior NL→temporal-logic work either handles only structured, grammar-constrained natural language (specification patterns, robotics datasets) or translates one-shot with a neural model (fine-tuned or GPT-3-based), and no previous tool detects or interactively resolves the inherent ambiguity of natural language — when a one-shot output is wrong, the user’s only recourse is redrafting the entire formalization by hand (§1–2).

Contribution (what’s new)

Decompose the NL→LTL translation into sub-translations — LLM-generated mappings from subformulas of the produced formalization back to the natural-language fragments they came from — and make those pairs the unit of human interaction: users add, edit, or delete them, and the edits feed back verbatim into the prompt’s “Given translations” slot to constrain the next generation (Alg.1, Fig.3). The form is forced by where ambiguity lives: operator precedence and semantic readings attach to sub-formula scope, which an end-to-end formula hides but a fragment-level mapping exposes — and fixing one fragment (e.g. adding parentheses) is far cheaper than redrafting. Secondary deltas: consensus confidence scores computed as votes over multiple sampled runs, with alternative sub-translations selectable in the UI; a model- and domain-agnostic open-source tool (prompts are swappable .txt files, with STL and smart-home prompts as proofs of concept); and a deliberately adversarial 36-instance expert benchmark.

Research questions

(1) Are initial LLM translations of unstructured natural language to LTL good enough to seed an efficient interactive workflow? (2) Does interactively refining sub-translations let users resolve ambiguity and fix erroneous formalizations more cheaply than redrafting? (3) Does sub-translation quality causally drive final-formalization quality?

Methodology

A flask frontend/backend around swappable LLMs (Codex code-davinci-002 and Bloom-176B in the study). Each loop: build the prompt from a specification-language header, two few-shot examples, the input sentence, and the current sub-translations; sample the model several times (3 runs, temperature 0.2 in the experiments); parse out an explanation, a sub-translation dictionary, and the final formula; show the highest-vote candidates with vote-share confidence; the user edits sub-translations and reruns until approving the formula (Alg.1). Benchmark: five experts wrote 36 deliberately challenging single-sentence requirements over atomic propositions a–e; a translation counts as correct only if it matches the expert’s intended meaning — alternative readings of ambiguous inputs are rejected (§4.1–4.2).

Method details
  1. Prompt anatomy (Fig.3) — Three parts: a specification-language header carrying minimal LTL domain knowledge with chain-of-thought phrasing (lines 1-4); two few-shot examples, each demonstrating input sentence, a Given-translations dictionary, a step-by-step explanation, an explanation dictionary of sub-translations, and the final formula, ended by the FINISH stop token; and the interactive part holding the user's sentence plus current sub-translations. The minimal prompt was frozen before the user study and contains no example with non-empty given translations.
  2. Interactive loop (Alg.1) — While the user has not approved the formula: compute the interactive prompt from sentence S, few-shot prompt F, and the sub-translation pairs; query model M under parameters P (temperature, number of runs); receive explanation, sub-translations, confidence scores, and final formula; the user adds, edits, deletes, or picks alternative sub-translations; rerun.
  3. Confidence and parsing — Confidence of each (sub-)translation is its vote share across the sampled runs; the highest-consensus candidate is displayed, alternatives sit in a drop-down. Output formulas are parsed with a standard LTL parser, so syntactic validity is checked mechanically - semantic correctness is not.
  4. Extendability (App.C, E) — Prompts are plain .txt files: swapping header and examples ports the tool to other spec languages (an STL prompt and a smart-home LTL prompt ship as proofs of concept). Variable conventions are set by seeding one sub-translation - giving 'process 0 terminates' as t_p0 makes the model adopt the naming scheme (s_p1) for the rest of the sentence.

Main result

On the 36-instance expert set, nl2spec+Codex translates 44.4% (16/36) correctly with no interaction — versus 2.7% for nl2ltl (Rasa→Declare patterns) and 5.5% for a T-5 fine-tuned on structured data — and reaches 86.11% (31/36) after interactive sub-translation repair, at 1.4 translation loops on average (Tab.1, p.9).

Key findings

  • In-distribution few-shot examples help only slightly: 58.3% vs 44.4% (Tab.1, §4.2) — and 4 of the eval instances sit verbatim in that prompt — so the interactive mechanism, not prompt engineering, carries the method; the authors read this as making ambiguity detection and cheap debugging the valuable contribution.
  • Sub-translations transfer across models with no human involved: of 11 instances Codex solved but Bloom failed, Bloom solves 4 (36.4%) when given Codex’s sub-translations as input (§4.2, p.9) — direct evidence that improving sub-translation quality causally improves the final formalization.
  • At least 9/36 (25%) of expert-written single-sentence requirements are ambiguous, in two classes (§4.2, p.10): linguistic ambiguity (operator precedence: “a holds until b holds or always a holds” → tool (a U (b | G(a))) vs intended (a U b) | G a) and semantic ambiguity (“b must hold in the next two steps” → tool G((a -> X(X(b)))) vs intended G (a -> (b | X b))); both kinds were fixed by editing a single sub-translation.
  • Of 20 initial failures, 15 were repaired within at most 3 loops (1.86 loops on average); the remaining 5 had to be translated by hand (§4.2, p.10) — the hand-translated residue uses advanced operators or hides temporal meaning in phrasing (e.g. “once a happened, b won’t happen again” → G (a -> X G ! b); “a releases b”) (App.D).
  • The open Bloom-176B backend manages only 13.8% initial accuracy vs Codex’s 44.4% (Tab.1, p.9): the framework is model-agnostic, but its floor is set by the backend’s pretraining exposure to logic and code.

Implications

The durable pattern is NL→formal-artifact compilation with an inspectable, editable intermediate decomposition — a repair interface at exactly the granularity where ambiguity lives. Within its lineage it adds the missing disambiguation loop to one-shot neural translation (fine-tuned LMs (Hahn et al. 2022), DeepSTL, nl2ltl’s GPT-3/Rasa→Declare pipeline, Lang2LTL for robot commands), and the .txt-prompt architecture ports it across spec languages. Threads worth chasing: replacing the human approval gate with mechanical adjudication — e.g. equivalence or trace-distinguishing checks between candidate readings, which LTL’s decidability permits but the paper never uses; whether consensus-vote confidence actually flags the ambiguous 25% (calibration is unreported); the robotics NL→LTL branch (Lang2LTL, grounded semantic parsers) as the agent-facing continuation of this line.

Limitations

  • The interactive headline is author-in-the-loop, not user-in-the-loop: the expert study only produced the dataset; the 86.11% repair experiment was performed by the authors, who could compare candidates against the known intended formula — a feasibility ceiling, not a usability measurement (§4.1–4.2).
  • 36 single-sentence instances over five atomic propositions from five experts; no variance, seeds, or significance reporting; single run configuration (3 samples, temperature 0.2).
  • How “matches the intended meaning” was adjudicated is not reported — no mention of automated equivalence checking — and the in-distribution prompt leaks 4 eval instances into the few-shot examples.
  • Author-stated: reliance on inference-time compute, and initial-translation quality is hostage to how much logic/code/math the backend saw in pretraining (§5).
  • Confidence is LLM self-consistency over 3 samples: uncalibrated, and a low score conflates model uncertainty with genuine input ambiguity.

Critiques and Questions

  1. The central workflow claim — that verifying and debugging sub-translations is significantly easier than redrafting the formula — is asserted, never measured: no timing, error-rate, or preference comparison against a redrafting baseline, and no non-author users ever ran the loop.
  2. Termination is “while user not approves”: with no mechanical check, a user who mis-approves ships a wrong spec and the tool cannot notice. A model-based probe (e.g. sampling traces that distinguish the candidate readings) would de-circularize exactly the adjudication step that remains human here.
  3. Does the model ever override a wrong user-provided sub-translation, or does garbage-in propagate to the final formula? The feedback channel is only ever tested with helpful edits.
  4. With 3 samples at temperature 0.2, the vote-based confidence can take almost no distinct values — how much signal does it carry in practice?

Personal notes

For the TDE related-work section, cite as category-D evidence for three points: (1) NL→decidable-spec compilation is LLM-feasible on genuinely unstructured input, but one-shot accuracy stalls near 44% even for expert single sentences; (2) ≥25% of expert-written one-sentence requirements were ambiguous, so instruction→suite compilation needs an explicit disambiguation mechanism — nl2spec’s is human-elective editing of an inspectable decomposition, a pattern TDE could reuse for surfacing compiled-suite provenance; (3) the loop closes on human approval plus LLM-vote confidence — precisely the adjudication TDE mechanizes with environment-evaluated suites. Sharpest contrast sentence: nl2spec verifies the spec against the human; TDE verifies the world against the spec.
