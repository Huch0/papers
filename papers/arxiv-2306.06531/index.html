Curated byChiyeong Heo

Instead of letting an LLM plan, AutoTAMP has it few-shot translate a natural-language task (with temporal and geometric constraints) into STL that a formal joint task-and-motion planner solves — wrapped in two corrective re-prompting loops: a mechanical syntax check, and a novel “autoregressive” semantic check in which the LLM itself judges whether the planner’s output plan matches the instruction.

Category-D relative for TDE: it shares the compile-NL-to-a-formal-spec move, an external solver, and a red–green re-prompting loop — but its acceptance object is pre-execution plan validity, not a post-execution acceptance suite over the final world state, and only the syntax gate is mechanical: the semantic gate (“does the plan match the instruction?”) is adjudicated by the LLM itself — exactly the circular adjudication TDE removes. Mechanical task-success checkers exist in this paper only as offline evaluation harness, and there is no per-action pre/postcondition gating during execution — a clean foil for the novelty defense.

Motivation

When instructions carry hard temporal and geometric constraints, the task plan and motion plan must be optimized jointly — for “reach all locations via the shortest path”, the visit order depends on environment geometry — so factoring the problem into LLM-planned sub-goals handed to a motion planner is untenable (§I). Prior LLM approaches either use LLMs as direct task planners, which struggle with temporally-dependent multi-step actions, action-sequence optimization, and constraints on task execution, or emit trajectories end-to-end, which fails outright from poor spatial/numerical reasoning (Fig.2). NL-to-formal-spec translation existed, but prior targets (LTL, PDDL goals/problems) miss continuous real-time constraints, and open-loop translation yields both syntax errors and semantic misalignment — and while a syntax verifier can drive corrective re-prompting, no external verifier exists for semantic misalignment (§I).

Contribution (what’s new)

Reposition the LLM at the specification boundary — translator and checker, not planner: few-shot translate NL to STL and let a formal multi-agent STL planner jointly solve task sequencing and motion, getting STL’s expressivity for real-time constraints plus solver guarantees the LLM lacks. The second delta is an autoregressive semantic re-prompting loop: the planner’s output state sequence is fed back to the LLM alongside the original instruction, and the LLM decides whether the plan aligns with the instruction’s semantics, rewriting the STL if not — the first automated correction signal for the error class that has no external verifier (syntax reuses the verifier-in-the-loop technique of Skreta et al.). The design must take this form because feasibility must live in the solver (LLM planners score 0% under hard geometric constraints), while translation error dominates the residual — so each error class gets its own closed loop.

Research questions

  1. Does LLM-as-translator + formal planner beat LLMs-as-planners on TAMP with hard geometric/temporal constraints? 2. How much do syntactic and semantic correction loops each contribute? 3. Is few-shot translation with a pre-trained LLM competitive with a fine-tuned NL-to-temporal-logic model (NL2TL)?

Methodology

Input is a text description of the environment (named polygonal regions), five in-context examples, and the NL instruction; output is a trajectory as timed waypoints (x_i, y_i, t_i) (linear interpolation, max-velocity and time-limit constraints). The LLM translates the instruction to STL over enter(room) / not_enter(room) primitives; a rules-based checker repairs syntax via re-prompting; the STL planner of Sun et al. 2022 (MILP-based, multi-agent) optimizes a trajectory maximizing formula validity; then the semantic loop re-prompts the LLM with instruction + STL + the planner’s state sequence to catch misalignment. Baselines share the same STL planner for motion, isolating where the LLM sits in the stack.

Method and experiment details
  1. Translate NL → STL — Few-shot (5 examples). STL chosen over LTL/PDDL for continuous real-time constraints and joint task-motion planning. Best of six candidate prompt sets used; prompt variance reported as insignificant relative to method gaps (§IV).
  2. Syntax loop (mechanical) — A simple rules-based STL syntax checker feeds specific errors back for corrected STL; repeat until clean, up to 5 iterations (adopted from Skreta et al. [20]).
  3. Plan (formal solver) — Sun et al. 2022 multi-agent STL planner: piece-wise linear timed-waypoint paths, recursively encodes the STL constraints, optimizes trajectory validity and time efficiency under max-velocity dynamics. Assumes all object/room locations and shapes are known.
  4. Semantic loop (LLM-judged) — The planner's state sequence, e.g. [[in(road), 0], [in(red_kitchen), 0.5], ...], is given to the LLM with the original instruction; the LLM judges alignment and, if misaligned, edits the STL, re-entering both loops. Terminates on no detected error or unchanged STL, up to 3 iterations.

Scenarios (§IV): HouseWorld1 (single-agent, no hard time limit), HouseWorld2 (same, hard time limit set from the correct trajectory at 0.8 max velocity), Chip’s Challenge (single-agent, key–door geometric/logical dependencies), and multi-agent Overcooked, Rover, Wall (all hard time + geometric constraints). Instructions: 10 hand-written HouseWorld instructions each GPT-4-paraphrased into 9 variants (100 instructions × 2 start/end pairs = 200 cases); each rule-based scenario paraphrased into 20 human-checked variants × 3 environment instances × 5 start/end pairs (300 cases each) — 1400 total, all released with generated STL and trajectories. Baselines: LLM end-to-end motion planning (≤5 violation-feedback re-prompts), Naive Task Planning (Huang et al.), SayCan (K=5), Task Planning + Feedback (Text2Motion-like); sub-tasks are converted to STL and executed by the same planner. Success is judged by hard-coded trajectory checkers; runs over 90 minutes count as failure. Full grid: ~2 weeks on four 16-core CPUs, ~1500 USD of API calls. SayCan and Task Planning + Feedback are omitted in multi-agent scenarios (per-agent completion times make the feedback timing ill-defined).

Main result

Wherever hard geometric or temporal constraints exist, AutoTAMP dominates LLMs-as-planners: on Chip’s Challenge every LLM-as-planner baseline scores 0.0% while AutoTAMP reaches 87.7% (GPT-4; 74.3% with GPT-3) (Tab.I, p.5), and on multi-agent Overcooked/Wall AutoTAMP (GPT-4) hits 100.0% vs 17.0%/47.0% for naive task planning (Tab.II, p.5). The honest flip side: on unconstrained HouseWorld1, LLM task planners win (92.0% vs AutoTAMP’s 82.5%) (Tab.I, p.5) — with direct paths always feasible, AutoTAMP’s only failure source is translation error.

Key findings

  • Constraint type flips the ranking (Tab.I, p.5): adding only a hard time limit (HouseWorld1 → HouseWorld2) collapses GPT-4 task planners from 90–92% to 45–49%, while AutoTAMP barely moves (82.5% → 82.0%).
  • Both correction loops matter, everywhere (Tab.I–II, p.5): syntax correction then semantic correction improve every scenario, e.g. GPT-4 HouseWorld1 43.5% → 59.5% → 82.5%; GPT-3 Overcooked 25.0% → 70.0% → 89.0%.
  • Few-shot translation ≈ fine-tuned translation (Tab.I–II, §V): swapping GPT-4 translation for NL2TL (T5-large fine-tuned on 30K instruction–logic pairs; GPT-4 still does correction) changes results marginally (82.0→83.5 HouseWorld2, 79.0→79.7 Rover, ties at 100.0) — in-context learning suffices without training data.
  • LLMs cannot emit trajectories (Fig.2, Tab.I–II): end-to-end motion planning stays at 0–9.5% (GPT-4) even with five violation-feedback re-prompts.
  • Failure-mode split (§V): task-planner failures come from execution-time violations, long-horizon sequencing (collecting keys for future doors), and multi-agent collisions; translator-pipeline failures are residual mistranslations that survive both loops.
  • Transfer demos (§V): 3D drone and tabletop-manipulation simulations (semantic check disabled; a simple discrete planner added for mode transitions) and physical Robotarium runs with a control-barrier-function tracking controller and obstacle padding.

Implications

The load-bearing lesson for agent design: put the LLM at the spec boundary and keep solving mechanical — and close a loop on each error class you can detect. It extends the verifier-driven re-prompting of Skreta et al. [20] from syntax to semantics (at the price of an LLM judge), and positions itself against LLM-planner lines (Huang et al., SayCan, Inner Monologue, Text2Motion) and NL-to-spec translation lines (LLM+P, Lang2LTL, NL2TL, DeepSTL). Whether the semantic gate can be de-circularized — e.g. replaced by an executable acceptance check over the final state, as TDE proposes, rather than an LLM reading a state sequence; whether the “no change in STL” stopping rule locks in confident mistranslations; runtime cost reduction for the re-prompt × MILP-planner loop.

Limitations

  • The semantic checker is the LLM itself, and its judging accuracy is never measured — no precision/recall against the hard-coded ground-truth checkers, though the 1400 released cases would support exactly that analysis. Residual failures are still mistranslations.
  • High planning cost (author-stated): multiple LLM + MILP iterations; a 90-minute-per-case timeout counted as failure; the full evaluation took ~2 weeks on four 16-core CPUs and ~1500 USD in API calls. Per-case runtime distribution: Not reported.
  • All verification is pre-execution: the loops close over the planned trajectory in a fully known, static 2D world (enter/not_enter primitives only); nothing re-checks the plan against execution observations — physical demos rely on trajectory tracking plus obstacle padding.
  • Best-of-six prompt selection (author-stated); authors argue method-level trends persist across prompts.
  • The STL planner does not handle manipulation (author-stated); multi-agent comparisons omit SayCan/feedback baselines; single evaluation pass, no variance or significance reported.

Critiques and Questions

  1. The semantic loop re-introduces the circularity the syntax loop escapes: the same model that mistranslated adjudicates alignment, reading a symbolic state sequence it may misinterpret the same way. How often does it green-light a wrong plan? The data to answer existed; the paper doesn’t report it.
  2. Translation is the persistent bottleneck (17.5–18% residual failure on HouseWorld even for GPT-4 with both loops) — is STL itself an LLM-hostile target language, and would a constrained decoder or grammar-guided generation beat re-prompting?
  3. Test instructions were largely GPT-4 paraphrases of a few seed instructions, and GPT-4 is also the evaluated translator — a possible favorable-distribution bias the paper does not discuss.
  4. The 90-minute timeout conflates planner blow-ups with wrong plans; the split between timeout failures and semantic failures is Not reported.
What exactly does AutoTAMP's semantic check compare, and who adjudicates it?
It compares the original NL instruction against the STL planner's output state sequence (timed region-entry events), with the generated STL as context — and the adjudicator is the LLM itself, re-prompted to judge alignment and rewrite the STL if misaligned. Only the syntax check is mechanical (rules-based verifier); ground-truth task success is checked by hard-coded evaluators used only offline for the experiments.

Personal notes

For the TDE novelty defense, the precise characterization: AutoTAMP mechanizes syntax (rules-based verifier) and feasibility (MILP planner), but delegates semantic acceptance to an LLM self-check over the planned state sequence — pre-execution, no runtime observation ever feeds verification, and the genuinely mechanical task-success checkers are quarantined in the evaluation harness. TDE’s delta in one line: make the semantic gate itself executable (acceptance suite over the final world state, environment-evaluated) and move gating into execution (per-action pre/postconditions), rather than asking the translator to grade its own translation. The ablation (43.5→59.5→82.5) is useful ammunition that closing loops on formal artifacts is where the gains are.
