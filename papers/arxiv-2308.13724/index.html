Curated byChiyeong Heo

ISR-LLM wraps an LLM planner in a pre-execution validate-and-revise loop — an LLM translator turns the natural-language task into PDDL, an LLM planner drafts an action sequence, and a validator (LLM self-check or a mechanical external checker) feeds back the first detected error until the plan passes — with the mechanical external validator, not LLM self-validation, delivering most of the gain.

Category-E related work for TDE: it shares a red–green-shaped loop (revise until the validator passes), per-action precondition/effect checking, and pre-execution mechanical validation in its best variant — and its headline ablation (the external validator beats the LLM self-validator in all 12 conditions, Tab.1) is direct empirical support for TDE’s de-circularization premise that adjudication must not be an LLM judge. It differs fundamentally in what is verified: plan coherence under symbolic simulation of an LLM-translated PDDL model, never an acceptance suite evaluated by the real environment over the actual final world state, and no action is gated at run time. Also a clean evaluation-methodology datapoint for verifier design in agent harnesses.

Motivation

Plans generated by LLMs often lack feasibility and correctness: Valmeekam et al. (2022) found discouraging performance even on seemingly uncomplicated Blocksworld tasks, and the failure sharpens in long-horizon settings where interdependent actions compound errors (§1). Existing remedies each give something up: prompting with raw PDDL (Silver et al. 2022, 2023) improves accuracy but sacrifices natural-language generality and demands expert-written PDDL; LLM+P (Liu et al. 2023) demotes the LLM to a translator and requires an external classical solver; corrective re-prompting (Raman et al. 2022) repairs plans only after execution errors surface (§2.2). Classical symbolic planners, meanwhile, need hand-specified domains and cannot absorb preferences stated in natural language (§1).

Contribution (what’s new)

An iterative pre-execution refinement loop around an LLM planner: a validator steps through the drafted plan, stops at the first infeasible action, and returns exactly that error as feedback for replanning, repeating until no error is found or an iteration budget is exhausted (§4.3). Refinement must be pre-execution because the target is robotics, where executing a bad plan is precisely the failure to avoid — the delta versus Raman et al.’s post-execution re-prompting. Second, the NL-to-PDDL translation exists to make validation possible: a formal representation both enables mechanical validators (VAL, PDDL.jl) and gives the LLM self-validator a state-machine-like grasp of system state instead of linguistic cues (§4.1). Third, a controlled head-to-head of LLM self-validator versus external mechanical validator as the feedback source.

Research questions

(1) Does iterative self-refinement raise LLM success on long-horizon task planning? (2) Is an external, tool-based validator a better feedback source than the LLM validating itself? (3) Does the PDDL translation itself help, and which component benefits? (4) How do object count and the underlying model (GPT-3.5 vs GPT-4) modulate the gains?

Methodology

Three sequential stages (Fig.1): an LLM translator converts the instruction (assumed to state initial state and goal) into PDDL domain and problem files via few-shot in-context learning; an LLM planner generates an action sequence from those files with few-shot examples plus CoT; a validator then checks the plan and the planner revises, looping until the validator finds no error or a predefined maximum number of iterations (value not reported) is reached. Both validators simulate the plan step by step — check each action’s preconditions, apply its effects, halt at the first violation, and after a clean pass compare the simulated final state against the goal (Fig.2; App.A.3). The self-validator does this in-context as text; the external validator does it in code — the authors implement custom per-domain validators rather than using VAL, “to mitigate the influence of existing PDDL validators” (§5.1).

Method and experiment details
  1. Preprocessing (§4.1) — Translator prompt = few-shot examples (3 per domain, App.A.1) + the natural-language question → domain file (predicates; actions with preconditions/effects) and problem file (objects, init, goal). Domain knowledge is assumed available in advance and baked into the few-shot examples, as in LLM+P.
  2. Planning (§4.2) — Planner prompt = few-shot examples (3–5 per domain, App.A.2) with CoT decompositions (e.g. Blocksworld plans built bottom-to-top, Cooking iterated ingredient-by-ingredient) + the translated PDDL files → action sequence.
  3. Refinement loop (§4.3) — Validator output is appended to the planner's prompt as feedback history; only the first detected error is reported per iteration, since actions after it may be fundamentally invalidated. Loop ends when no error is found or the iteration cap is hit.
  4. Setup (§5.1) — Domains: Cooking (n pots, 6 ingredients, each pickable exactly once, random 2–4-ingredient recipes), Blocksworld (restack n blocks into a prescribed order), Ball Moving (n balls across 4 rooms, robot carries at most one). n = 3 and n = 4; 30 random instances per task; methods LLM-direct / ISR-LLM-self / ISR-LLM-external; models GPT-3.5 and GPT-4 (versions, decoding settings not reported). LLM-direct also uses the translator, for fairness.
  5. Grounding demo (§5.4) — A 4-block Blocksworld plan is executed by a pick-and-place controller in NVIDIA Isaac Sim, assuming known block poses — a demonstration that PDDL-structured actions simplify motion grounding, explicitly beyond scope.

Main result

With GPT-3.5, the external validator lifts success by roughly 40–50 percentage points over LLM-direct (Blocksworld n=3: 20% to 70%; Cooking n=3: 47% to 100%), while the LLM self-validator adds only about 15 points (Tab.1, p.8; §5.2); the one exception is Cooking n=4 (+23, 40% to 63%), which the authors attribute to the excessive number of required actions. With GPT-4, direct planning already saturates Cooking and Ball Moving (90% or higher), but on logic-heavy Blocksworld ISR-LLM-external still adds more than 40 points (n=3: 43% to 97%; n=4: 40% to 80%) (Tab.1, p.8).

Key findings

  • The external validator matches or beats the LLM self-validator in every one of the 12 conditions (Tab.1, p.8): mechanical checking dominates LLM self-judgment as a refinement signal, at every model size and horizon.
  • Feedback precision is the stated mechanism (§6, p.10): the external validator identifies the exact action where the error resides, while the self-validator usually returns only an overarching estimate that the whole plan is wrong — and the gap widens as the horizon extends or logic gets harder.
  • PDDL translation mainly helps the self-validator (Tab.2, p.9): on Blocksworld n=3/GPT-3.5, removing the translator drops ISR-LLM-self from 36% to 16% but ISR-LLM-external only from 70% to 63% — the formal representation is what lets the LLM track state, while the coded validator is accurate either way. (Minor internal inconsistency: Table 1 lists this self-validator cell as 37%.)
  • More objects means lower success for every method (§5.2, p.8): GPT-3.5 drops from n=3 to n=4 by 7/10/16 points (LLM-direct), 14/20/23 (self), 37/17/13 (external) across Cooking/Blocksworld/Ball Moving — error correction gets harder as plans lengthen; the effect largely vanishes with GPT-4.
  • Domain character determines difficulty (§6, p.10): instruction-following (Cooking) and repeated-pattern (Ball Moving) domains are near-solved by GPT-4 even without refinement, while Blocksworld’s stacking logic stays hard — read by the authors as LLMs suiting instruction/pattern following better than logical reasoning.

Implications

The transferable result for agent design: in a generate–check–revise loop, the checker is the bottleneck — an LLM self-check buys a little, a mechanical checker with pinpoint feedback buys a lot. That positions ISR-LLM inside the Self-Refine / self-improvement line (Madaan et al. 2023; Huang et al. 2022b) while empirically undercutting its self-sufficiency ethos for planning; it complements LLM+P (LLM as translator, classical solver plans) and Silver et al.’s PDDL-direct prompting, and is the pre-execution counterpart of Raman et al. 2022’s corrective re-prompting from execution errors. Moving the checked artifact from a predicted plan under a model to the actual post-execution world state — environment-evaluated acceptance, the TDE thread. Auditing translator fidelity: every downstream check trusts the LLM-written PDDL spec.

Limitations

  • Author-stated: even with ISR-LLM, success rates generally fail to exceed traditional search-based planners, and LLM randomness precludes correctness or constraint-satisfaction guarantees, making the approach inappropriate for safety-critical tasks (§6).
  • Toy scale and single runs: three synthetic domains, 3–4 objects, 30 instances per task, no variance/seeds/significance; GPT versions, decoding settings, the iteration cap, and per-run refinement counts are all not reported.
  • Refinement cost is invisible: no token, latency, or iteration accounting, so the comparison with LLM-direct is not compute-matched.
  • The success-grading procedure is not described — if the same custom validator both supplies feedback and grades final success, ISR-LLM-external is optimized against its own grader. Unclear from the paper.
  • Spec circularity is unexamined: the self-validator reads initial state and goal from the LLM-translated problem file (Fig.2), so a mistranslation corrupts the check silently; translator error rates are not reported.

Critiques and Questions

  1. The headline claim — external beats self-validation — is well supported in these domains, but the “external validator” is hand-built per domain with ground-truth semantics; the off-the-shelf validators (VAL, PDDL.jl) whose existence justifies the PDDL translation step are never actually run.
  2. “Markedly higher success rates … compared to state-of-the-art LLM-based planners” is measured only against the authors’ own re-implementation of a direct-prompting baseline; there is no head-to-head with LLM+P, which on these fully-formalizable domains would presumably plan near-perfectly via a sound solver — a comparison the discussion implicitly concedes by admitting classical planners still win.
  3. Because validation is pre-execution simulation, correctness is relative to the model, not the world: any gap between the PDDL model and the real environment — or a mistranslated goal — passes undetected. The Isaac Sim demo assumes known block poses and does not close this loop.
  4. The marginal value of iteration is unmeasured: only end-of-loop success is reported, so one cannot tell whether refinement converges in one repair, oscillates, or exhausts its (unreported) budget.
Why does the external validator produce much larger gains than the LLM self-validator, according to the paper?
Feedback precision: the external validator simulates the plan and pinpoints the exact first infeasible action, so each refinement iteration targets a concrete error, while the LLM self-validator usually returns only a holistic judgment that the plan is wrong. The advantage grows with longer horizons and logic-heavy domains like Blocksworld (§6, Tab.1).

Personal notes

For the TDE novelty defense, the load-bearing quote is §6: the external validator “identifies the exact action in which an error resides” while the self-validator gives “an overarching estimation” — Tab.1 then shows mechanical checks beating the LLM judge in all 12 cells. Cite this as pre-execution evidence for de-circularization. Sharpest contrasts to draw: (a) ISR-LLM’s green signal is symbolic simulation of a predicted plan, never the realized world state; (b) the spec being checked against is itself LLM-authored (translator) and its fidelity is unaudited; (c) no runtime gating of actions; (d) even the final success grader is undescribed.
