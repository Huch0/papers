Curated byChiyeong Heo

Instead of asking an LLM to produce a plan, this framework has the LLM compile a natural-language multi-constraint query into a Z3 SMT program (query → natural-language steps → Python code) and lets the sound-and-complete solver do all the deciding — lifting TravelPlanner’s final pass rate from at most 10% (o1-preview) to 93.9%, with solver unsat cores driving an interactive repair loop for infeasible queries.

Category-E related work for TDE: it shares the core move of compiling natural language into a formal artifact whose verdict is computed mechanically — Z3 decides satisfiability, never an LLM judge — and its unsat-core → revise → re-solve loop is a planning-domain analogue of red–green iteration. It differs on the object and timing of verification: it certifies a plan against a static database before anything executes — no environment, no state-changing actions, hence no acceptance suite over final world state and no Hoare-style pre/postcondition gating of actions — and its loop repairs the user’s constraints (spec relaxation, with the user in the loop) rather than the agent’s behavior against a fixed suite. Its sharpest lesson for TDE: the NL→SMT compilation itself is unverified LLM output, and the gap between delivered and passing plans shows mechanical adjudication is only as sound as the compiled spec.

Motivation

LLMs cannot solve multi-constraint combinatorial planning by direct generation — token-probability decoding does not perform rigorous joint constraint satisfaction: on TravelPlanner, GPT-4 passes 0.6% and even o1-preview only 10.0% with all information pre-collected; self-verification and self-critique do not fix it, and the best prior tool-use framework, LLM-Modulo, reaches 20% (GPT-4-Turbo) and 65% (o1-preview) (§1). Conversely, algorithm-based solvers are sound and complete but unusable at the interface: they cannot parse free-form natural language, have steep learning curves, and when a query is infeasible the user must hand-modify inputs and re-query repeatedly (§1-2).

Contribution (what’s new)

A division of labor in which the LLM never plans: it compiles the query into an SMT constraint program — natural-language encoding steps, then Python/Z3 code that also calls database APIs — and the solver does all constraint satisfaction. The form is forced by the complementary failure modes: rigor must move out of the LLM into the solver, and NL parsing must move out of the solver into the LLM. Two further deltas: named assertions (assert_and_track) let Z3’s get_unsat_core localize exactly which constraints are infeasible, turning UNSAT from a dead end into a diagnosable state that seeds a ReAct-style, optionally human-in-the-loop repair dialogue; and the pipeline is taught with only three in-context example queries plus per-constraint code snippets, which is what makes zero-shot transfer to unseen constraints and domains plausible.

Research questions

  1. Can an LLM+SMT compile-and-solve pipeline reach near-solver reliability on realistic multi-constraint natural-language planning, across different LLMs? 2. Does the learned formalization pattern generalize zero-shot to unseen constraint types and fundamentally different domains, and survive prompt paraphrase? 3. When queries are unsatisfiable, can solver unsat cores plus LLM analysis repair them interactively under diverse user preferences?

Methodology

Four stages (Fig.1), LLM at temperature 0. Query-Step generation translates the query into natural-language encoding steps organized in nine constraint sections (destination cities, departure dates, transportation, flight, driving, restaurant, attraction, accommodation, budget). Step-Code generation converts each step into Python that calls information APIs (CitySearch, FlightSearch, AccommodationSearch, …) and asserts Z3 constraints. Executing the code runs the solver (30-minute cap); the found model is formatted into the day-by-day plan. If Z3 proves UNSAT, the framework extracts the unsat core and enters interactive repair: the LLM alternates info-collection actions, analysis, and one concrete suggestion (raise the budget, change a destination city, drop the non-stop rule, …); the user may agree, refuse, or state preferences; a code-modification prompt patches the constraint program and the solver re-runs — up to 10 iterations (20 in Ours-20).

Method details
  1. Query-Step generation (§3.3.1) — Three human-crafted examples map NL queries to step sequences; steps are sectioned per constraint subject so the LLM learns generic per-section patterns rather than memorizing whole programs. An optional NL-to-JSON pre-step first summarizes the query into fixed fields (origin, dest, days, budget, local constraints); it is excluded when comparing against NL-input baselines for fairness.
  2. Step-Code generation (§3.3.2) — Per-constraint example pairs (step comment, human-written code) teach API and solver usage without separate documentation, following Code as Policies. Generated code enumerates destination-city combinations in outer Python loops and instantiates a fresh Optimize() solver per combination — part of the search is enumeration outside the SMT encoding. Optimize() also supplies objectives (maximize score, minimize time or distance) used in the new domains.
  3. Solve (§3.3.3) — Z3 decides satisfiability of the encoded constraints; SAT yields a formally checked plan, UNSAT yields named cores. A simple heuristic prioritizes cities with available transportation from the origin to cut runtime.
  4. Interactive plan repair (§3.4) — ReAct-style loop with dataset-specific action menus (FlightCheck, FlightSearch, AirlineSearch, AttractionSearch, CategorySearch, TypeSearch, ...). The LLM must ground each suggestion in collected information, keep changes minimal, and may only modify permitted fields. User feedback can be yes, no, or free-form preference; accepted modifications go to a code-update prompt and the solver re-verifies.

Main result

On TravelPlanner, Ours (Claude-3) passes 93.3% of 180 validation queries and 93.9% of 1000 test queries — versus 0.6% (TwoStage GPT-4), 4.4% (Direct GPT-4), 10.0% (Direct o1-preview), and 0% (Greedy Search) (Tab.1, p.7). Adding the JSON pre-step lifts GPT-4 to 98.9% validation and 97.0% test (average +9.4 points across the three LLMs on validation) (Tab.8, p.19).

Key findings

  • The framework is portable across LLMs, but not model-free (Tab.1; App.G.1.3-G.1.4): Claude-3 and GPT-4 tie at 93.3% validation, while Mistral-Large drops 26.6/26.1 points (66.7/67.8) — largely code-generation and step-generalization errors (its failure to generalize the unseen “no shared room” room type alone accounts for 7.8 of its 15.0% failed deliveries). Still, 92.3%/97.0% of the plans Mistral does deliver are correct.
  • Zero-shot transfer to four new combinatorial domains needs only a few description lines in the prompt (Tab.2, p.7; Fig.3): optimal rates of 92 (Block Picking), 92 (Task Allocation), 100 (TSP), 72 (Warehouse), average 89.0%, while TwoStage (GPT-4o) never exceeds 4% optimal; residual failures are silent encoding slips — a missing all-distinct assertion, misusing the provided Max() helper, station-ID vs index confusion (App.F.3).
  • Ablations show the solver is the load-bearing component of repair (Tab.3-4, p.7): removing it collapses average repair success from 78.6/85.0 to 25.2/25.0 (−53.4/−60.0 points); passing unsat reasons to the LLM is worth +14.9/+5.0; free-form user feedback vs binary agree/disagree is worth +7.8/+14.1.
  • Repairs concentrate early (App.E, Fig.5): 63.7%/65.0% of repairable queries are fixed within 3 iterations, 78.6%/85.0% within 10, 81.6%/91.7% within 20.
  • Performance is not a prompt-engineering artifact (§5.2.1): with the entire prompt set (examples included) paraphrased by GPT-4o per query, validation final pass drops only to 86.7%.
  • Latency is dominated by the LLM, not the solver (App.B, Tab.6): 245.66 s per query total, of which Step-Code generation takes 166.66 s and Z3 only 38.39 s; just 1.3% of 1180 queries hit the 30-minute solver cap.

Implications

The strongest TravelPlanner evidence for the neuro-symbolic split “LLM formalizes, solver decides”: a mechanical adjudicator outperforms LLM self-critique (Reflexion, Self-Refine) and LLM-critic scaffolds (LLM-Modulo (Kambhampati et al. 2024; Gundawar et al. 2024)) by 29-93 points on the same benchmark, extending the LLM-to-formal-planner line (LLM+P; the same group’s AutoTAMP; Code as Policies for the code-prompting style). Verifying the compiled spec itself — the one remaining unverified LLM step — e.g. property-testing or round-tripping the generated constraint program. Whether unsat-core-guided repair transfers from relaxing user constraints to repairing agent behavior in stateful environments (the TDE setting). The sketched MILP back-end swap for runtime on linear problems.

Limitations

  • Task-specific offline prompt engineering: the nine-section step examples and per-constraint code demonstrations are hand-crafted (author-stated, §7); generalization amortizes this cost but does not remove it.
  • Static, closed-world database; nothing executes: feasibility is checked against sandbox tables, there are no environment dynamics, and the framework cannot detect unsafe or incorrect database information (author-stated “risky data”).
  • The completeness guarantee is conditional: “guaranteed to generate a plan if it exists” holds only for the constraints as the LLM encoded them, within the 30-minute cap; delivery below 100% and delivered-but-failing plans (delivery 96.1% vs final 93.3%, Claude-3 validation) show the compilation link is fallible and itself unverified.
  • Solver runtime scales poorly with problem size (author-stated): bigger databases or nearly-infeasible queries may require heuristics or different solvers.
  • Evaluation breadth: single-run point estimates with no variance; repair is tested only against scripted mimic users; the unsatisfiable sets are small (39 + 12 queries) and UnsatChristmas was authored by the same team.

Critiques and Questions

  1. The “formally verified plan” framing overstates end-to-end soundness: Z3 verifies satisfiability of the encoded constraints, and nothing verifies the encoding against user intent. On TravelPlanner the benchmark’s external evaluator catches mis-encodings; deployed, there is no such checker, so silent mis-compilations would ship as “verified” plans.
  2. Repair success partly measures persuasion: the loop relaxes the user’s constraints until SAT, and the metric counts solving the modified problem. Scripted mimic users cannot establish that real users would accept those relaxations — and the budget-hard user, arguably the most realistic refusal pattern, is the worst column (59.0-61.5% on UnsatChristmas).
  3. The generalization instances are small (25 scenarios per domain; a 10-city TSP), so “100% optimal” there does not establish scaling — and App.F.3’s failure analysis shows the silent-encoding-slip class grows exactly as encoding complexity grows (Warehouse: 4/25 undelivered, 3/21 non-optimal).
  4. No hand-engineered skyline (fixed parser + solver) is compared, so the LLM front-end’s contribution is not isolated from the solver back-end’s; the LLM-Modulo figures are cited from other papers, not reproduced under identical conditions.
The paper says the framework is 'guaranteed to generate a plan if it exists.' What conditions this guarantee, and where is that visible in the results?
The guarantee is inherited from the SMT solver's soundness and completeness, so it holds only with respect to the constraint program the LLM generated, and only within the 30-minute solver cap. If the LLM mis-encodes a constraint or emits broken code, the guarantee says nothing. This is visible as delivery rates below 100% (e.g. 96.1% for Claude-3 validation), a final pass rate below delivery (93.3%), Mistral-Large's 15.0% failed deliveries, and the 1.3% of queries that time out.

Personal notes

The reusable move for TDE positioning: this is the cleanest existing demonstration that pushing adjudication out of the LLM into a mechanical decider produces step-function gains (0.6-10% → 93.9%) — quote it as evidence that de-circularizing verification pays. But the verification object is a plan against a static database, pre-execution; TDE’s object is post-execution world state with per-action gating. The residual weakness to cite in the novelty defense: their compile step is unverified (delivery-vs-final gap), exactly the seam TDE also has to defend for compiled acceptance suites. Also note the repair loop mutates the spec (user constraints), not the behavior — the inverse of red–green, where the suite is fixed and the work iterates.
