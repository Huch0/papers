Interaction2Code: Benchmarking MLLM-based Interactive Webpage Code Generation from Interactive Prototyping

Curated byChiyeong Heo

Interaction2Code turns design-to-code into an execution-checked, behavioral task: given a pre/post-interaction screenshot pair (an “interactive prototype”), a multimodal LLM must emit a single HTML/CSS/JS file whose interaction, replayed by Selenium, reproduces the after-state; on 127 real webpages / 374 interactions, every model does clearly worse on the interactive region than on the static page, fails in ten catalogued ways, and only recovers with highlighting, failure-aware prompts, cropping, and textual descriptions.

This is the closest existing benchmark to my thesis (execution-grounded synthesis and repair of stateful visual components): it already replays interactions in a real browser and diffs screenshots, and it shows that open-weight Qwen2.5-VL-72B sits at Gemini-1.5-flash level while 3B/7B collapse. Its failure taxonomy (spatial / type / behavioral) is a ready-made target list for a repair loop.

Motivation

Design-to-code benchmarks (Design2Code, WebSight, Vision2UI, DesignBench) score a generated page by how much it looks like a screenshot. They never ask whether anything on the page works: a size selector that does not open, a quantity button that does not count, a carousel that does not advance all score perfectly on CLIP/SSIM. That gap is not a corner case — on 10 random real pages the authors count interactive elements at more than 50% of all elements in every topic, up to 96% for “music” (Fig.1b, p.1). Prior MLLM UI-code work (Design2Code, DCGen, DeclarUI) therefore optimizes the static half of the page and has no signal at all on the dynamic half. Nobody had defined the task, built a dataset of real interactions, or catalogued how models fail on them.

Contribution (what’s new)

The insight that survives deleting “we propose”: an interaction can be specified purely visually as a pair of screenshots (before, after) — an interactive prototype — and it can be graded by execution, because the generated page is asked to tag its interactive element with a known id (interact1), so a webdriver can click it, screenshot the result, and diff against the reference after-state. This must take this form: without the id convention there is no deterministic way to trigger the interaction in generated code; without the after-screenshot there is no ground truth for what the interaction should do; without diffing the changed region the static page dominates the score and hides the interaction (Limitation 1 is exactly that hiding). On top of this, the paper contributes (1) the benchmark with human failure annotations (Tab.I is the only one with real-world + failure annotation + interactive), (2) four diagnosed limitations, and (3) four prompt/input-level fixes that follow one-to-one from the diagnoses.

Research questions

  1. How well do SOTA MLLMs (closed and open-weight) generate interactive webpages from interactive prototypes, relative to generating the static page?
  2. How do they fail, and how severe is each failure for usability?
  3. Which input properties (visual saliency of the interaction area, modality of the description) drive failures?
  4. Do simple interventions targeted at those causes (highlighting, failure-aware prompting, cropping, text+vision) recover performance, and are they complementary?

Methodology

Running example: a shop page where clicking the “M” size button changes the displayed size. The prototype is {screenshot_before, screenshot_after_click}. The MLLM gets both images plus the Direct prompt (Fig.5) and must return one HTML/CSS/JS file with id="interact1" on the button. Evaluation loads the file, clicks #interact1 with Selenium, screenshots, and compares two things: the whole page against the reference, and the interaction region — extracted by pixel subtraction when page size is unchanged, or by git diff on rows/columns when the page grows (Alg.1, p.4) — against the reference region.

Benchmark construction and metrics
  1. Webpage selection — 100 pages from C4 (Design2Code-style filtering, 15 topics, 1,000 sampled, 4 PhD students pick ~25 each with 'at least one meaningful interaction' as the criterion) + 27 GitHub open-source production projects (avg 13k stars) so that React/Vue/Angular/Next.js pages (56/22/11/11%, Fig.4b) are represented. Total 127 pages (§III-A).
  2. Interaction extraction — The same 4 students interact manually, keep 1-10 'important and functional' interactions per page (trivial hover effects are excluded), and capture before/after screenshots. 374 interactions; annotated with HTML tag category (23: button 235, input 52, span 37, link 36, select 35, ...) and visual-effect category (8: text 162, new component 161, color 85, position 45, switch 41, new page 37, new window 34, size 20; Tab.II). One interaction can carry several categories.
  3. Automated interaction — Prompt asks the model to encode interact ids; Selenium locates by id and performs the click. An interaction counts as 'implemented' iff the webdriver can detect it (Implement Rate, IR).
  4. Metrics — Full page: CLIP (visual), SSIM (structure), OCR+BLEU (text), Widget Similarity / Widget Match Rate via GUIPilot. Interaction part: CLIP, SSIM, Text on the extracted region; Position similarity P = 1 - max(|x_o - x_g|, |y_o - y_g|) on normalized region centers; IR; and Usability Rate (UR) judged by humans as 'precisely matches the prototype behavior'.
  5. Models and settings — Gemini-1.5-flash, GPT-4o-20240806, Claude-3.5-Sonnet-20240620, Qwen2.5-VL-Instruct 3B/7B/72B (chosen because many open MLLMs cannot take multiple images). Temperature 0, max tokens 4096 (closed) / 2048 (Qwen). Prompts: Direct, CoT (3 steps: analyze effect, locate element, implement), Mark (red bounding boxes drawn on the screenshots), FAP (list of the 10 failure types to avoid).

Contamination check: BLEU between generated and original HTML is 0.12–0.14 for all four large models (Tab.III), so pages are not being recited. The four fixes are each tested on a different slice: CoT/Mark on the full benchmark (Tab.IV); FAP on a 1/3 held-out split after annotating failures on 2/3 (Tab.VI); Visual Saliency Enhancement (crop the screenshot so the interaction occupies a larger fraction) on 10 failure-case pages (Fig.11, Tab.VII); modality ablation (V / T / V+T, human-written one-line descriptions) on 10 failure-case pages with GPT-4o (Tab.VIII); combined ablation on GPT-4o (Tab.IX).

Main result

Every model scores lower on the interaction part than on the full page, on every metric (Tab.IV, p.6) — Claude-3.5-Sonnet Direct: CLIP 0.7172 → 0.5674, SSIM 0.5318 → 0.4209, Text 0.6003 → 0.3833. GPT-4o and Claude-3.5-Sonnet lead; open-weight Qwen2.5-VL-72B (avg IR 0.7005) matches Gemini-1.5-flash (0.7059), and Qwen scales monotonically 3B → 7B → 72B (Tab.IV). Best single configuration: GPT-4o + Mark, IR 0.8128, interaction CLIP 0.5955. Human usability (Fig.6a) tells the same story: Claude Mark 77% usable, GPT-4o Mark 81%, Gemini Mark 64%, Qwen-72B Mark 54%, Qwen-7B ≈30%, Qwen-3B ≈18%.

Key findings

  • Highlighting the interaction helps, and drawing boxes beats reasoning about it (Tab.IV, Fig.6): Mark > CoT > Direct for the large models (Gemini interaction CLIP 0.4737 → 0.5093 → 0.5194; IR 0.6738 → 0.7112 → 0.7326). Claude’s usability rises 11 pts over Direct and 8 over CoT with Mark. For CoT the gain is model-dependent: GPT-4o and Claude lose under CoT on most metrics (GPT-4o IR 0.7754 → 0.7273), and Qwen-3B collapses (IR 0.3449 → 0.1979), presumably because the 2048-token budget is eaten by reasoning. The paper’s summary sentence “both CoT and Mark improve over direct” is only true on average.
  • Ten failure types, clustered into three causes (Tab.V, Fig.9, §V-B): spatial (missing element, wrong element, wrong element position, wrong effect position), type (wrong widget type, wrong effect type), behavioral (no interaction, effect on wrong element, partial implementation, wrong function). Most frequent: no interaction, partial implementation, missing element, wrong function. Most severe (usability rate): missing element 0%, wrong function 0%, no interaction 6.9%, effect on wrong element 44.4%, wrong effect type 57.1% — whereas positional/type errors leave the interaction mostly usable (89–98%). So the behavioral failures are the ones that matter, and they are exactly the ones a screenshot-similarity metric cannot see.
  • Failure-aware prompting helps the four large models but not the small open ones (Tab.VI): on the 1/3 held-out split, IR rises for Gemini 0.7636 → 0.8182, GPT-4o 0.7636 → 0.8364, Claude 0.6364 → 0.6545, Qwen-72B 0.6545 → 0.7636; but Qwen-3B drops on 7 of 8 metrics (IR 0.4727 → 0.3818) and Qwen-7B is mixed (interaction CLIP 0.2802 → 0.2603). The text claims FAP “can improve … on all models”; the table contradicts this for 3B/7B.
  • Visually subtle interactions fail (Fig.10, §V-C): binning Gemini’s 374 samples by visual saliency into five roughly equal groups, SSIM and Position similarity increase monotonically with saliency (lowest for VS in [0, 0.025), highest for [0.2, 1)); CLIP and Text merely fluctuate. Cropping to magnify the interaction (VSE) turns 10 total failures (all metrics 0 at 1x) into successes: from 1.2x the interaction appears, and by 3x CLIP/SSIM approach 0.8 and Text/Position ≈0.6 (Fig.11), while full-page scores stay flat (CLIP 0.826–0.843, Tab.VII) when the cropped-off remainder is generated separately and stitched.
  • A one-line human text description is worth more than the screenshots (Tab.VIII) (GPT-4o, 10 failure pages): Direct V-only Position 0.3951, T-only 0.4293, V+T 0.7157; CLIP 0.3737 / 0.4174 / 0.6735. V+T wins across all three prompt styles. The screenshots alone leave the model guessing what the interaction is.
  • The four fixes are complementary (Tab.IX) (GPT-4o): base 0.5700/0.4891/0.3652/0.5802 (CLIP/SSIM/Text/Position) → all four 0.6937/0.6251/0.5187/0.7371; the strongest single fix is the textual description (Position 0.7024), and dropping any one from the full stack lowers every metric.
  • User study: an Interaction2Code tool cuts task time 413s → 279s (32.4%) and raises expert-rated quality 3.875 → 4.5 (16.1%) (Tab.X) — but on 4 tasks with 2 developers per arm, so treat it as anecdotal.
  • Widget-level matching (WS ≈ 0.02–0.05) is uninformative (§V-A1): GUIPilot’s detector, built for compact mobile screens, misses most web elements, so the widget metrics say more about the detector than the models.

Implications

For anyone building an interactive-component synthesizer, the takeaways are concrete. (1) Behavior is the bottleneck, not appearance: the fatal failures are “no interaction”, “wrong function”, “missing element”, none of which visual similarity detects, so a behavioral oracle — replay the event, diff the DOM/state, not just pixels — is the metric that should drive training or repair. (2) The three failure clusters map onto three separable sub-skills — localize the element, pick the widget type, infer the state-transition logic — and a repair loop could dispatch on which cluster the execution diff reveals. (3) Screenshot pairs underspecify the transition (toggle vs. open-modal) — the V+T result says a short textual spec of the intended behavior is the cheapest fix, which argues for spec-plus-screenshot inputs. (4) Open weights are viable at 72B and useless below it with pure prompting; the CoT/FAP regressions on 3B/7B show that prompt-only fixes do not transfer down, which leaves room for execution-feedback fine-tuning or RL on small open models. Lineage: extends Design2Code / DCGen (static UI2Code), and the same group’s DesignBench, MRWeb, EfficientUICoder; the execution harness (id tagging + Selenium + region diff) is reusable as a test oracle for stateful component generation.

Limitations

  • Ground truth is a single click and a single after-screenshot: multi-step, stateful, or timing-dependent interactions (drag, typing sequences, animations, toggling back) are reduced to one transition; “partial implementation” (e.g., select but cannot unselect) is only caught by humans.
  • Usability, failure types, and pairwise wins are judged by 4–5 annotators who are also the dataset builders; no inter-annotator agreement is reported.
  • FAP, VSE, and the modality study use tiny or non-comparable slices (1/3 split; 10 failure pages; 10 pages for V+T), and Tab.VI’s Claude Direct IR (0.6364) is far below Tab.IV’s (0.7914), so the subsets differ in difficulty. VSE is only shown for cases that failed at 1x.
  • Position similarity uses only region centers and ignores region size; the region extractor uses pixel/git diff heuristics that break on any incidental change (animations, ads).
  • No backend: login/search-type interactions cannot be verified (author-stated, §VI). Context length for many-interaction pages is also author-stated.
  • No training or execution-feedback baselines: all fixes are prompt/input-level; whether models can repair a page given the Selenium diff is untested.
  • Interaction categories are per-element tags, not behavioral classes — “31 categories” = 23 HTML tags + 8 visual effects, which says little about state complexity.

Critiques and Questions

  1. The headline “MLLMs do worse on the interaction part than the full page” partly conflates two things: the interaction region is smaller (so per-pixel metrics are noisier) and it requires behavior. The saliency analysis (Fig.10) suggests much of the gap is the former; the behavioral gap is better measured by IR/UR alone.
  2. IR counts an interaction as “implemented” if Selenium can find the id and interact — a page with the right id and a no-op handler passes IR. The failure “no interaction” (6.9% usable) shows this is a real gap between IR and usability.
  3. The Mark prompt injects human-drawn boxes, and the V+T setting injects human-written descriptions — both are oracle-assisted, so they are upper bounds on what an automatic pipeline could get, not deployable methods.
  4. Is the per-model drop under CoT a token-budget artifact (2048 for Qwen) rather than a reasoning failure? Not reported.
  5. Selection was “at least one meaningful interaction” by the annotators, and trivial hovers were excluded — the distribution of difficulty is curated, so absolute numbers are not comparable across benchmarks.
Why does the benchmark require the model to write id='interact1' on the interactive element, and what breaks without it?
The id is the handle that lets a Selenium webdriver deterministically find and trigger the generated interaction so the after-state can be screenshotted and diffed against the reference. Without it there is no automatic way to execute the interaction, so evaluation would collapse back to static screenshot similarity — exactly the blind spot the benchmark exists to remove.
Which failure types matter most, and why can screenshot-similarity metrics not catch them?
Missing interactive element, wrong function, and no interaction have usability rates of 0%, 0%, and 6.9% (Tab.V). They are behavioral: the page can look identical before the click and simply do nothing or the wrong thing, so CLIP/SSIM on the static page stay high while the interaction is useless.
