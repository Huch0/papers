Related concepts: Interactive Artifact Generation Baselines

We make design-to-code behavioral and execution-checked — from before/after screenshots of one interaction an MLLM must emit a page whose tagged element, clicked by a webdriver, reproduces the after-state — and on 127 real webpages / 374 interactions every model does worse on the interaction than on the static page, failing in ten catalogued ways.

The closest existing harness to execution-grounded synthesis of stateful visual components: browser replay, changed-region diff, and human usability, plus a failure taxonomy that reads like a repair-loop dispatch table.

Motivation

Take the product page in Fig.1(a): a row of size buttons and a quantity stepper. A static screenshot of it is what every design-to-code benchmark (WebSight, Vision2UI, Design2Code, DesignBench — Tab.I) hands to a model, and a generated page in which clicking “M” does nothing scores perfectly. Existing benchmarks grade how a page looks and are silent on whether anything works — no corner case, since interactive elements are 50% (code) to 96% (music) of all elements on 10 random real pages (Fig.1b). MLLM UI-code methods (Design2Code, DCGen, DeclarUI) therefore optimize the static half of a page with no signal on the dynamic half; nobody had defined the task or catalogued the failures.

Contribution (what’s new)

An interaction can be specified purely visually as a before/after screenshot pair and graded by execution: the model must tag its interactive element with a known id, so a webdriver can click it, screenshot, and diff the changed region against the reference after-state. Each part is forced: without the after-screenshot there is no ground truth for the click; without the id, no deterministic trigger; without region-level diffing, the unchanged page dominates the score and hides the interaction. On top: human failure annotations and four fixes derived from them.

Research questions

  1. How well do closed and open MLLMs generate the interactive part of a page, relative to its static appearance?
  2. How do they fail, and what does each failure type cost in usability?
  3. Do visual saliency of the interaction area and the modality of the description drive the failures?
  4. Do cheap fixes aimed at those causes (highlighting, failure-aware prompting, cropping, adding text) recover performance, and do they stack?

Methodology

Running example: the size selector of Fig.7(b), where clicking “M” changes the displayed size; the interactive prototype is that before/after pair. The model gets both images plus the Direct prompt (Fig.5) and must return one HTML/CSS/JS file with id="interact1" on the M button. Selenium loads the file, clicks #interact1, screenshots, and compares twice: whole page against reference, and the changed region against the reference’s changed region. Four PhD annotators then click M themselves and ask: does the behavior precisely match the prototype?

Why each piece: the selector is a few hundred pixels, so a page-level score is dominated by content that never changed. The after-screenshot is the only ground truth for the click, and designers already produce it. Humans sit on top because pixel similarity cannot tell “the size label changed for the right reason” from “something nearby redrew”, and three of our ten failure types leave the static page pixel-identical. Comparing against the real site is differential testing; the replay is one-edge model-based GUI testing.

Benchmark construction, models, prompts, and the contamination check
  1. Webpage selection (§III-A) — C4 validation pages filtered Design2Code-style (drop too-long / image-only / text-only, dedupe), 15 topics, 1,000 sampled; four CS PhD students with front-end experience pick about 25 each with the criteria 'at least one meaningful interaction' and diversity, giving 100 C4 pages. Because C4 sites rarely use UI frameworks we add 27 GitHub projects found via 'open-production-web-projects' / 'awesome-opensource-apps' with deployed links, averaging 13k stars. Total 127 pages; frameworks React 56%, Vue 22%, Angular 11%, Next.js 11% (Fig.4b).
  2. Interaction extraction and annotation — The same four students interact manually, discard trivial effects such as hover underlines, keep 1–10 important and functional interactions per page, and capture the before/after screenshots. 374 interactions. Each is tagged by HTML tag (23 categories: button 235, input 52, span 37, link 36, select 35, textarea 35, …) and by visual effect (8: text 162, new component 161, color 85, position 45, switch 41, new page 37, new window 34, size 20; Tab.II). One interaction can carry several tags.
  3. Automated replay — Requirement 3 of the prompt asks for interact ids; Selenium locates by id, performs the interaction, screenshots, and the harness rebuilds the generated prototype for comparison. Full-page metrics: CLIP, SSIM, OCR+BLEU text, and Widget Similarity / Widget Match Rate from GUIPilot's detector.
  4. Models and decoding (§IV-A) — Gemini-1.5-flash, GPT-4o-20240806, Claude-3.5-Sonnet-20240620, and Qwen2.5-VL-Instruct 3B / 7B / 72B — chosen because many open MLLMs (LLaVA, Llama-3.2-vision) cannot take multiple images. Temperature 0; max output 4096 tokens for the closed models, 2048 for Qwen. One generation per interaction; no variance reported.
  5. Prompts (Fig.5) — Direct: two screenshots + replicate design, replicate interaction, number interactions, one file. CoT: 'think step by step' with three steps — analyze the effect, locate the element, implement. Mark: red bounding boxes on the interactive element (first screenshot) and on the effect (later screenshots), with an instruction not to render the boxes. FAP: the list of ten failure types to avoid.
  6. Where each fix is measured — CoT / Mark: the full benchmark (Tab.IV, Fig.6). FAP: failure types annotated on 2/3 of the data, tested on the remaining 1/3 (Tab.VI). Visual Saliency Enhancement: 10 randomly sampled failure-case pages, screenshots cropped by 1x–3x, with a two-step generate-focused-area / generate-rest / stitch procedure to keep the full page (Fig.11, Tab.VII). Modality: 10 failure-case pages, GPT-4o, human-written one-line descriptions such as 'clicking the login button triggers a new window with two input boxes' (Tab.VIII). Ablation of all four on GPT-4o (Tab.IX).
  7. Tool user study (§V-F, Tab.X) — Four PhD students, four interaction tasks, 30 minutes; two use an Interaction2Code tool, two use plain LLMs; two external front-end experts score 1–5. Average time 279s with the tool vs 413s without (over 32.4% faster), average score 4.5 vs 3.875 (over 16.1%). Two developers per arm, so this is a demonstration rather than a result.

the pixel area of the interaction region over the pixel area of the after-screenshot (§V-C). Samples are binned into five roughly equal groups: [0, 0.025), [0.025, 0.05), [0.05, 0.1], [0.1, 0.2), [0.2, 1). Cropping a screenshot to half its size doubles VS.

Contamination check (§IV-C, Tab.III): we argue that C4 is text-only (no HTML/CSS/JS) and that MLLM training sets contain no interactive-prototype data, and we measure BLEU between generated and original HTML: Qwen2.5-VL-72B 0.1274, Gemini-1.5-flash 0.1368, GPT-4o 0.1214, Claude-3.5-Sonnet 0.1294. Low BLEU is our evidence that models are not reciting the page markup.

Main result

Every model scores lower on the interaction part than on the full page, on every shared metric and prompt (Tab.IV): Claude-3.5-Sonnet (Direct) drops CLIP 0.7172 → 0.5674, SSIM 0.5318 → 0.4209, Text 0.6003 → 0.3833. GPT-4o and Claude-3.5-Sonnet lead; open-weight Qwen2.5-VL-72B (average IR 0.7005) matches Gemini-1.5-flash (0.7059), and Qwen scales monotonically 3B → 7B → 72B (Tab.IV, Fig.6a). Best single setting: GPT-4o + Mark, IR 0.8128, interaction CLIP 0.5955, 81% judged usable. For the size selector: the M button is usually present and placed right; what fails is what happens on click.

Key findings

  • Drawing boxes on the interaction beats reasoning about it, and CoT is not free (Tab.IV, Fig.6a): Gemini’s interaction CLIP goes 0.4737 → 0.5093 (CoT) → 0.5194 (Mark), IR 0.6738 → 0.7112 → 0.7326; Mark lifts Claude’s usability 11 points. But GPT-4o’s IR falls under CoT (0.7754 → 0.7273) and Qwen-3B collapses (0.3449 → 0.1979); “both improve” holds on average, not per model.
  • Ten failure types, three causes, and only the behavioral ones are fatal (Tab.V, Fig.9): missing element 0% usable, wrong function 0%, no interaction 6.93%, effect on wrong element 44.44%, versus 92.31–98.41% for wrong element / type / position. Fig.7(b) is our size selector with the M button rendered but inert — a top-frequency failure whose static screenshot matches a correct page.
  • Failure-aware prompting helps the four large models and hurts the small ones (Tab.VI): on the 1/3 held-out split IR rises for Gemini 0.7636 → 0.8182, GPT-4o 0.7636 → 0.8364, Qwen-72B 0.6545 → 0.7636; Qwen-3B drops on 7 of 8 metrics (IR 0.4727 → 0.3818). We wrote “improves on all models”; the table disagrees for 3B and 7B.
  • Visually subtle interactions fail, and cropping rescues them (Fig.10, Fig.11, Tab.VII): binned by visual saliency, Gemini’s SSIM and position similarity rise monotonically from bin [0, 0.025) to [0.2, 1). On 10 failure pages all metrics are 0 at 1x magnification and CLIP/SSIM approach 0.8 at 3x, with the stitched full page flat (CLIP 0.826–0.843).
  • One human sentence beats the screenshots, and the four fixes stack (Tab.VIII, Tab.IX): GPT-4o Direct position similarity 0.3951 (visual) / 0.4293 (text) / 0.7157 (both); with all four fixes CLIP/SSIM/Text/Position go 0.5700/0.4891/0.3652/0.5802 → 0.6937/0.6251/0.5187/0.7371, and removing any one lowers every metric.

Implications

Behavior, not appearance, is the bottleneck: the fatal failures are the ones similarity cannot see, so a behavioral oracle — replay the event and diff state, not pixels — should drive training or repair. The three failure causes (spatial, type, behavioral) are separable sub-skills, so a repair loop could dispatch on which cluster the execution diff reveals. Screenshot pairs underspecify the transition (toggle vs. open-modal); the V+T result says a one-line behavioral spec is the cheapest fix — treat the after-state as a contract, as in state-contract verification. Prompting alone works at 72B and not below, so execution-feedback fine-tuning on small open models is the open slot. Lineage: extends Design2Code and DCGen (static UI2Code) and our own DesignBench, MRWeb, EfficientUICoder; the harness (id tagging + Selenium + region diff) is a reusable oracle for stateful component generation.

Limitations

  • We know the ground truth is one click and one after-screenshot: multi-step or toggling interactions collapse to one transition, “partial implementation” (select but not unselect, Fig.8i) is caught only by humans, and backend-dependent interactions (login, search) cannot be verified (§VI).
  • We did not report evaluator agreement: the dataset builders also judge usability and failures with no inter-annotator agreement; “consistent with the automatic metrics” (§V-A2) is rank-level, no correlation coefficient; every number is a single temperature-0 run (variance Not reported); and we did not test an LLM-as-a-judge as a replacement.
  • Our fixes are measured on small, non-comparable slices with oracle help: FAP on a 1/3 split whose Claude Direct IR (0.6364, Tab.VI) is far below the full benchmark’s (0.7914, Tab.IV); VSE and V+T on 10 failure pages; Mark and V+T rely on human-drawn boxes and human-written descriptions — upper bounds for any automatic pipeline.
  • Some metrics measure the wrong thing: position similarity uses centres only; the region extractor breaks on incidental change (animations, ads); widget similarity is 0.0185–0.0533 for every model (Tab.IV) because GUIPilot’s detector targets mobile screens; and “implemented iff detectable by the webdriver” leaves Unclear whether an inert tagged button counts.

Critiques and Questions

  1. Contamination: BLEU of 0.12–0.14 against the original HTML (Tab.III) rules out recitation, not familiarity. The 27 GitHub projects (average 13k stars) are public source almost certainly in code-pretraining corpora, and the C4 pages are live sites that HTML-bearing crawls also cover; “C4 is text-only” describes one corpus, not what the models saw. A behavior-level contamination test is Not reported.
  2. Aging: the models are Gemini-1.5-flash, GPT-4o-20240806, Claude-3.5-Sonnet-20240620, Qwen2.5-VL (Pixtral untested, §VI). Frozen screenshots keep tasks stable, but the top setting already reaches IR 0.8128 / 81% usable, so headroom is thin; the taxonomy and harness outlive the leaderboard.
  3. The headline gap conflates region size with behavior: small regions make pixel metrics noisier (Fig.10 shows SSIM and position track saliency). IR and UR isolate the behavioral gap better.
  4. Tab.IX’s base row equals GPT-4o Direct in Tab.VI (0.5700 / 0.4891 / 0.3652), so the ablation runs on the 1/3 split — yet textual descriptions were written for 10 pages (§V-D). Their source for the whole split is Unclear.
A generated page renders the M size button with id='interact1', Selenium clicks it, and nothing changes. What do IR, the interaction-part metrics, and the human judgment each say, and why does the benchmark need all three?
The webdriver locates and clicks the id, so IR may count it as implemented (we define 'implemented' as 'detectable by webdriver' without saying whether an inert element counts). The interaction-part metrics see no changed region, so they are 0 — as in the 1x magnification case of Fig.11. The annotator clicks M, sees no size change, and marks it unusable: failure type (b) 'no interaction', 6.93% usable (Tab.V). IR alone over-credits, region metrics alone cannot say what changed for the wrong reason, and only the human ties the after-state to the intended behavior.
Why does the benchmark score the extracted interaction region separately from the full page, and what would be lost by scoring only the full page?
The size selector is a small fraction of the page; full-page CLIP/SSIM are dominated by the header, product image, and text that never change, so a page whose M button does nothing scores nearly as well as a correct one. Tab.IV shows exactly this: every model's full-page scores exceed its interaction-part scores (Claude Direct CLIP 0.7172 vs 0.5674), and Fig.10 shows the region metrics fall further as the region gets smaller. Scoring only the full page would reproduce the blind spot of static design-to-code benchmarks.
