VerifyLLM: LLM-Based Pre-Execution Task Plan Verification for Robots

VerifyLLM is a pre-execution repair loop for robot task plans: an LLM compiles the instruction into an LTL formula, then a sliding-window LLM pass over the action sequence — prompted with the formula’s atomic propositions — issues keep / move / remove / augment verdicts per action to fix position errors, missing prerequisites, and redundant steps before anything is executed.

TDE related work (survey category E). It shares the shape “compile NL into a formal spec, check before acting” (NL→LTL, syntax-validated by Spot). But — correcting my survey note, which credited it with “pre-execution mechanical validation” — the validation itself is not mechanical: the plan is never model-checked against the LTL formula; an LLM judge adjudicates with the formula’s propositions injected as prompt context (the ablation prices the entire LTL module at 0.005 LCS), and evaluation is text similarity to a reference plan, never environment execution or final-state grading. VerifyLLM is thus a clean instance of the circular, judge-based verification TDE de-circularizes; the survey’s “Differs” line holds (plan-level static checking, not runtime pre/postconditions or final-state acceptance).

Motivation

LLM-generated robot plans look plausible but hide execution-fatal flaws: a robot may plan to pour water into an upside-down or closed container — a common-sense error, not a hardware one (§I). Classical PDDL planning overlooks preconditions and consequences that were never explicitly encoded (is the container empty before filling? is the fridge closed afterwards?), while LLM-robotics work overwhelmingly generates plans rather than verifying them, and the few existing verifiers lean on simple failure templates (“object X is blocking”) or narrow feasibility domains like motion planning (§II-A). Formal LTL model checking verifies system properties but struggles with natural-language understanding (§II-B).

Contribution (what’s new)

LTL used as an intermediate representation for LLM-based plan repair rather than for strict model checking: the instruction is compiled into a syntax-validated formula whose atomic propositions ground a windowed LLM review of the plan (§II-B). On top of that, a typed error taxonomy (position error / missing prerequisite / redundant action) bound to per-action edit operations — keep, move, remove, augment — applied over a sliding context window and iterated to convergence (Alg.1). Second claimed contribution: ALFRED-LTL and VirtualHome-LTL, LTL-annotated datasets — only the VirtualHome side appears in the experiments.

Research questions

  1. What errors do small-LLM planners actually make on household tasks? 2. Does LTL-guided LLM verification repair plans better than prompting-only optimizers? 3. Which component — LTL translation or LLM reasoning — carries the effect?

Methodology

Two modules operate on an externally generated plan π = ⟨a1, ..., an⟩ and task description τ; the framework generates nothing itself. The Translation Module maps τ to an LTL formula ϕ by few-shot prompting, with Spot validating syntax (up to 3 reprompts). The Verification Module sweeps the plan with a sliding window (w=5): for each action the LLM sees up to five previous/next actions plus propositions extracted from ϕ, and returns a structured JSON verdict that is applied as an edit; sweeps repeat until convergence. Formally the whole procedure is V : Π × τ → Π — plan in, refined plan out (Eq.6). Evaluation: 71 VirtualHome instructions from the ZeroShot planner, plans generated by five 0.5B-3B models, verifiers Llama-3.2-1B and Claude; quality is measured as similarity to the dataset’s reference plan.

Method details
  1. Translate to LTL (§V-B) — Few-shot LLM maps the task description to a formula over atomic propositions, e.g. F(heat water) ∧ F(add tea) ∧ F(serve) for tea-making (Eq.8). The Spot library converts the formula to a Büchi automaton to validate syntax; on failure, reprompt up to 3 times. Note the example formula encodes eventualities only — no ordering constraints.
  2. Windowed review (§V-C) — For each action, build a context of up to w=5 previous and next actions plus propositions from ϕ (Eq.9); w=5 was chosen empirically (Tab.IV). The LLM assesses position optimality, necessity, and compatibility with the propositions (the text announces 'four key aspects' but lists these three).
  3. Decide and edit (Alg.1, Fig.3) — The prompt enforces a structured JSON response: per action, keep / remove (redundant) / move (reorder) / augment (insert a generated prerequisite via GenPrereq), with reasoning. Edits are applied in place to the working plan.
  4. Iterate and measure (§VI) — Sweeps repeat until convergence (criterion not reported). After normalization (lowercase, strip prepositions), quality vs the reference plan is: LCS ratio |LCS(S1,S2)| / max(|S1|,|S2|); Missing = |Aref \ Agen|; Extra = |Agen \ Aref|; Order Errors = positional mismatches plus length surplus (Eqs.10-13).

Main result

On the 71 VirtualHome instructions, VerifyLLM with Claude as verifier lifts LCS similarity from 0.0717 (unverified Llama-3.2-1B plans) to 0.183 and cuts order errors from 16.48 to 9.47 (Tab.II, p.6), while all three prompting-only baselines fail to beat the unverified plans on LCS (best: CoT at 0.0705 vs 0.0717) (Tab.II, p.6). The paper reports the order-error cut as “nearly 40%” against the best baseline; arithmetically 16.80 to 9.47 is 43.6%. Rows below from Tab.II, with the unverified row from Tab.I/Tab.III:

Key findings

  • Small-LLM planners share a consistent error profile regardless of scale (0.5B-3B) (Tab.I, p.6): per plan, 10.21-10.29 missing actions, 7.51-10.45 extra actions, 13.94-17.58 order errors; LCS stays below 0.09 for all five models, with ordering the most prevalent error type.
  • Naive prompting verifiers actively damage plans (Tab.II, p.6): Window Opt. inflates extra actions from 9.14 to 13.47 and order errors from 16.48 to 22.84 relative to doing nothing, and all three baselines sit at identical Missing (10.38) — worse than the unverified 10.28.
  • The LLM is load-bearing; the LTL is marginal (Tab.III, p.6): removing LLM verification collapses LCS 0.183 to 0.0717 (order errors 9.47 to 16.48), while removing LTL translation costs only 0.183 to 0.178 (order 9.47 to 9.80) and even improves Extra (8.32 to 8.25). The evidence supports “the LLM is critical”; it does not support the paper’s symmetric claim that both components are.
  • Verifier capacity dominates outcome quality (Tab.II, §VI-A.5): Claude vs Llama-3.2-1B as verifier is 0.183 vs 0.0982 LCS; with the small verifier, Missing gets worse than no verification at all (11.18 vs 10.28).
  • The motivating error class barely improves (Tab.II, p.6): missing actions move from 10.28 (unverified) to 10.17 at best — about 1% — so the augment operation largely fails at inserting the missing prerequisites the paper opens with.
  • Window size w=5 is optimal (Tab.IV, p.7): F1 0.65 vs 0.58 (w=3) and 0.54 (w=7); what the F1 is computed over is not defined anywhere in the paper.

Implications

This is the LLM-judge pole of the pre-execution-verification design space: it shows a typed edit loop with a strong model helps while its own ablation undercuts the formal-methods framing. It extends the authors’ HAIS 2024 common-sense plan verifier (Grigorev et al. [12]), and contrasts with classical mechanical plan validation (VAL [20]) and LTL model checking in robotics (Kress-Gazit et al. [13]), template-based failure detection (Zhang et al. [22]) and feasibility checking (Text2Motion [23]; Yang et al. [21]), and runtime monitoring/replanning (Replan [26]); the NL-to-LTL step follows lifted-LTL translation (Hsiung et al. [31]). Would actually model-checking the plan against the compiled ϕ beat prompt-injecting its propositions? Closing the loop with execution — grading verified plans by simulator task success or final world state instead of reference-plan similarity — is exactly the gap TDE’s environment-evaluated acceptance suite targets.

Limitations

  • Author-stated: struggles with complex temporal dependencies and parallel task sequences; lacks a mechanism mapping robot capabilities to plan actions; household domains only (§VII).
  • No execution-based evaluation: verified plans are never run in VirtualHome or ALFRED despite the “before execution in simulator or real-world environments” framing; all metrics are text similarity to a single reference plan, so valid alternative plans are penalized and “improvement” need not imply executability or goal achievement.
  • ALFRED-LTL is announced as a contribution but never used in any experiment; the entire evaluation is 71 VirtualHome instructions.
  • Reporting gaps: the Claude variant/version is unspecified; single runs with no variance or significance; the convergence criterion and the Tab.IV F1 definition are missing; the plan generator for Tab.II is implied (Llama-3.2-1B, matching the ablation row) rather than stated.

Critiques and Questions

  1. “Verification” here is text-to-text repair: V : Π × τ → Π takes no environment state and executes nothing, and nothing certifies the refined plan is executable or goal-reaching. Under a mechanical-verification criterion (TDE’s), this is an unverified transformation with an LLM adjudicator.
  2. The formal layer does no formal work: the plan is never checked against ϕ (Spot only syntax-checks ϕ itself), and the example compilation F(heat water) ∧ F(add tea) ∧ F(serve) encodes no ordering, so the formula could not catch position errors even in principle. The ablation (-0.005 LCS) quantifies this; “combining formal methods with LLMs” is mostly prompt engineering here.
  3. Metric validity: LCS against one reference after normalization rewards mimicking the reference’s phrasing and ordering conventions, and the Order Errors count (positional mismatch plus length surplus) inflates under a single insertion offset. A strong verifier could “win” by style conformity rather than correctness.
  4. Internal inconsistencies erode confidence: the prose claims baselines “reduced the percentage of missing actions” vs the original, but the tables show an increase (10.38 vs 10.28); “four key aspects” precedes a list of three; “nearly 40%” is arithmetically 43.6%.
  5. Unclear scope of the headline: results are reported only for plans from one generator (implied Llama-3.2-1B); whether verification gains transfer across the other four generators in Tab.I is not reported.
What mechanical role does the LTL formula actually play in VerifyLLM's verification, and what does the ablation say about its contribution?
Only the formula itself is mechanically checked: Spot converts it to a Büchi automaton to validate syntax, with up to 3 reprompts. The plan is never model-checked against the formula; its atomic propositions are merely injected into the LLM prompt as context. Ablating the LTL module shifts LCS only from 0.183 to 0.178, while removing the LLM verifier collapses it to 0.0717 — the LLM judge, not the formal layer, does the verification.

Personal notes

For the TDE novelty defense: VerifyLLM is the cleanest “formal clothing, LLM body” specimen in the corpus. It compiles NL to LTL (superficially like TDE compiling NL to an acceptance suite) but never checks anything against the formula mechanically — the LTL is prompt garnish priced at 0.005 LCS by their own ablation, and the adjudicator is an LLM judge over plan text. Contrast axes vs TDE: (1) static plan text vs runtime world state; (2) LLM verdicts vs environment-computed checks; (3) reference-plan similarity vs final-state acceptance; (4) a repair operator V: plan → plan vs a red-green gate on task completion. Soften the survey line “shares pre-execution mechanical validation” accordingly — only the Spot syntax check of the formula is mechanical.
