Related concepts: Agent-as-a-Verifier

We make website generation self-supervising: at every step of our agent a VLM grades the landing-page screenshot (0–5) and a GUI agent clicks through the requirements and is graded (1–5), and the sum of those two grades drives repair, backtracking, select-best, and a per-step GRPO advantage — lifting Claude-3.5-Sonnet from 26.4% to 51.9% and Qwen2.5-Coder-7B from 38.9% to 45.4% on WebGen-Bench.

The closest existing template for my thesis: render-and-interact feedback on interactive web artifacts turned into a dense reward for an open 7B/8B engine, with an honest audit of where the agent-as-a-verifier signal is noisy and where functional fixes break appearance.

Motivation

Take the request we carry through this summary (Fig.9): “a multi-company dashboard that collects and displays financial data from each company, provides consolidated reports, and supports cross-company comparisons; mint cream background, teal components.” A code agent must turn that paragraph into a multi-file Vite + React project. Every code agent we compare against — OpenHands, Aider, Bolt.diy — verifies it by code execution alone: dependencies install, the dev server prints ready, feedback stops (§1). Execution output cannot see that the comparison view is buried behind repeated clicks, that components overlap, or that a button does nothing. On WebGen-Bench, even Claude-3.5-Sonnet inside Bolt.diy passes only 26.4% of test cases (Tab.1). Underneath: we want a cheap 7B–8B open engine, but such models lag far behind, and the RL recipes that could close the gap either reward only the final outcome (sparse) or need step-level ground truth that does not exist for websites (§2.2, §4).

Contribution (what’s new)

The two things a website must be — good-looking and working — are both measurable at every step by machinery already in the loop: a VLM grading the landing-page screenshot 0–5, and a VLM-driven GUI agent exercising the requirements, graded 1–5. Their sum is simultaneously a repair signal, a selection criterion for backtracking and select-best, and a dense per-step reward for GRPO. The form is forced: looks need a picture, function needs clicks, and because each score measures the codebase at that step, the advantage must be per-step and non-cumulative.

Research questions

  1. Does screenshot + GUI-agent feedback, with backtracking and select-best, beat execution-only feedback across many engine LLMs?
  2. Can the scores produced inside that loop train 7B–8B engines as step-level rewards, and which advantage design matters?
  3. Is a small open VLM a good enough judge, and can it replace the coding LLM?

Methodology

One WebGen-Agent step is edit → execute → gather feedback (Fig.1). For the dashboard, the coding LLM (behind a Bolt.diy-style prompt inside WebContainer) writes the Vite + React files; dependencies install, the dev server starts. A VLM sees the landing-page screenshot and returns a description (teal header titled Financial Dashboard, a search bar, four equal-sized cards), an appearance grade, and suggestions (Fig.4–5). This LLM-as-a-judge on pixels is not enough alone: the page grades 4 and looks finished, yet the cross-company comparison is unreachable. So once the agent emits screenshot_validated, it writes a test instruction for a GUI agent — verify the colours, browse company data, view consolidated reports, perform comparisons (Fig.6) — which clicks through the site; its trajectory is graded 1–5 with fix suggestions (Fig.7). First pass: shot=4, gui=2, “critical features are hidden behind repetitive interactions; add drill-down options”. The next edit adds a comparison mode, financial ratios, and export; second pass shot=4, gui=5, finish (Fig.9). Because a later edit sometimes makes the site worse, after five consecutive execution errors we backtrack to the best stored step, and at termination we select-best (§2.1, Alg.1–2).

A 7B engine needs two training stages. First a light SFT warm start — not optional: raw Qwen2.5-Coder-7B-Instruct fails to even start the site on 24.3% of test cases (Tab.1), and a rollout group in which every site fails yields identical rewards, hence zero advantage, so GRPO has nothing to climb. Then Step-GRPO on 500 WebGen-Instruct prompts, 5 rollouts each, one epoch (§3.1). In the dashboard rollout, step 1 earns r1=4+2=6r_1 = 4 + 2 = 6r1​=4+2=6, step 2 earns r2=4+5=9r_2 = 4 + 5 = 9r2​=4+5=9; each step’s edit tokens get their own advantage, normalised against every step reward of all five rollouts. We do not fold future rewards into earlier steps: the score at step jjj already measures the codebase at step jjj. Outcome-only reward would give both steps the same credit; cumulative credit would drag step 1 up on step 2’s success — both lose in Tab.3.

Definition — WebGen-Bench metrics (§3.1, Tab.1)

Each of the 647 test cases is executed by a GUI agent driven by Qwen2.5-VL-32B-Instruct and judged Yes, Partial, or No, or counted as Start failed if the site does not serve. Accuracy is the share of test cases passed; the Tab.1 rows are consistent with Yes + ½·Partial (22.6 + 7.6/2 = 26.4), the weighting inherited from Lu et al. 2025b. Appearance score is GPT-4o’s appearance grade (§3.1); its scale and aggregation are inherited from Lu et al. 2025b and not restated here. Both judges are the benchmark’s, not ours.

Training details (§3.1, App.A). SFT: learning rate 4e-5, batch 32, one epoch, on approximately 700 DeepSeek-V3 trajectories collected with rejection sampling. Step-GRPO: learning rate 1e-6, batch 16, 5 samples per instruction, 500 WebGen-Instruct instructions randomly sampled and manually filtered for ambiguity, one epoch, no KL term; more than 24 hours on 16 A800 GPUs. Training on more samples “does not yield noticeable gains” (no numbers given). The same recipe is applied to Qwen3-8B.

  1. Edit — The coding LLM emits Bolt-style file artifacts given the trajectory so far.
  2. Execute — Install dependencies, start the dev server; on error append stderr and retry; five consecutive errors trigger backtracking.
  3. Screenshot feedback — The VLM describes the landing page, grades it 0–5, suggests fixes; the agent decides whether to iterate on looks or emit screenshot_validated.
  4. GUI-agent testing — The coding LLM writes a test instruction; the GUI agent browses; the trajectory is graded 1–5 with fix suggestions; pass means finish.
  5. Select best — Restore the step with the highest GUI score, then highest screenshot score, then the latest.

Main result

Same engine, different scaffold: Claude-3.5-Sonnet goes from 26.4% / 3.0 (Bolt.diy) to 51.9% / 3.9 in WebGen-Agent; DeepSeek-V3 from 20.8% / 2.0 to 52.6% / 3.8; DeepSeek-R1 from 27.8% / 2.5 to 46.4% / 3.8 (Tab.1). The best engine is open-weight: Qwen3-Coder-480B-A35B reaches 58.2% / 4.3 and Qwen3-Coder-30B-A3B 52.8% / 4.0 (Tab.1). For the small engines we train, Qwen2.5-Coder-7B-Instruct goes 12.4% → 38.9% (SFT) → 45.4% (Step-GRPO) with appearance 1.6 → 3.4 → 3.7, and Qwen3-8B goes 34.1% → 38.6% → 43.4% (3.2 → 3.4 → 3.6) (Tab.1). The dashboard’s tested requirements — browse, report, compare — are the functional test cases accuracy counts and a screenshot cannot certify.

Key findings

  • The workflow pieces pull in different directions: execution-only 45.9% / 3.0 → +screenshot 46.6% / 3.6 → +GUI-agent 49.9% / 3.4 → +backtrack 51.2% / 3.7 → +select-best 52.6% / 3.8 (DeepSeek-V3) (Tab.2). GUI testing is the largest accuracy lever (+3.3) but costs 0.2 appearance because functional edits break layout; backtracking and select-best recover it.
  • Same reward, different advantage: naive outcome GRPO 42.5%, cumulative-advantage Step-GRPO 38.7% (below the SFT baseline of 38.9%), per-step non-accumulated advantage 45.4%; a second SFT epoch is flat at 39.3% (Tab.3). Folding future steps into the current one adds noise to a state measurement.
  • Both reward halves are necessary: screenshot-only 40.2% / 3.5, GUI-only 40.4% / 3.4, the sum 45.4% / 3.7 (Tab.3).
  • The judge can be small, the coder cannot: swapping Qwen2.5-VL-32B for GPT-4o as feedback VLM moves DeepSeek-V3 from 52.6% / 3.8 to 52.1% / 3.6, while using Qwen2.5-VL-32B as the coding LLM collapses to 5.6% / 1.3 (Tab.4).
  • Human audit: screenshot scores agree with annotators 93.6–95.6% and GUI-agent scores 89.6–92.2% (standard errors 0.20–0.26 and 0.31–0.44); 98.3% of generated GUI test instructions cover at least 75% of the requirements and 77.2% cover roughly all of them (Tab.5, Tab.6). The functional half still carries a one-in-ten error that RL can exploit.
  • Step-GRPO’s gain over SFT on the 7B model lands where interaction is tested: User Interaction 33.5% → 41.1%, Data Management 33.8% → 47.8%, Functional Testing 23.5% → 30.7%, while Content Presentation slips 53.4% → 51.1% (Tab.7). The reward taught the model to make things work, not to write more content.
Secondary results
  • The iteration budget saturates: accuracy 42.4% at 2 iterations, 52.0% at 10, 53.3% at 16, 52.6% at 20, while the share of tasks hitting the limit falls from 100% to 7.9% (DeepSeek-V3) (Tab.8). The ±1-point jitter between budgets 10 and 20 is our only free estimate of run-to-run noise.
  • Both SFT and Step-GRPO raise the average file count and line count of generated projects for the 7B and 8B models (Fig.3); qualitatively (App.I) SFT removes malformed sites and Step-GRPO refines aesthetics and harmony.
  • Mid-size open engines gain the most from the scaffold: Qwen2.5-Coder-32B 9.5% → 32.0% and Qwen2.5-72B 13.8% → 35.9% versus Bolt.diy (Tab.1).
  • GPT-4o as judge moves agreement only from 94.8% to 95.5% (screenshot) and 91.2% to 92.2% (GUI) on DeepSeek-V3 sites (Tab.5).

Implications

We closed the WebGen-Bench line (Lu et al. 2025b) and Bolt.diy-style scaffolds into an RL loop with no human labels, between execution-reward code RL (RLEF, SWE-RL-style outcome rewards) and process-reward methods that need ground-truth steps. Lessons for interactive component synthesis: keep the appearance judge and the behaviour judge separate and sum them; make the advantage per-step and non-cumulative when the reward is a state measurement; keep a select-best snapshot because repair edits regress. Whether the recipe holds for a single stateful component (a colour picker, a sortable table) where the tester must check state transitions. Whether the one-in-ten GUI-score error becomes reward hacking at larger RL budgets than our one epoch on 500 prompts, and whether mutation-hardened checks would close it. Replacing the VLM tester with deterministic checks derived from the instruction (model-based GUI testing) to remove judge noise.

Limitations

  • We know our in-loop GUI judge is the same VLM WebGen-Bench uses for functional testing (Qwen2.5-VL-32B-Instruct, §3.1), so the loop partly optimises against the benchmark’s own grader; only the appearance judge (GPT-4o) differs.
  • We did not run seeds or report confidence intervals; every number is one run, and several ablation deltas (0.7–1.5 points) sit inside the ±1-point jitter across iteration budgets in Tab.8.
  • We trained only 7B/8B models because Step-GRPO takes over 24 hours on 16 A800s (App.A); scaling to 30B–72B is future work, our SFT data is distilled from DeepSeek-V3 so raw-model → RL without SFT is untested, and per-task cost is Not reported.
  • We grade only the landing-page screenshot and ignore response speed, network conditions, and multi-page appearance (§2.1, App.A); we did not check overlap between the 500 RL prompts and the 101 test instructions.

Critiques and Questions

  1. The advantage normalises each step against the pool of all steps of all rollouts, so an early 4+2 step and a final 4+2 step earn the same credit; the model is rewarded for being in a good state, never for improving one. A delta reward (gain over the previous step) is untested.
  2. The GUI test instruction is written by the coding LLM (Fig.6), so during RL the policy partly controls its own test; coverage was audited only on untrained engines (Tab.6). And §2.1 says the engine LLM grades the GUI trajectory while §3.1 and App.E credit the feedback VLM — Unclear which model produces the reward.
  3. Much of the weak-engine gain is the Start-failed column (raw Qwen2.5-Coder-7B: 24.3%, Tab.1): part of the SFT jump is learning the Bolt artifact format, and nothing separates that from website skill.
  4. Accuracy is judged by a GUI agent that agrees with humans nine times in ten (Tab.5); nothing bounds how much of the 45.4% survives a human pass.
On the financial-dashboard example, why does screenshot feedback alone let the agent stop too early, and what does the GUI-agent test add?
The first landing page scores shot=4 and looks finished, but the cross-company comparison is hidden behind repetitive clicks; the GUI agent's trajectory scores gui=2 with the suggestion to add drill-down options, the agent adds a comparison mode and export, and the second pass scores gui=5 (Fig.9). Only interaction exposes the functional gap.
Why do we refuse to accumulate future-step rewards into the current step's advantage, and what happens when you do?
Because the screenshot and GUI scores at step j directly measure the codebase at step j, so future rewards add noise rather than information. Cumulative-advantage Step-GRPO drops to 38.7% accuracy, below the SFT baseline of 38.9%, versus 45.4% with per-step advantages (Tab.3).
