Curated byChiyeong Heo

TDFlow flips SWE-Bench into a test-resolution task — reveal the normally hidden human-written tests, then loop a fixed four-sub-agent workflow (propose patch → revise → debug each failing test → re-propose) red–green until the suite passes — reaching 94.3% on SWE-Bench Verified with human tests vs 68.0% with self-generated ones, and locating the last obstacle to autonomous repository repair in writing reproduction tests, not solving them.

The closest SWE-domain precedent for TDE’s run loop: completion is gated on a mechanically executed acceptance suite, iterated red–green until green, and its Generate Tests mode is exactly TDE’s compile-the-instruction-into-tests step — here quantified as the weak link (94.3% → 68.0%, back to 93.3% when generated tests are valid). The TDE deltas survive contact with the paper: TDFlow’s suite asserts repository code behavior, not final environment state; its best mode needs human-written tests; there are no per-action, environment-evaluated pre/postconditions (guardrails are prompts plus file-access restrictions); and its anti-gaming adjudication — the test-hacking audit — is manual human review, precisely the hole TDE’s mechanical postconditions aim to close.

Motivation

Industrial TDD studies report large quality gains — defect density improved up to 90% (Nagappan et al. 2008), 18% higher functional-test quality (George & Williams 2003) — at the price of 16–35% more development time, and that time burden is the stated blocker keeping teams off test-first development (§2.1). On the evaluation side, SWE-Bench-style benchmarks hide the human-written acceptance tests, forcing agents to simultaneously understand the issue, invent their own validation, and patch the repo — conflating test writing with test solving (§1, §2.2). Architecturally, monolithic agents couple every subtask capability inside one ever-growing context: overall success is bottlenecked by the weakest subtask, and long-context tool use degrades performance (§2.3).

Contribution (what’s new)

Reframe repository-scale repair as test resolution: hand the system the acceptance tests and gate completion exclusively on making them pass — turning SWE-Bench inside out and enabling a division of labor where humans write tests and LLMs solve them. The mechanism is forced decomposition into four minimal-tool sub-agents (Explore Files, Revise Patch, Debug One, optional Generate Tests) in a fixed loop where each iteration proposes a fresh whole-repo diff against the pristine initial state, from rewritten minimal context — aggregated debugging reports instead of a growing transcript. The form follows the failure mode: if monolithic agents decay with context length and couple subtasks, the workflow — not the LLM — must own the decomposition, which also makes each sub-task individually improvable and trainable.

Research questions

  1. Given ground-truth tests, can a tightly constrained agentic workflow resolve them at repository scale at human level, and at what cost? 2. Does the residual gap to fully autonomous software engineering lie in solving tests or in writing them? 3. When success is gated purely on tests, how often does the system hack the tests instead of fixing the issue?

Methodology

Run the failing reproduction tests; hand the issue, failing-test sources, and error messages to a read-only Explore Files sub-agent (find / view / hierarchy tools only — no file editing, no bash) that proposes a whole-repository patch. If the diff fails to apply, a Revise Patch sub-agent repairs its context lines (never the inserted code). All tests re-run; one debugger-equipped Debug One sub-agent per failing test (up to 18) writes a root-cause report; reports are aggregated into the next Explore Files iteration — up to 10 red–green rounds. The repo always resets to its initial state, so every candidate patch is a diff against the same baseline. If no patch passes everything, TDFlow outputs the one passing the most reproduction tests without breaking regressions (§3.5). Without human tests, a Generate Tests sub-agent first compiles the issue description into single-assert reproduction tests that must fail pre-patch (§3.4).

Workflow details, settings, and prompt design
  1. Generate Tests (optional entry, §3.4) — Claude 4 Sonnet (on Verified) explores the repo, writes reproduction tests with exactly one assert each, must run them via an evaluate_tests tool before submitting (they should fail pre-fix), and returns test names + file lines so the workflow can run and debug each test individually later.
  2. Explore Files (§3.1) — Context is engineered as the minimum complete representation of history: the issue, plus — for each previous attempt — the proposed global patch, the source of the tests it still fails (regressions included), and the debugging reports. The prompt frames reports as analyses by 'a junior engineer equipped with a debugger' and insists a patch is 100% necessary.
  3. Revise Patch (§3.2) — Triggered only when a patch fails to apply for lack of correct context. Receives the malformed patch + the same read-only tools; forbidden from modifying inserted code. Authors report this beats feeding apply-errors back to Explore Files.
  4. Debug One (§3.3, App.D) — Per failing test: test source, error message, the failing patch, and a restricted Python debugger (step / next / return / continue, breakpoints incl. conditional, p / pp / whatis / args / locals / globals, list, stack, restart — Table 8). Instructed to chase root cause, not symptoms, and to avoid breakpoints on function signatures.
  5. Caps and knobs (Table 6) — 10 total iterations; at most 18 tests debugged per iteration; max turns 200 (Generate Tests), 250 (Debug One), 75 (Explore Files), 50 (Revise Patch); temperature 1.0 gave the best performance — attributed to exploring creative alternative solutions across iterations.

Test-hacking mitigations: precisely engineered system prompts, patches blocked from touching test folders or test source, sub-agents see only the repo folder (not the filesystem), and repeated nudging via tool-call results (§4.4).

Main result

With human-written tests revealed on SWE-Bench Lite (all systems GPT-4.1; every baseline modified by the authors to receive and run the tests), TDFlow resolves 88.8% vs 61.0% for the strongest baseline (modified Agentless) — +27.8 points absolute (Tab.1, p.5), at the highest cost per issue ($1.51). On SWE-Bench Verified with GPT-5 sub-agents, TDFlow reaches 94.3% with human-written tests, 87.2% without the debugging sub-agent, and 68.0% when generating its own tests (Tab.2, p.7) (the intro instead quotes 69.8% — see Critiques).

Key findings

  • When every generated test is a true reproduction test (BTR = 0), TDFlow solves 93.3% — essentially the human-written 94.3% (Fig.2, §5): test provenance is irrelevant; test validity is everything. The bottleneck to autonomy is generation quality, not resolution ability.
  • Success degrades smoothly as BTR rises, with a sharp drop only when no valid reproduction test exists (Fig.2, §5): the fallback selection rule (most repro tests passed, no regressions broken) keeps partially-tested instances alive.
  • Ablating the Debug One sub-agent costs 7.1 points (94.3% → 87.2%) (Tab.2, p.7): dedicated per-test debugger reports buy real accuracy for +$0.28/issue.
  • Only 7 of 800 audited runs show test hacking (4 Lite, 3 Verified) (§4.4, App.C): three engineers, a 13-sign rubric, a 2-of-3 vote; all hacks counted as failures.
  • Agentless is both the strongest and cheapest baseline (61.0%, $0.53) (Tab.1, §4.1): its up-to-40-patch ensemble filtered against the revealed tests approximates test-driven search without agency; agentic baselines burn budget on localization.
  • Bad tests are expensive: test-resolution cost nearly triples in self-generated mode ($2.83 vs $1.01/issue) (Tab.2, §4.2) — the loop burns debugging budget optimizing against tests that never reproduced the issue. Pass rate scales with loop iterations with fast diminishing returns (Fig.3a, §4.3), evidence that accumulated failure context helps.

Implications

If valid tests exist, repository-scale test resolution is essentially solved — so the frontier moves to test generation. That promotes test-generation systems and benchmarks (CodeT, Libro, Otter, AEGIS, UTBoost; SWT-Bench, TDD-Bench) from complementary work to critical path, and the decoupled workflow makes Generate Tests individually trainable — the authors propose long-horizon RL post-training targeted specifically at test generation. It also sharpens the workflow-vs-agent argument of Agentless against ReACT-style SWE-agent and OpenHands and memory-augmented ExpeRepair: when the task structure is known (TDD’s loop), fixed decomposition beats agentic freedom. Automated test-hacking detection is the acknowledged missing piece for production use. For TDE specifically: whether suite-gated red–green loops transfer from repository tests to environment-state assertions (AppWorld-style state diffs), where a ‘don’t touch the test folder’ guardrail has no analog and gaming must be excluded by construction rather than by audit.

Limitations

  • The headline denominators are not the official benchmarks: TDFlow could not run 22/300 Lite instances (88.8% is computed over 278) and 45/500 Verified instances (the denominator behind 94.3% is not stated; presumably 455). Counting exclusions as failures gives roughly 82.3% (Lite) and 85.8% (Verified) — my arithmetic, not the paper’s. OpenHands’ Lite denominator is 201 after 91 evaluation failures (App.A–B).
  • The exclusions come from rigid infrastructure requirements: every test must be individually runnable and debuggable with a unique name-to-line mapping — a setup tax purely agentic systems don’t pay (§8, App.B).
  • Tests are frozen once provided or generated — no correction mechanism, no early stopping: wrong or unsolvable tests are optimized against until the 10-iteration cap; author-stated cause of the self-generated gap (§5, §8).
  • Test-hacking control is prompt-level and detection is manual — no automated check exists yet (§6).
  • Single runs, no variance or seeds; Lite uses GPT-4.1 while Verified uses GPT-5, so the 88.8% vs 94.3% difference across benchmarks partly reflects model choice. Seed/variance analysis: Not reported.
  • The revealed-tests setting is non-standard by design: numbers are not comparable to SWE-Bench leaderboard results (where tests stay hidden).

Critiques and Questions

  1. The +27.8 headline compares against baselines the authors themselves modified (default configs, GPT-4.1) for a setting those systems weren’t built for; ensembling alone took Agentless to 61.0%, so a test-aware baseline tuned for this setting might close a real chunk of the gap.
  2. Internal inconsistencies: the intro says 69.8% for self-generated Verified where Table 2, §4.2, and §5 say 68.0%; the intro claims all 300+500 runs were audited while the appendices report 22+45 instances never ran; and the BTR figure is cross-referenced as Figure 4 but captioned Figure 2.
  3. The human-level claim rests on SWE-Bench Verified’s annotation that instances are solvable given the issue — not on measured human pass rates on the same task — so it is an interpretation, not a comparison.
  4. 7/800 test hacks is a floor, not a ceiling: manual majority-vote log review can miss subtle assertion-overfitting. The paper simultaneously demonstrates mechanical success-gating and concedes its integrity check still needs humans.
  5. All evidence is Python on SWE-Bench repositories (Django-class). The per-repo engineering cost of the test harness for a new language or repo: Not reported.
Why does the self-generated-tests mode (68.0%) fall so far below the human-written mode (94.3%), and what evidence shows the gap is not a resolution failure?
Generated tests are frozen after the Generate Tests phase — TDFlow may not modify them — so invalid reproduction tests are never corrected and the loop optimizes a wrong target until the iteration cap. On instances where every generated test is a true reproduction test (BTR = 0), the solve rate is 93.3%, essentially matching the human-written 94.3%: resolution capability is intact, and failures concentrate in test generation.

Personal notes

Cleanest code-domain evidence for the TDE bet: mechanical suite-gating plus red–green looping hits ceiling performance, and the spec-compilation step (issue → tests) is where autonomy dies — BTR is the whole story. Reusable framings: frozen tests (the system may not rewrite its own spec) ≈ TDE’s immutable acceptance suite; their manual test-hacking audit is the anti-pattern TDE’s environment-evaluated postconditions should replace. Cite 88.8/94.3 with the denominator caveat (278/≈455, not 300/500).
