Curated byChiyeong Heo

VAGEN turns GUI-agent reward modeling into a single tool-augmented verifier agent that grounds its verdict in the recorded trajectory first and escalates to shell/Python/GUI probes of latent environment state only when trajectory evidence runs out, beating both passive LLM judges and probing-first verifiers on accuracy and cost.

For TDE this is the canonical category-F contrast: verification is environment-grounded in its evidence (shell reads like gsettings, GUI probes of the final state) but the adjudicator is still an LLM agent — checks are ad-hoc per trajectory, never compiled into a reusable executable acceptance suite, and the verdict is post-hoc reward modeling with no completion gating and no red–green loop (Best-of-N submits a trajectory even when every rollout is judged a failure). Its scalability case against rule-based checkers — backed by a human audit documenting false negatives in OSWorld-Verified’s own test scripts — is the sharpest empirical objection TDE’s runtime-compiled suites must answer.

Motivation

RLVR for GUI agents needs a reliable binary reward per trajectory. Rule-based checkers (the hand-written test scripts of OSWorld-Verified and AndroidWorld) are accurate but unscalable and fail open-ended or multi-solution tasks (§1). LLM-as-a-Judge verification is passive and partially blind: the judge can only consume the pre-recorded trajectory — it cannot decide which intermediate states to re-examine, so evidence dilutes over long horizons — and the decisive evidence often lives in latent environment state that no screenshot shows (§1). Recent active-probing verifiers fix observability but over-probe while under-using the trajectory: ProRe reduces the trajectory to claims checked for consistency against probe results, paying multi-round interaction cost even when the trajectory already contains the answer (§2.2).

Contribution (what’s new)

Unify trajectory verification and environment interaction in one end-to-end verifier agent, ordered surface-to-latent and cheap-to-expensive with early stopping: read the trajectory first, probe the environment only when the trajectory cannot decide. The form is forced by the two baseline failures — passivity fails on latent state; unconditional probing wastes steps when trajectory evidence suffices. Feasibility rests on an explicitly measured “easy to verify, hard to solve” asymmetry: the same model verifying instead of acting reaches 83.1% vs 55.9% SR on OSWorld-Verified, in 17.4 vs 28.5 steps (Tab.1, p.2). A second delta: read-only test-time scaling — because verification is predominantly read operations, N serial verifications can share one environment instance with no snapshot restoration (§3.6.1).

Research questions

(1) Does trajectory-grounded escalation beat both passive judges and probing-first verifiers on accuracy and cost? (2) Do more accurate rewards translate into better GRPO training and Best-of-N inference for the actor? (3) Can verifier and actor be scaled at test time without environment resets?

Methodology

An LLM first consolidates the actor’s per-step reasoning into an operation summary H — keeping state observations and action descriptions, discarding sub-goal analysis so the verifier sees objective operations rather than possibly hallucinated intent (§3.3). The verifier agent (default Claude-Sonnet-4.5, max 30 steps) takes the task q, terminal screenshot s_n, and H, then works through three stages with early stop: static assessment (tool-free), visual retrospection (a check-screenshot tool over intermediate steps t < n), and proactive probing (execute-shell, execute-python, and a computer-use tool sharing the actor’s action space). It outputs a binary reward plus LOW/MEDIUM/HIGH confidence (§3.4–3.5). The staging is enforced by prompt protocol, not learned.

Method details and evaluation protocol
  1. Trajectory memory consolidation (§3.3) — A summarizer LLM maps each step's (reasoning, action) to a one-sentence operation, keeping only State Observation + Action Description and dropping Sub-goal Analysis — the actor's subjective plans, which for weak actors are hallucination-laden. Output H is the verifier's map of what was done.
  2. Stage 1 — Static Assessment — Tool-free judgment from (q, s_n, H). Output immediately if evidence is clear (immediate successes or obvious failures).
  3. Stage 2 — Visual Retrospection — If ambiguous, call check_screenshot on the most relevant intermediate steps indicated by H, accumulating indirect visual evidence; reassess sufficiency after each screenshot.
  4. Stage 3 — Proactive Probing — If still undecided (typically non-visual state changes), interact with the live environment: shell / Python reads preferred, direct GUI interaction last. The case study (App.F.3) shows it catching a false actor success-claim on a 'Do Not Disturb' task via gsettings show-banners=true. In AndroidWorld the shell/python tools are unavailable and excluded.
  5. Read-only verifier scaling (§3.6.1) — Restrict the verifier to read-only actions (enforced by prompt guidance + a secondary LLM check, App.A.3) so environment state stays invariant; run an odd number N of serial verifications on one instance and majority-vote.
  6. Reward-guided actor scaling (§3.6.2) — Best-of-N rejection sampling: prefer trajectories judged successful, tie-break by confidence; if ALL N are judged failures, submit a random one. App.D derives the closed form P_final(N) = (pa/alpha)(1 - beta^N) + p(1-a)beta^(N-1) with alpha = pa+(1-p)(1-a), beta = 1-alpha: reward-model accuracy a is the decisive factor, and a near 50% makes Best-of-N useless or harmful.
  7. Evaluation protocol (§4.1) — OSWorld-Verified (361 tasks, no Google Drive) + AndroidWorld. Actors: Claude-Sonnet-4.5 (SR 55.9%, class-balanced) and UI-TARS-1.5-7B (SR 22.4%, class-imbalanced), 50-step budget. All verifier methods share the Claude-Sonnet-4.5 backbone; ZeroGUI/FullTrajEval get the last 15 steps' screenshots (context limit). GT = benchmark scripts AND a dual-annotator human evaluation. Baselines: DigiRL, DistRL, WebRL, AndroidGen, ZeroGUI, FullTrajEval (ZeroGUI + full action history), ProRe.

Main result

Against human-evaluation ground truth on OSWorld-Verified, VAGEN reaches 94.6 F1 / 92.9 accuracy with the strong actor and 89.3 F1 / 93.4 accuracy with the weak actor — beating the best active baseline (ProRe) by 4.2 and 8.4 F1 points respectively, and every passive judge by more (Tab.2, p.8). Key findings

  • Verification is empirically easier than acting (Tab.1, p.2): the same Claude-Sonnet-4.5 gets 83.1% SR as verifier vs 55.9% as actor on OSWorld-Verified (93.1% vs 62.1% on AndroidWorld), in roughly 60% of the steps — the load-bearing feasibility claim for agentic verification.
  • Trajectory evidence alone nearly matches LLM-as-a-Judge at a fraction of the cost (Tab.4, p.10): ablating all interaction tools gives 82.8 F1 (vs ZeroGUI 81.5) with only 6.4 avg steps and 5.4 images / 532 tokens — because the agent selects which screenshots to inspect. The computer-use tool is the key interactive ingredient (removing it: 86.2 to 83.4 F1); shell/python are auxiliary efficiency tools (removing them costs little accuracy but raises steps 17.4 to 19.7 and images 11.9 to 18.7).
  • Memory consolidation matters mainly for weak actors (Tab.4, p.10): removing it costs 0.3 F1 with the Claude actor but 2.3 F1 with UI-TARS-1.5-7B, whose reasoning is hallucination-laden; consistently, FullTrajEval (which reads actor text) scores below ZeroGUI (screenshots only) in the imbalanced setting.
  • OSWorld-Verified’s own ground truth has false negatives but not false positives (App.A.2, Fig.7): a full audit of script-judged successes found zero false positives, while two annotators found 37 and 35 false negatives among script-judged failures (34 overlap, Jaccard 89.5%) caused by multi-path solutions (e.g. shell instead of GUI), incomplete answer whitelists, and ambiguous specs — this is why script-GT precision looks low (79.2) for VAGEN in Tab.2.
  • Reward quality propagates to RL (Fig.4, §4.3): GRPO on 6K AgentSynth tasks (16 rollouts/task) lifts UI-TARS-1.5-7B from 22.4% to 34.3% SR on OSWorld-Verified with VAGEN rewards, +3.8 over the strongest baseline (ProRe); all reward models improve over vanilla.
  • VAGEN scales and stays stable where judges degrade (Fig.5–6, Fig.8): it gains most from read-only majority-vote scaling (verification rarely needs writes even unrestricted), matches baselines’ Best-of-N=8 actor performance at N=5, and holds accuracy as actor step budgets grow while FullTrajEval declines. Backbone swaps (Gemini-3-Flash 85.3 F1, Doubao-Seed-1.8 82.1 vs Claude 86.2) barely move it (Tab.7).

Implications

Positions outcome reward modeling for GUI RLVR as an agentic-verification lineage — beyond passive ORMs (DigiRL, WebRL, ZeroGUI) and probing-first designs (ProRe’s reasoner–actor split, SmartSnap’s jointly-trained self-verification) — and shows the ordering of evidence sources (trajectory before environment, reads before writes) is itself worth points and tokens. The verifier-vs-actor asymmetry (Tab.1) and the read-only observation give general design levers for any harness that must certify final world state, TDE included. Their stated next step — deriving step-level rewards from outcome verdicts — and training a dedicated verifier model; whether the ad-hoc probe sequences could be compiled into persistent, environment-executed acceptance checks (the TDE move) instead of being re-derived and re-adjudicated by an LLM per trajectory.

Limitations

  • The final verdict is still an LLM judgment: probes return mechanical facts, but which probes to run and what they imply is decided by the verifier model; there is no executable pass/fail artifact. Author-stated: no iterative refinement loop, and outcome-level only — no step-level reward signals (App.E.1).
  • Read-only is enforced by prompt guidance plus a secondary LLM check, not a sandbox (App.A.3); the authors themselves recommend sandboxed deployment because the probing verifier executes shell/Python/GUI actions autonomously (App.E.3).
  • Human-eval GT is partially anchored to the scripts being critiqued: only script-judged failures were re-annotated, and annotator disagreements default to the script’s verdict (App.A.2).
  • Verification needs the live terminal environment: Stage 3 assumes the post-trajectory environment is still available, which in RL training means holding or restoring instances — the very cost that motivated read-only scaling; dollar/latency cost of a frontier-model verifier over 6K tasks x 16 rollouts is Not reported.
  • Mobile drops two of four tools (no shell/python in AndroidWorld), and scaling results (Fig.4–6) are figure-only — exact per-method curves are Not reported in text.

Critiques and Questions

  1. Self-preference is untested: the Claude-Sonnet-4.5 verifier judges Claude-Sonnet-4.5 actor trajectories in the class-balanced setting. The paper shows actor text sways judges (FullTrajEval below ZeroGUI), yet consolidated operations H still contain the actor’s own state-observation claims — the case study’s actor falsely claimed success in exactly that channel. How much residual actor bias survives consolidation?
  2. The 92.9% headline is against a GT that defers to the benchmark scripts on annotator disagreement, while the paper simultaneously argues those scripts are wrong on failures. A verifier that shares the annotators’ (or scripts’) blind spots would be flattered by this construction.
  3. Probing perturbs the environment: the verifier opens menus and popups (GUI actions in the case study) even in “read-only” mode. For serial N-sample scaling on one instance, transient-state drift between votes is assumed harmless but never measured.
  4. Efficiency is measured in steps/images/tokens relative to ProRe — but VAGEN still averages 17.4 frontier-model steps per verification, roughly 2.7x its own trajectory-only ablation. For large-scale RLVR, when is the +3.4 F1 over that ablation worth the interaction cost?
Why does VAGEN need Stage 3 (proactive probing) at all, when Stages 1-2 already see every screenshot of the trajectory?
Because of partial state observability: for many tasks the decisive evidence is in latent environment state — file attributes, application configurations, background processes — which no screenshot ever shows. Stage 3 queries that state directly (shell/Python reads or GUI interaction), e.g. the case study confirms a 'Do Not Disturb' failure by reading gsettings show-banners=true, which no trajectory frame could prove.

Personal notes

For the TDE novelty defense, this paper is the cleanest “agentic verifier” foil: environment-grounded evidence, LLM-adjudicated verdict, post-hoc reward (RLVR + Best-of-N), no gating — if all N rollouts are judged failures it still submits one, the opposite of red–green-until-pass. Two things to engage head-on: (1) its scalability argument against rule-based checkers is exactly the objection TDE answers by compiling checks at runtime instead of hand-writing them; (2) its App.A.2 audit is empirical ammunition that fixed acceptance scripts produce false negatives under multi-path solutions and format whitelists — TDE’s compiled suites must be robust to solution multiplicity (assert final-state properties, not paths). Also steal the Tab.1 asymmetry and the read-only-verification observation as supporting evidence for cheap mechanical final-state checking. Naming hazard: this “VAGEN” (verification framework, 2026) is unrelated to the 2025 VAGEN multi-turn VLM-agent RL framework — cite carefully.
