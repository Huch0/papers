Related concepts: Deterministic verifier design for interactive artifactsState-Contract VerificationModel-Based GUI Testing

We make the environment its own verifier: a coding agent builds each website from an LLM-written finite-state machine whose signature-space preconditions and effects make every breadth-first path correct by construction, a strict Playwright replay keeps only executable paths, and 16k steps from the resulting 11,663 trajectories (29 sites, $0.04 each) lift a GRPO-trained Qwen2.5-VL-7B to 27.42% on a 9-site WebVoyager subset, with a monotone data-scaling curve.

Model-based GUI testing run in reverse — the model generates the app, so the state contract is intrinsic — and the clearest evidence yet that contract-certified synthetic trajectories transfer to live sites. For state-contract verification: nothing compares site with FSM beyond selector executability; the contract never scores the policy online.

Motivation

The task we carry through this summary: in a synthesized workspace site, accept the cookie banner, open the bases list, sort it by most recent, open the filtered base, and save an automation that emails whenever a record is created — the bfs.json path printed in App. A.2.6 (its vocabulary matches Tab. 7’s Airtable theme). On the real product only rendered UI feedback is observable; whether the trigger was actually stored is internal state neither agent nor verifier sees (§1, p.1). So every real-site pipeline — exploration (Explorer, Fara), demonstration (Mind2Web), video mining — ends in an external verifier, a human or an LLM-as-a-judge, guessing internal state from screenshots: inconsistent across verifiers and $0.15–$1.00 per trajectory (§2.1, §4.5, Tab. 1). Synthetic environments with built-in checks exist as evaluation benchmarks; the few that also synthesize trajectories do not model a fully known transition structure (§2.2, p.3).

Contribution (what’s new)

Derive both site and data from one explicit transition system: an FSM whose preconditions and effects live only in signature space is compiled into a website by a coding agent and into trajectories by breadth-first search over (p,hash(σ))(p,\mathrm{hash}(\sigma))(p,hash(σ)), so paths are correct by construction and only executability remains to check. The form is forced: crawled sites hide transitions, so a judge must guess them; screenshot-level conditions would tie availability to rendering, so BFS could not enumerate; and with no judge to rescue partial paths, the executability filter must be strict.

Research questions

  1. Do trajectories certified only inside a synthetic FSM transfer to live-site navigation (WebVoyager, Online-Mind2Web) and to grounding (ScreenSpot-V2/Pro)?
  2. Does live-site success keep rising with synthetic volume at a fixed data mixture?
  3. Are the synthesized sites hard enough to serve as benchmarks?

Methodology

Four steps (Fig. 2), each on the running task. FSM. From a theme name a GPT-5.1 proposer drafts fsm.json — pages with default signatures, actions with $.-path preconditions and local-update effects, terminal pages — and a validator/improver loop re-checks reachability, $. paths and pagination resets (§4.1, App. A.1.6): an agent-as-a-verifier loop whose realism criterion is the same model’s judgment. In the A.3 schema our ACT_BASES_SORT assigns $.sort_by and resets $.pagination.page_index to 1, and ACT_BASES_OPEN_FILTERED_BASE is a navigation action that assigns $.selected_item_id. Site. Gemini3-Pro compiles the FSM into a Vue project and must implement every FSM selector in the DOM (§4.2–4.3). Search. BFS from the initial page expands only precondition-satisfied actions, deduplicates on the signature hash and returns the shortest path to any state with G(s)=1G(s)=1G(s)=1; our task is an 11-action path from ACT_HOME_ACCEPT_COOKIES to ACT_AUTOMATION_SAVE (App. A.2). Replay. Each action’s gui_procedure expands the path into 15 atomic operations (my count from App. A.2.6): click #cookie-accept, hover #topbar-workspace-menu then click .option-bases, …, open #bases-sort-dropdown, pick #bases-sort-recent-desc, …, click #save-automation-button. Playwright resolves each selector to a bounding box, clicks its centre and screenshots; if any selector fails to render or respond, the whole trajectory is dropped (§4.4). Survivors get a query from DeepSeek-V3.2 and, afterwards, per-step <think> traces from Gemini2.5-Flash — search needs no reasoning, so rationales are written only for survivors, and they dominate cost. Each step becomes a (screenshot, history, action, box) sample; GRPO on Qwen2.5-VL rewards action type, coordinate-in-box and format (App. D.4).

  1. 1 · FSM generation (GPT-5.1 proposer, validator, improver; §4.1, App. A.1) — fsm.json has four top-level blocks: meta (initial_page_id, terminal_pages, a complexity_profile used for generation statistics only), pages (per-page signature defaults and available actions), actions (preconditions, effects, is_navigation / to_page_id, gui_procedure) and nav_skeleton (a derived cross-page subgraph for reachability sanity checks, never a source of semantics). Signatures must be minimal (only variables that affect success or reachability) and stable (fixed names, defaults and serialization order, so hash(sigma) is reproducible). Every condition path starts with $. and must not depend on screenshot-level element existence. The validator's checks: (1) every terminal page reachable from the initial page; (2) preconditions reference only $. paths, no placeholders; (3) effects deterministic and local; (4) navigation targets well defined with same-name merge; (5) search/filter/sort actions reset pagination. The improver revises only the implicated pages/actions and the loop reruns until all checks pass. The A.3 skeleton's profile: 20-35 pages, 6-8 actions per page, 5 terminals, shortest paths of length 6-8, cookie and location interceptors switched on - the running example opens with accepting cookies and granting location.
  2. 2 · Site generation (Gemini3-Pro coding agent; §4.2) — Stage 1 writes guidelines: a style specification, a task checklist, an executable FSM runtime module and a mock data file (data.js is a Pinia store; App. B prints a health-app instance with providers, therapists, prescriptions, appointments, bills and plans, plus one feature-conditioned image per item). Stage 2 generates Vue page components in batches, pausing after a fixed number of pages to self-review the repository against the guidelines and update the to-do plan. Stage 3 builds and runs the project. Stage 4 feeds build logs and errors back to the agent until the build succeeds. The reference website name is only a style anchor, so several distinct sites can share a theme. Every selector assigned during FSM specification must appear in the rendered DOM; this shared selector namespace is the only bridge between FSM actions and pixels.
  3. 3 · BFS over the FSM (§4.3, App. A.2) — Start at s0 = (initial page, default signature). At each dequeued node enumerate the page's actions, keep those whose preconditions hold, apply effects (and Init/Carry for navigation) to obtain the unique successor, and dedupe on key(s) = (p, hash(sigma)); a node is expanded at most once per key. A depth cap L and optional per-page or per-goal node caps bound the enumeration. G(s) is checked on dequeue, so the first hit is the shortest path to that goal key. The paper's own illustration of ordering: Add to cart is expanded only after BFS has traversed and fixed the product's unit options (§1). Several distinct paths to the same goal (different queries, filters or navigation choices) may be kept for diversity, and negative trajectories can be minted by truncating before the goal or forcing a precondition-violating action, recorded as invalid (App. A.2.4).
  4. 4 · Playwright replay and strict filter (§4.3-4.4, App. A.1.4) — The BFS action sequence is expanded into the concatenation of its gui_procedures (running example: 11 actions, 15 atomic operations - 14 clicks and one hover). For each operation Playwright locates the selector, reads its bounding box, performs the operation at the box centre and records a screenshot; procedures use a normalized [0,1]^2 coordinate system with frame-consistency checks. A trajectory is kept only if every step executes; a selector that never renders or a control that does not respond discards the whole path. Kept trajectories carry the GUI-level operations, screenshots and bounding boxes, and the aligned FSM state sequence. Not checked: that the DOM state after an operation equals the FSM signature.
  5. 5 · Queries, thinking traces, grounding samples (§4.4, §5.1, App. B, Tab. 2) — DeepSeek-V3.2 writes the natural-language query from the complete path (a printed example from the Tumblr clone: 'From the blogs sorted by followers from most to least, get the sixth one and follow it', Fig. 6). Three query families: BFS-driven (name-based targets), visual-grounded (targets described through the per-item image) and screenshot QA (feature questions kept only if a VLM visibility check finds the feature on the screenshot); five interaction modes: search, scroll, slider, sort, checkbox. Gemini2.5-Flash then writes step-level thinking traces ($272.17 of the $447.37 total). One trajectory is sampled per set of parallel trajectories for the same task (1,215 of 11,663; 12,585 steps); individual steps are rewritten into grounding examples; the mixture is held at 2:8 grounding to navigation, about 16k steps in total.
  6. 6 · GRPO training and evaluation (App. D, §5.1) — Qwen2.5-VL-7B (and 3B) initialization on 8x A800: torchrun with 8 processes, max prompt 1024 tokens, per-device batch 4 x 8 gradient-accumulation steps x 8 GPUs = 256 samples per optimizer step, BF16, gradient checkpointing, FlashAttention-2, at most 12,845,056 pixels per image, 1 epoch, 8 rollouts per prompt, DeepSpeed ZeRO-3. Action space (Tab. 8): click, hover, drag, type text, press enter, scroll, hotkey, wait, answer, each a JSON dictionary. Evaluation: the agent sees the full textual history of its thoughts and actions but only the current screenshot; 15 actions per task; Gemini-3-Flash judges success from the instruction and the trace; the 9 most stable WebVoyager sites are kept and Online-Mind2Web likewise drops sites with frequent access restrictions; ScreenSpot-V2/Pro follow their original protocols; a 25-trajectory AutoWebWorld suite from the cloned Quora and GitHub sites tests UI-TARS-1.5-7B and Claude-4-Sonnet.

Main result

On the 9-site, 15-step WebVoyager subset Ours-7B reaches 27.42% overall, above UI-TARS-1.5-7B (26.51%), Claude-4.0-Sonnet (26.11%), GPT-5.1 (18.96%) and its own Qwen2.5-VL-7B base (5.62%) (Tab. 3, p.7); Ours-3B reaches 15.09% from 16K synthesized steps, above UI-Venus-7B (9.73%, roughly 1M SFT samples) and TongUI-7B (9.83%, about 350K RL samples) (Tab. 3, §5.2.1). What transfers is the step mapping learnt on paths like our 15-operation automation task — screenshot plus history to an action type and a point in the target box — on sites we never synthesized.

Key findings

  • Success rises monotonically with synthetic volume at a fixed 2:8 grounding-to-navigation mixture (Fig. 4, p.8): 8 → 256 → 1,024 → 16,253 samples give 3.92% → 17.59% → 19.09% → 27.42% on WebVoyager and 1.22% → 7.32% → 7.93% → 14.02% on Online-Mind2Web — four points, no repeats reported; the “polynomial fitting” that predicts further gains is extrapolation.
  • Grounding supervision cut from the same trajectories transfers (Tab. 4, Tab. 5, p.7): ScreenSpot-V2 61.87 → 65.88 (3B) and 84.83 → 86.16 (7B); ScreenSpot-Pro 13.3 → 18.0 and 23.2 → 27.5, driven by text targets (23.3 → 30.9; 39.8 → 46.1).
  • Grounding data is what makes the coordinate reward climb (Fig. 5, §5.4): without it the total reward is briefly higher (harder instances removed) but after roughly 25 steps the with-grounding run climbs faster and plateaus higher.
  • Reasoning, not environments, dominates cost (Tab. 2, Tab. 7, App. C): thinking traces cost $272.17 of $447.37, against $57.10 for FSMs, $52.26 for sites and $65.84 for queries; Skyscanner ($53.25) and Walmart ($37.92) carry the largest thinking bills.
  • The clones are not easier than the live web (Tab. 6, §5.5): on 25 tasks from cloned Quora and GitHub, UI-TARS-1.5-7B scores 20.00 and Claude-4-Sonnet 16.00, against 26.51 and 26.11 on WebVoyager.
  • Most of the 11,663 trajectories are parallel solutions of the same tasks (§5.1, Tab. 1, §4.5): one per task set leaves 1,215 distinct trajectories (12,585 steps), padded with grounding examples to about 16k steps; average horizon 21.94 steps against 6.9–12.1 in real-world corpora.

Implications

WebArena/BrowserGym evaluators and WebShop/World-of-Bits sites put the checker inside the environment, for evaluation only; InfiniteWeb and WebFactory couple site generation with trajectory synthesis without an explicit transition model; Explorer, AgentTrek, Fara and Mind2Web are the external-verifier corpora we undercut on cost (§2, Tab. 1). In state-contract verification terms fsm.json is a contract — precondition, effect, goal — used only to mint data. Differential testing of site against FSM: after each replayed operation read the DOM state and assert it equals σt\sigma_tσt​, turning executability into conformance. Mutation-hardened checks: break one effect or component on purpose and confirm the pipeline rejects the path. Use G(s)G(s)G(s) as the online GRPO reward instead of matching stored actions; the negative trajectories of App. A.2.4 are generated but unused.

Limitations

  • We never verify that a site obeys its FSM beyond selector executability: App. A.2.4’s “intrinsic verification” replays the FSM against itself, and the Playwright pass only asks that #bases-sort-recent-desc render and accept a click — a page that never re-sorts, or stores the wrong trigger, passes. We audited no FSM by hand; the validator’s realism check is GPT-5.1’s judgment.
  • The FSM reward is never used online: GRPO scores a rollout against the stored action and bounding box (Eq. 7–9); G(s)G(s)G(s) only gates dataset membership, and the environment never sees the policy.
  • Real-world evaluation is a 9-site, 15-step WebVoyager subset judged by Gemini-3-Flash, with no repeats, seeds or intervals reported; the 25-task check in Tab. 6 measures difficulty, not verifier validity.
  • Effective data is smaller and dearer than the headline: 1,215 distinct trajectories carry the signal, and we do not say where the $272.17 of <think> traces enter GRPO — Eq. 10 rewards only their format.

Critiques and Questions

  1. Contamination and aging. The FSMs are GPT-5.1’s recollection of named real products (Facebook, Gmail, p.2; Tab. 7); Coursera is both a training theme (751 trajectories, Tab. 7) and a WebVoyager test site (30.00%, Tab. 3), and Skyscanner (1300) mirrors Google Flights. Real-world verdicts then come from Gemini-3-Flash — the external judge the method exists to remove — on 9 sites kept because the rest now throw access-denied pages or CAPTCHAs; the “state-of-the-art” claim is not comparable with full-suite WebVoyager results.
  2. Bookkeeping. Tab. 7 lists 27 sites whose trajectory counts sum to 11,638 by my addition, while its total row says 29 sites and 11,663 (the cost columns do sum exactly); Tumblr (Fig. 6) is absent. Per distinct trajectory, $447.37 over 1,215 is about $0.37 — inside the $0.15–$1.00 band it is compared against.
  3. Gemini3-Pro scores 5.46% overall (Tab. 3), below the untrained Qwen2.5-VL-7B (5.62%), unexplained — and it built the sites. A harness or output-format failure is the likelier reading, weakening the “beats frontier models” framing; one success moves a site score 2–3 points (GF 2.44% is one success by my arithmetic).
  4. What does “verified” certify? Path and site are two LLM renderings of one spec, and #bases-grid .base-card-filtered shows the site is built so the path executes; a sort effect has no site-side consequence anything reads. Executability is a weak witness.
In the running example the generated site renders #bases-sort-recent-desc and accepts the click but leaves the bases grid unsorted. Does the trajectory survive the filter, and what does the FSM record?
It survives. The execution filter (§4.4) only requires every selector to resolve and every atomic operation to execute; the FSM-level replay (App. A.2.4) re-applies preconditions and effects in signature space, so $.sort_by becomes the recent-desc option and $.pagination.page_index resets to 1 whatever the DOM shows. Nothing compares rendered state with the signature — site-to-FSM conformance is the unverified link.
