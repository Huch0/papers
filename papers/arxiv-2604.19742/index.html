Related concepts: Agent-as-a-Verifier

A GUI program that runs without an exception can still be unplayable, so we make a vision-language agent (PlayTester) play the generated app, turn its verdict into a metric (Play@k) and a benchmark (PlayEval), and feed its diagnostics into a repair loop (PlayCoder) that doubles Python Play@3 on the same backbone, 9.9% to 20.3%.

If you build repair loops for interactive programs, Tab. 5 is the ablation you would otherwise run yourself: compile/run/unit-test feedback buys executability, only play-based feedback buys behavioral correctness — and an open-weight backbone (Qwen3-Coder) is among the best.

Motivation

Fig. 1 is why we built this. We asked GPT-4o-mini for a Flappy Bird. It runs without one runtime error — and the bird flies straight through the pipes, so the game never ends. Compilation success and unit tests cannot see this silent failure: nothing raises, and the broken property (“a collision must end the game”) is temporal, over pipes spawned at random coordinates, so there is no fixed input–output pair to assert on (§2.1); our source repos’ own tests cover only 47.2% of lines and 32.1% of branches (§3.1.3). Code benchmarks score GUI programs by tests alone, and GUI testers (Selenium, GPTDroid, LLMDroid, VETL) need a DOM or accessibility tree that canvas-rendered desktop apps such as Pygame games do not expose (§2.1). The best base model, Claude-Sonnet-4, drops from 18.6% Exec@3 to 9.9% Play@3 on Python (Tab. 2).

Contribution (what’s new)

The only oracle that can see a stateful, pixel-rendered logic bug is one that plays the app — so we make a vision-language agent the oracle, then reuse that same agent as the repair signal. Everything else is forced: Play@k sits strictly inside Pass@k so the syntactic-vs-behavioral gap is measurable (§3.1.4); PlayTester works from screenshots because canvas games expose no DOM (§2.1); PlayRefiner consumes screenshots-plus-actions instead of a fixed test suite because the Fig. 1 bug has no fixed input to assert on (§1).

Research questions

  • Preliminaries: is a VLM tester a reliable oracle (§3.5), and how far does playability fall below executability (§3.6)?
  • RQ-1: does closed-loop repair from visual, interactive feedback beat prompting and multi-agent baselines on the same backbone? RQ-2: at what token cost? RQ-3: which of APR, GUI feedback and context retrieval carries the gain? (§5)

Methodology

The task. One function to re-implement inside a checked-out repository, given signature, requirement docstring and repository context (Fig. 2) — for Flappy Bird the game loop or an event handler, since we keep only functions of at least 28 non-docstring lines (§3.1.1). Three nested gates follow (§3.4):

Definition — Exec@k, Pass@k, Play@k (PlayEval scoring rule)

With nnn samples per problem, csucceedc_{\text{succeed}}csucceed​ meeting the stage criterion:

[Exec,Pass,Play]@k:=Eproblems[1−(n−csucceedk)(nk)][\mathrm{Exec},\mathrm{Pass},\mathrm{Play}]@k := \mathbb{E}_{\text{problems}}\left[1 - \frac{\binom{n-c_{\text{succeed}}}{k}}{\binom{n}{k}}\right][Exec,Pass,Play]@k:=Eproblems​[1−(kn​)(kn−csucceed​​)​]

where Exec: no syntax, import or runtime error; Pass: Exec and all unit tests; Play: Pass and no PlayTester violation, plus hard constraints (“did the game crash?”) on logs and the final screenshot. So Play@k≤Pass@k≤Exec@k\mathrm{Play}@k \le \mathrm{Pass}@k \le \mathrm{Exec}@kPlay@k≤Pass@k≤Exec@k.

Playing Flappy Bird (§3.3). PlayTester launches the app, screenshots it one second after each action (three frames kept to detect motion), then writes a test strategy. Games get a goal-driven strategy (reach the terminal state; success and failure criteria), tool-like apps a coverage-driven one, since “winning” a text editor means nothing (§3.3.3). Then one action per step from click / type / hotkey / press / scroll / wait / finish: press to flap, screenshot, compare. Bird overlaps a pipe, no game-over: the failure criterion fires and finish(failure) ends the run. This is agent-as-a-verifier, not model-based GUI testing: only pixels, no widget tree.

Closing the loop (§4). PlayCoder runs generate → play-test → diagnose → patch → re-test. PlayDeveloper writes the function with grep-based repository retrieval; PlayRefiner folds compiler output, runtime logs and the behavioral report (screenshots, action trace, and the violation; for Fig. 1: “Collision detection error, APR required”, Fig. 4) into a typed failure summary and routes on it: compile errors to the Validator, undefined symbols to the ContextSearcher, wrong physics to a logic edit (§2.2, §4.3). The typing makes feedback actionable: a bare failed screenshot would send the refiner back to fixing imports while the bug is in the collision test. The loop stops when all checks pass or after T=6 rounds (§4.1.1), capped because each round is a full launch-and-play with a VLM call per step (testing is already ~22% of our tokens, §5.2) and an uncapped loop would void Tab. 4’s cost comparison; the cap is untuned (Not reported).

Method details

Benchmark construction (§3.1). Repositories: commits in the last 12 months at selection time, or at least 6 months of sustained history; mostly over 100 GitHub stars; complete GUI workflows; framework diversity (PyQt, PySide, Tkinter, Pygame). Categories (Tab. 1): Game Emulation (1 repo, PyBoy, 26,699 LOC), Classic Games (6 repos, 2,605 LOC: 2048, Snake, Flappy Bird, Sudoku, Chrome Dragon, Solitaire, Chess variants), Game Engine (1, Jupylet), Standalone Applications (24, 123,442 LOC), Desktop Widgets (9, 21,420 LOC), MMORPG (2 TypeScript games with over 1000 stars: CyberCodeOnline, biomes-game). Totals: 637 files, 188,432 LOC, 4,497 functions, 595 classes, 2,104 test cases; average cyclomatic complexity 10.2 per file, 30.4 control-flow structures per kLOC. Requirements: GPT-4o-mini docstrings generated from the original function body, about 10% verified by 3 developer experts, over 95.6% judged high quality by vote. Unit tests: the original repo tests (47.2% line / 32.1% branch coverage) plus an LLM-generated suite of unit, integration, functional and edge-case tests. Repository state is fixed with git checkout so PlayCoder sees the same context a human developer would. Fig. 2 lists 4,159 instances, 35 repositories, 578 classes and 2,072 test cases, which does not match Tab. 1.

PlayTester internals (§3.3). VisualObserver: pyautogui + PIL screenshots, region capture, window detection via AppleScript (macOS) and Win32; Windows, macOS and X11 Linux only — Wayland blocks cross-window capture and input injection. ActionExecutor: click(x, y), type(text), hotkey(keys), press(key), scroll(x, y, direction), wait(duration), finish(success/failure), with coordinate bounds checks, a failsafe cursor and an action history; actions are parsed from structured Thought: / Action: output. Test Manager: three prompt phases — GUI analysis (type, screen, UI elements with position/size/color/text/purpose, controls, objective), test-strategy formulation (primary objective, success criteria, failure criteria; launch, functionality and UI tests), action decision — with one template per phase except strategy, which has a game and a non-game template. Tests are reusable across consistent screen resolutions. Worked 2048 trace (Fig. 3): the observer reads r3c1=2, r3c4=2, r4c4=4, score=8; the planner chooses a rightward swipe because it both advances a corner strategy (merging into a 4 at r3c4) and exercises swipe responsiveness, merge logic and score update in one move, while watching for invalid moves, freezes and wrong termination.

Evaluator validation (§3.5). 100 PlayTester successes and 100 failures, randomly selected and shown in random order to 3 engineers with over 5 years of GUI experience, human judgment as ground truth: 16% false-negative rate, 5% false-positive rate, Krippendorff’s α = 0.790, Kendall’s τ-b = 0.795.

PlayCoder agents (§4.2–4.3).

  1. PlayDeveloper: context-aware generation — Tool-based agent with ContextSearchTool (grep-based retrieval of code examples and import patterns), FileReadTool, BashTool, ConversationTool; few-shot requirement→code prompting.
  2. Behavioral testing — PlayTester runs the app and records screenshots, actions, violations, compiler and runtime logs into an AgentTrajectory log; execution is sandboxed with deterministic seeding and controlled timing.
  3. PlayRefiner: diagnosis and repair — Three tools — ContextSearcher, Validator (syntax/AST, fast compile gate), Executor (sandboxed run). Five phases: diagnosis into an actionable failure summary; minimal patch proposal guided by retrieved context; atomic patch application; build and runtime validation followed by behavioral re-evaluation; iterate.
  4. Stop — Terminate early once all per-sample behavioral checks pass, otherwise after T=6 iterations.

Baselines and statistical protocol (§3.2, §5). Ten base LLMs: GPT-5, GPT-5-mini, GPT-4o, GPT-4o-mini, Claude-Sonnet-4, Claude-Sonnet-3.7, Grok-3-mini (closed); Qwen3-Coder 480B, GLM-4.5 355B, DeepSeek-V3 671B (open). Five enhanced methods run with their official configuration on three shared backbones (GPT-5-mini, Claude-Sonnet-3.7, Qwen3-Coder). Every number is a mean over 5 runs, each with a distinct fixed seed, temperature 0.3, identical prompts, tools and database state reset before each run; 95% CIs from the Student’s t-distribution. Ablation rows (Tab. 5): full, no-APR, no-GUI, no-APR-no-GUI (context only), no-agent. Note that the abstract’s headline pair — 38.1% Exec@3 (Qwen3-Coder, Tab. 3) and 20.3% Play@3 (Claude-Sonnet-4, Tab. 6) — comes from two different backbones, not one run.

Case studies (§5.4). Success: MetaGPT’s 2048 drew white digits on a white background; unit tests passed, the game was unplayable, PlayTester flagged the absence of visible change, and the rendering was repaired. Failure: bugs that need high-frequency feedback (only above 60 FPS) or long-duration survival (a crash after 2 minutes of Flappy Bird) defeat all methods; 4 of 43 projects, concentrated in fast arcade games (Flappy Bird, Snake) and real-time physics.

Main result

Same backbone, roughly double the behavioral correctness of the strongest baseline: GPT-5-mini: PlayCoder 26.8% Exec@3 / 9.8% Play@3 (Python) vs DeepCode 17.9% / 6.4% (Tab.3); Qwen3-Coder: 38.1% / 18.9% vs 37.6% / 9.8% (Tab.3); DeepCode already matches us on executability there, so the whole gain is behavioral: Flappy Birds that end when the bird hits a pipe. Best overall is Claude-Sonnet-4: 36.8% / 20.3% on Python, 44.5% / 24.6% on JavaScript (Tab.6).

Key findings

  • GUI feedback buys playability; APR buys executability (Tab.5, §5.3): GPT-5-mini, Python: no GUI feedback leaves Exec@3 at 24.1% but drops Play@3 9.8% → 5.3%; no APR drops Exec@3 26.8% → 18.3% but Play@3 only to 7.9%. APR-only Play@3 sits at the no-agent 4.9%, and for Claude-Sonnet-3.7 falls below it (6.9% vs 7.6%): compile/run/test signals fix crashes, not a bird flying through pipes.
  • Stronger backbones lose more without APR (Tab.5): Claude-Sonnet-3.7 −14.1pp Python Exec@3 (35.6% → 21.5%). Context retrieval alone does nothing (Tab.5): context-only equals no-agent (14.3% Exec@3 / 4.9% Play@3 in both).
  • PlayCoder spends 164K tokens (5,480 per function) vs 128K bare and 252K for DeepCode, with the highest Efficiency@1 (1.51 vs 1.01 bare); testing is ~22% of tokens (Tab.4).
  • JavaScript ≥ Python > TypeScript for every model and method (Tab.2, Tab.6, §5.3) (Qwen3-Coder Exec@3: 31.0% TS vs 38.1% Py), which we attribute to the two MMORPG repos being TypeScript (§5.1). All 10 backbones improve; open-weight Qwen3-Coder is second only to Claude-Sonnet-4 on Python Play@3 (18.9% vs 20.3%) (Tab.2, Tab.6).
  • Bugs needing high-frequency or long-horizon observation (a glitch only above 60 FPS, a crash after two minutes of Flappy Bird) defeat every method including ours: 4 of 43 projects (about 9%) (§5.4).

Implications

Tab. 5 is the design rule for repair loops on interactive programs: compile/run/unit-test feedback moves executability; only an oracle that drives and watches the program moves playability. Lineage: Self-Refine / Self-Debug repair with textual feedback, crossed with LLM GUI testers and agentic coders such as DeepCode; closest sibling “You Don’t Know Until You Click” (Bian et al. 2025). PlayTester verdicts as a training reward — we only prompt, and a 16% miss rate looks tolerable for RL or rejection sampling. State-contract verification or instrumented state dumps as a second oracle for the ~9% that 1 Hz screenshots miss.

Limitations

  • We know Play@k rests on a VLM judge with 16% false-negative / 5% false-positive rates (§3.5), and the evaluator’s default backbone is Not reported — only that a Claude-Sonnet-3.7 swap moved Play@3 by 0.9–3.7% (§5.1).
  • We know 1 Hz polling misses frame-rate and long-horizon bugs (about 9% of projects, unsolvable by construction) and did not try faster capture (§5.4, §7).
  • Task construction is partly LLM-made: GPT-4o-mini requirements and tests, about 10% human-checked; one regenerated function per instance, so “playable” means the app still plays after one replacement; Fig. 2’s instance and repo counts disagree with Tab. 1 (§3.1).
  • We did not address contamination or aging: the Classic Games and PyBoy are famous public repos whose reference code is likely in training data, and PlayEval has no refresh policy although we cite LiveCodeBench for exactly that (§6.1); PlayTester also runs only on Windows, macOS and X11 (§3.3.1).

Critiques and Questions

  1. Contamination: famous games from public repos, with the requirement docstring generated from the reference body, so a memorizing model can pass Exec@k and Pass@k by recall. Base Play@3 near zero suggests recall does not buy playability, yet PlayEval cannot separate “recalls Flappy Bird” from “understands collision”; no decontamination or held-out split is reported, and nothing guards against aging: a fixed set of ten backbones, a 12-month-activity rule, no versioning.
  2. Oracle and feedback are the same agent: six rounds against PlayTester, then scoring with PlayTester, optimizes toward its blind spots, the LLM-as-a-judge bias §5.1 acknowledges. PlayCoder’s outputs were never human re-checked; planting known logic bugs (mutation-hardened checks) would show whether the 16% miss rate concentrates on the physics bugs the loop targets.
  3. Fairness is partial: baselines ran in their official configuration (§3) without a GUI oracle, so Tab. 3 shows what a play-tester adds, not what DeepCode would do with one; token cost is matched only for GPT-5-mini (Tab. 4), and “164K tokens for 30 functions” suggests a subset, so the Efficiency@k basis is Unclear. What the six rounds actually change (violation and patch taxonomy, gain per iteration) is Not reported.
The Flappy Bird of Fig. 1 clears Exec@k and can clear Pass@k. Which gate rejects it, what evidence does PlayTester hand back, and what does PlayRefiner do with it?
Play@k. PlayTester launches the game under the goal-driven strategy, issues press actions to flap, screenshots one second after each, and when the bird overlaps a pipe with no game-over the failure criterion fires and the run ends with finish(failure). The report is screenshots plus the action trace plus a typed violation — 'Collision detection error, APR required' (Fig. 4). PlayRefiner aggregates that with compiler and runtime logs, routes a behavioral failure to a logic edit rather than to the Validator or ContextSearcher, patches, re-runs the play-test, and repeats until the checks pass or T=6 rounds are spent. Tab. 5 shows why the visual signal is essential: without GUI feedback GPT-5-mini keeps 24.1% Exec@3 but Play@3 falls from 9.8% to 5.3%.
