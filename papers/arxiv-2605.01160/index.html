Curated byChiyeong Heo

A 67-source multivocal literature review (2022–2026) that names the Productivity-Reliability Paradox — AI coding assistants improve individual output metrics while system-level dependability degrades — and argues from Transaction Cost Economics that specification-driven governance via machine-verifiable executable contracts (GitHub Spec Kit, TDAD) is the rational resolution.

Theory-side scaffolding for TDE: the SGM’s core prescription — as AI autonomy raises behavioral uncertainty, specifications must move from ambiguous natural language to executable, machine-verifiable contracts that gate acceptance — is TDE’s specify-then-gate logic stated as economics rather than as a harness mechanism. The survey’s characterization is accurate: every gate in this paper operates on development-time code artifacts (test suites, mutation scores, CI constitutions) under SDLC governance; nothing evaluates environment/world state at agent runtime and there are no per-action pre/postconditions — precisely the gap TDE fills. It also hands TDE useful vocabulary: “circular validation” (AI-generated tests mirroring AI-generated code) names the de-circularization problem that environment-computed verification escapes, and “deterministic specifications governing non-deterministic generators” is a citable one-line rationale.

Motivation

The empirical record on AI coding assistants is flatly contradictory: controlled studies report 20–56% individual speedups, while the most rigorous RCT (METR) measures a 19% slowdown for experienced developers, and organization-scale telemetry shows PR volume up 98% with review time up 91% and flat delivery metrics (§1). The most comprehensive systematic review labels the code-quality evidence “unresolved” (Mohamed et al. 2025). Three gaps follow: no framework reconciles individual-level gains with system-level degradation; no taxonomy describes how established methodologies (TDD, BDD, DDD/DDT, Agile, Waterfall, DevOps) transform under AI integration — a gap named by two systematic reviews; and no economic theory explains why specification-driven development keeps re-emerging as the governance response to non-deterministic code generators (§2.4–2.5).

Contribution (what’s new)

Reframing the contradictory evidence as one systematic phenomenon — the PRP — dissolved by three moderating variables (task abstraction level, codebase maturity, developer experience) and amplified by two mechanisms (the code-review bottleneck and the context-window constraint) (§4). The first application of Transaction Cost Economics to governing AI code generators: the SGM derives from high asset specificity + high behavioral uncertainty + high frequency that machine-verifiable executable contracts — not NL prompts, not post-hoc review — are the optimal contractual form between human principal and AI agent (§6). Plus the AAMT 6-methodology × 3-tier taxonomy (§5) and an evaluation of Spec Kit and TDAD as SGM instantiations with a 4-month pilot (§7). Thesis: specification discipline, not model capability, is the binding constraint on AI-assisted software dependability.

Research questions

RQ1: Is the divergence between individual productivity gains and system-level reliability degradation systematic, and what moderating variables explain it? RQ2: How do six established methodologies transform under three tiers of AI integration (passive suggestion, active generation, autonomous agency), and is there a coherent taxonomy? RQ3: Can specification-driven governance, theorized through TCE and operationalized by Spec Kit and TDAD, resolve the paradox? (§1.1)

Methodology

A multivocal literature review: seven databases/sources searched Feb–Apr 2026; 312 candidates → 128 full-texts → 67 included, each placed in a four-tier evidence-quality scheme (Tier 1 peer-reviewed → Tier 4 grey), with tier flagged wherever it affects claim strength. Findings are organized through a dual lens — the SPACE productivity framework and Transaction Cost Economics — and the PRP/AAMT/SGM constructs are built by abductive synthesis. Supplemented by an illustrative 4-month before/after pilot of Spec Kit (3 full-stack web teams, 14 mid/senior engineers, one organization, no control group).

SGM model, governance mechanisms, decision guide, and pilot design

SGM propositions (§6.2). Treating each AI code generation as a principal–agent transaction: (P1) higher asset specificity (domain-/architecture-specific code) shifts optimal governance from post-hoc review toward specification-first; (P2) higher behavioral uncertainty (non-determinism, larger codebases) forces the specification from natural language to executable contract; (P3) higher frequency (51% of developers use AI daily) amortizes governance fixed costs, making heavy upfront specification rational. A candid qualification: Williamson assumes opportunistic agents; LLMs are not opportunistic, merely stochastic — the author argues the distinction is “functionally immaterial” for governance design.

Four mechanisms by constraint intensity (§6.3).

  1. Post-hoc review — Developer reviews AI output after generation — the default Tier-1 mode and the source of the verification tax behind the METR slowdown. Optimal only for boilerplate.
  2. Natural-language specification — NL requirements before generation. Narrows the solution space but stays ambiguous; a non-deterministic generator can interpret it differently across invocations.
  3. Executable contract — A machine-verifiable spec — tests (TDD/TDAD), formal contracts (VibeContract), Gherkin scenarios, structured spec documents (Spec Kit) — constrains generation and enables automated verification. SGM-optimal for most Tier 2/3 use.
  4. Constitutional governance — A meta-specification of non-negotiable principles (testing approach, architecture, security invariants) governing all generation — Spec Kit constitution, Auton Constraint Manifold. Most comprehensive, highest upfront cost.

Decision guide (§6.4). Governance level follows task scope × codebase context × failure consequence: self-contained + greenfield + cosmetic → post-hoc review; self-contained + mature + functional → NL spec + targeted tests; cross-cutting + functional → executable contract approved before generation; security/data-integrity (auth, payments, PII, credentials) → constitutional governance. Governance intensity should vary per task within a sprint, not be uniform.

Instantiations (§7.1–7.3). Spec Kit (GitHub, Sept 2025, MIT, v0.8.x): /speckit.constitution → /speckit.specify → /speckit.plan → /speckit.analyze → /speckit.tasks → /speckit.implement; tool-agnostic, specs committed to the repo; reported (not independently validated) compression of upstream artifact production from ~12 hours to ~15 minutes of human steering. TDAD (Rehan 2026): NL behavioral spec → a coding agent (Claude Code in Docker) generates a pytest suite → a second agent iteratively refines the agent prompt until tests pass → mutation testing validates the suite itself. Comparative: Spec Kit has breadth (feature-level SDLC) but no automated check of spec completeness; TDAD has formal verifiability (mutation) but narrow scope (agent prompt quality). Optimal per SGM: layer them.

Pilot design (§7.4). Within-subject before/after at team level: 2-month baseline (NL tickets, opportunistic AI use) then 2-month intervention (constitution defined; medium/high-impact changes must pass the Spec Kit pipeline). Fourteen engineers (8 mid-level 3–5 yrs, 6 senior 6+ yrs; juniors deliberately excluded), three projects (React/Node B2B SaaS, Vue/NestJS consumer app, React + Go/Python internal tools). Metrics from Git/CI/issue trackers plus interviews and Likert questionnaires; explicitly framed as indicative, with temporal confounds (improving models) conceded.

Main result

There is no single new experiment; the headline is the reconciliation itself. The same class of tooling yields a 55.8% speedup in a greenfield RCT (Peng et al., N=95) and a 19% slowdown on mature OSS repositories (METR: 16 devs, 246 tasks, who had forecast a 24% speedup) (Tab.1–2, p.8–9), and at organizational scale, +21% tasks and +98% merged PRs coincide with +91% PR review time, +154% PR size, +9% bugs, and no measurable DORA-metric improvement (Faros AI, 10,000+ devs / 1,255 teams) (§4.2.6, p.11). The moderating variables predict which side of the paradox a given setting lands on.

Key findings

  • Three moderators dissolve the contradiction (§4.2.3, p.9–10): AI excels on low-abstraction, greenfield, junior-accessible tasks and degrades on high-abstraction brownfield work. The senior verification tax can exceed generation savings; juniors gain 30–40% speed but show skill-formation damage (Anthropic 2026: 17% lower comprehension when delegating code vs using AI for conceptual inquiry).
  • The code-review bottleneck is a Theory-of-Constraints failure (§4.2.6, p.11): generation is only ~25–35% of the SDLC, so accelerating it without scaling review just queues unreviewed PRs — individual gains are absorbed before reaching organizational metrics.
  • Specifications double as compressed, persistent context (§4.2.5, p.10–11): since 128K–200K-token windows cannot hold a non-trivial codebase, constitutions/specs re-included in every invocation compensate for the model’s finite memory — an engineering rationale for spec governance independent of the economic one.
  • TDAD’s executable contracts are themselves validated (§7.2, p.18): 86–100% mutation scores, 97% mean regression safety under spec evolution, 92%/58% (v1/v2) compilation success and 97%/78% hidden-test pass across 4 domains / 24 trials — mutation testing “tests the tests,” the paper’s concrete answer to circular validation.
  • The pilot moved every reliability indicator in the predicted direction (Tab.4, p.20) at a cost of 45–90 min spec authoring per medium feature — but as indicative ranges, not controlled effects; the author states Spec Kit “did not eliminate the PRP, it shifted its locus” from late manual review to upstream specification work.
  • Economics compound the governance case (§8, p.22–23): per-token prices fell over 90% in ~3 years (a 600-fold cumulative decline per Du 2026) while agentic workflows multiply consumption ~7×; employment of 22–25-year-old developers fell ~20% since late 2022 (Stanford HAI 2026), creating a “skill pipeline problem” — AI automates exactly the tasks juniors learn on while degrading learning for those hired.

Implications

This is the umbrella theory paper for the specify-then-gate family: it explains in TCE terms — rather than by benchmark — why TDAD (Rehan 2026, arXiv:2603.08806), GitHub Spec Kit, Auton’s Constraint Manifold (Cao et al. 2026), and VibeContract (Wang 2026) all converge on machine-verifiable contracts, and it roots the lineage in Hoare’s 1969 axiomatic semantics and Meyer’s design-by-contract. For TDE: constitutional governance is the paper’s nearest analogue to invariant pre/postconditions, but it is enforced at CI/review time over code artifacts, never at agent-action time over environment state — a contrast worth citing verbatim in the novelty defense. Read TDAD itself as the mechanically closest relative in this corpus: it compiles NL specs into executable test gates with mutation-validated suites. The SGM propositions are explicitly testable (governance intensity should track asset specificity, uncertainty, frequency) — a ready framing for a TDE ablation: vary task risk and measure when runtime acceptance suites pay for themselves.

Limitations

  • A synthesis/position paper: it contributes no new controlled evidence, and the PRP is assembled from studies whose “productivity” constructs differ (author’s own §10.3 construct-validity threat).
  • Single-reviewer MLR — screening and tier-coding were not independently replicated (no inter-rater reliability) (§10.6).
  • The pilot is retrospective and uncontrolled: 14 engineers, one organization, range-valued metrics, conceded temporal confounds, juniors excluded — so it demonstrates deployability, not effect sizes, and says nothing about skill-atrophy interaction (§7.4.5).
  • Load-bearing numbers ride on vendor/grey sources: DZone’s 4.3-minute verification tax, Faros telemetry, GitClear churn, and an unpublished Anthropic study “reported via InfoQ.”
  • Spec Kit and TDAD outcomes are the tool authors’ own reports, not independently reproduced; Spec Kit is v0.8.x with no academic evaluation (§7.1, acknowledged).

Critiques and Questions

  1. No study in the corpus measures individual productivity and system reliability simultaneously under controlled conditions, so the “paradox” is a cross-study composition claim; the same moderators that dissolve it also make it hard to falsify — almost any outcome can be attributed to abstraction/maturity/experience after the fact.
  2. The TCE transplant concedes LLMs lack opportunism and asserts that substituting “stochastic unreliability” is functionally immaterial — asserted, not demonstrated; whether Williamson’s hierarchy predictions survive the substitution is left to future work while the model’s conclusions already depend on it.
  3. Table 4’s tidy improvements invite citation as effect sizes despite the disclaimers; a developer-visible intervention with no control group is a recipe for expectation effects.
  4. Tier-3 autonomous deployment safety is delegated to constitution constraints (“never deploy without passing integration tests”) whose enforcement mechanism is unspecified — who or what evaluates compliance, and when? The paper’s design space stops at CI gates over code; environment-evaluated runtime gating (TDE’s move) is absent.
  5. The SGM never operationalizes its variables — no procedure measures a team’s “asset specificity” or “behavioral uncertainty” — so the decision guide’s thresholds are judgment calls dressed as derivations.
According to the SGM, why must specifications shift from natural language to executable contracts as AI autonomy increases?
Rising autonomy raises behavioral uncertainty: natural language is ambiguous, and a non-deterministic generator can interpret the same prompt differently across invocations, so NL under-constrains behavior. A machine-verifiable contract (tests, Gherkin scenarios, structured specs) constrains generation ex ante and enables automated verification — and because invocation frequency is high, the fixed cost of authoring it is amortized (Propositions 2 and 3, §6.2).

Personal notes

For the TDE related-work section, this is the category-I umbrella: cite it for the economic argument that executable contracts dominate NL specs under high behavioral uncertainty, then draw the contrast on one axis — it gates code artifacts at development/CI time; TDE gates final environment state at agent runtime with per-action pre/postconditions. Phrases worth reusing: “deterministic specifications governing non-deterministic generators,” “circular validation” (AI-generated tests mirroring AI-generated code — the de-circularization problem), and the concession that constitution enforcement is unspecified. The mechanism papers to engage directly are TDAD (arXiv:2603.08806), VibeContract (2603.15691), and Auton (2602.23720); this one supplies framing, not a competing mechanism.
