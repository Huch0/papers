Curated byChiyeong Heo

Verify an LLM-generated game not by playing it but by decomposing its specification into keypoints, injecting each precondition state directly into the running game, executing the bounded interaction, and judging the outcome; on 100 generated games this agrees with human verdicts 92.2% of the time versus 58.8% for a coverage-enforced agent-as-a-verifier, in 16.6× less wall-clock time.

The first head-to-head showing that state-grounded verification beats AI play-testing on both accuracy and cost for generated interactive software — the empirical bet behind a contract-based checker — together with the engineering it takes (a real orchestration harness) and the limits (a VLM still judges most outcomes; white-box access is required).

Motivation

Code generation got its flywheel from tests: a benchmark, a data filter, and an RL reward all fall out of a reliable pass/fail signal. Games have no such signal — correctness is defined over long-horizon interaction, and a game can build, render, and look right while violating its core mechanics (state updates, interaction rules, phase transitions). The closest existing answer, Agent-as-a-Verifier, collapses verification into open-ended gameplay: before checking a mechanic the agent must reach a state that exercises it, so verdicts are reachability-bound, coverage-limited, slow, and hostage to the agent’s own skill at playing (Fig.2). Our own baseline makes this concrete: an agent told to verify the spec directly stops after an easy subset and scores 0.011 accuracy; forcing it to cover every element takes over two hours per game and still reaches only 0.588 (Tab.1).

Contribution (what’s new)

Two observations carry the design. First, most specification failures surface at a sparse set of localized behaviors — collisions, reward settlement, state updates, rule triggers, phase transitions — so correctness can be cast as a finite set of local, bounded assertions rather than a global trajectory property (§4.1). Second, and this is the part that removes the reachability problem, a game is a data-driven state machine and the verifier has the generated source: it can read the parameter structure and construct the precondition state directly — spawn the boss, place the player, set the quest flag — by patching runtime state, instead of playing its way there (§4.2). Each keypoint becomes an independent verification unit, which is what makes the whole thing parallel. Verdicts are aggregated falsification-first: a failed keypoint is a witness against its specification element and propagates to dependent elements; what remains is marked PASS in the sense that no executed check exposed a violation. GGV-Harness supplies what a coding-agent session cannot — an explicit scheduler with concurrency limits, per-unit runtime isolation, retries, and checkpoints (§4.3).

Research questions

Does keypoint verification agree with human judgment better than agent play-testing, and at what cost? And does the harness itself matter for scalable, repeatable verification (§5)?

Methodology

  1. Extract keypoints — An LLM agent reads the specification and proposes triples (P, a, Q) under three constraints: P is directly constructible, a is a short finite action sequence, Q admits an operational PASS/FAIL (§4.1). A review-and-refine loop rejects ill-formed units (App.D).
  2. Ground into units — Using the generated source, the worker instantiates P as a concrete state patch (entities that exist, values they hold), a as an executable script, Q as an expected outcome; one keypoint may yield several units for boundary conditions.
  3. Build, inject, interact — Each unit launches an isolated game instance, injects the state through the JavaScript runtime, and runs the bounded interaction; build failures, failed injection after retries, and incomplete interactions all count as FAIL.
  4. Judge and aggregate — A vision-language model judges screenshots, logs, and exposed state against Q, supplemented by programmatic assertions when Q is a predicate over exposed state; FAILs propagate through the dependency structure to specification-level verdicts.
Dataset and setup

VeriGame: 100 popular App Store / Steam titles across seven genres, filtered by an LLM judge on textual reconstructability, rule determinism, mechanic diversity, and bounded complexity, then rewritten by GPT-5.4 with deep search into anonymized natural-language specifications and refined by humans (App.E). Games are generated by Claude Code (Opus 4.6, high effort). Verifiers run under three backends — Codex CLI (GPT-5.4 xhigh), Claude Code (Opus 4.6), Claude Code (Kimi 2.6 Coding) — five runs each. Baselines: AaaV-Direct (prompted to play and verify the whole spec) and AaaV-CE (the same agent inside a todo-list harness that forces a verdict for every specification element). Human reference: three expert evaluators play each game and mark violated elements; majority vote. Metrics at the specification-element level with PASS as the positive class; an agent’s UNVERIFIED counts as a non-agreement (App.A).

Main result

Under the Codex backend GameGen-Verifier reaches Acc@5 0.922 and F1@5 0.954 in 443 s per game, against 0.588 / 0.645 in 7,356 s for the coverage-enforced agent and 0.011 / 0.018 for the direct agent. (Tab.1) The pattern holds across backends.

Key findings

  • The agent baselines fail for two different reasons: AaaV-Direct stops after checking a small, easy subset (near-zero recall), while AaaV-CE, forced to cover everything, still cannot verify elements that need sustained gameplay, precise state reachability, or multi-step causal attribution — high precision (0.968), recall under 0.5. (Tab.1, §5.3)
  • GameGen-Verifier’s recall is 1.000 under Codex and Opus with precision 0.89–0.91: the falsification-oriented design means keypoint extraction may lose coverage, but an observed violation is strong evidence of a real failure. (Tab.1)
  • Time drops by up to 16.6× because units are local and bounded, so they run in parallel instead of as one long play session. (§5.3)
  • The harness is not optional: the same workflow inside a coding-agent session with subagents takes 1,293 s (Codex) and 1,594 s (Claude Code) versus 457 s and 536 s under GGV-Harness — a 66.4% reduction — and only the latter guarantees concurrency control, runtime isolation, and fault recovery. (Tab.2)
  • Web-stack games are the easy case for injection because their state is mutable JavaScript reachable through the browser runtime; Godot, Unity, and Unreal expose equivalent primitives (scene tree, GameObject/Component, Actor/Component) but their generation pipelines are too immature to evaluate. (§4.2, App.B)

Implications

If a checker can construct the state a rule needs, it never has to play; every rule becomes a cheap, parallel, deterministic unit — and this paper shows that trade wins on accuracy as well as cost. It sits beside the agent-as-a-verifier line (WebCompass, WebGen-Bench, UXAgent) it replaces, the runtime-monitoring tradition of game testing, and WorldCoder-Bench’s required state interface. Their injection contract — control what entities exist and what values they hold — is what a program-side setState / dispatch contract provides by construction, which would remove the white-box parameter-discovery step and let programmatic assertions replace the VLM judge for most outcomes; and their keypoint triples are a ready format for an agent-written checklist, with the same coverage gap (extraction is not guaranteed complete) that differential testing across candidates is meant to expose.

Limitations

Web-stack games only; keypoint extraction is not guaranteed complete; state construction needs white-box access to the implementation’s parameter structure; a PASS means no executed keypoint exposed a violation, not proven correctness (§6). Most verdicts are still produced by a vision-language judge over screenshots and logs; programmatic assertions are used only when the outcome is expressible over exposed state. All 100 games come from one generator (Claude Code, Opus 4.6); only wall-clock time is reported, not tokens or dollars; human raters judge from gameplay and could miss the same deep mechanics an agent misses.

Critiques and Questions

  1. The 16.6× speedup is against a baseline that is expensive by construction (it loops until every element has a verdict); the more honest cost comparison is against AaaV-Direct, which is faster but useless.
  2. AaaV-Direct’s near-zero accuracy is largely a coverage artifact of counting UNVERIFIED as disagreement (App.A); the interesting question — how often the agent is wrong when it does answer — is its precision, 0.67–0.81.
  3. The keypoints come from an LLM reading the spec, so the checklist can be silently incomplete in exactly the way the generated game can be; recall of 1.000 against human labels says humans and the extractor missed the same things, not that nothing was missed.
  4. Class balance of PASS/FAIL at the element level is not reported, so accuracy is hard to interpret on its own; F1 is the safer number.
Why does injecting the precondition state, rather than playing to it, change the complexity of verification?
Reaching a state through gameplay is a reachability search in an exponentially growing state space and depends on the agent's playing skill (Fig.2). Constructing it from the implementation's parameters is a configuration step, so each keypoint becomes an independent, bounded unit that can run in parallel and be retried in isolation (§4.2, §4.3).
