We verify an LLM-generated game without playing it: we decompose its specification into keypoints, inject each precondition state directly into the running game, execute the bounded interaction, judge the outcome, and aggregate falsification-first — on 100 generated games this agrees with human verdicts 92.2% of the time against 58.8% for a coverage-enforced play-testing agent, in 16.6× less wall-clock time.

The first head-to-head evidence that state-grounded checking beats agent-as-a-verifier play-testing on both accuracy and cost for generated interactive software — the empirical bet behind any state-contract verification checker — plus the harness it took and the parts that still rest on a vision-language judge.

Motivation

Code generation has a flywheel because it has a reliable pass/fail signal (§1). Games have no such signal: correctness is defined over long-horizon interaction, so a generated game can build, render, and look right while violating its state updates, interaction rules, or phase transitions. Our running example is the boss-phase rule of an action game: what must happen once the boss fight enters its second phase. To check that by playing, a verifier must find the arena, survive to the boss, and push the fight into phase 2 — a reachability search in an exponentially growing state space (Fig.2). That is where Agent-as-a-Verifier (AaaV) breaks: every mechanic must be reached before it can be checked, so verdicts are reachability-bound, coverage-limited, slow, hostage to the agent’s playing skill, and without a correctness oracle (Fig.2, §1). Concretely: AaaV-Direct stops after an easy subset and scores 0.011 accuracy; AaaV-CE costs 7,356 s per game and still reaches only 0.588 (Tab.1).

Contribution (what’s new)

Most specification failures surface at a sparse set of localized behaviors — collisions, reward settlement, state updates, rule triggers, phase transitions — so correctness can be cast as a finite set of local, bounded assertions rather than a global trajectory property (§4.1). Because we hold the generated source, the game is a data-driven state machine whose parameters we can read, so we construct the precondition state directly — spawn the boss, place the player, set the quest flag — instead of playing to it (§4.2). Each assertion is then an independent, parallel unit.

Research questions

Does keypoint verification with state injection agree with human judgment better than agent play-testing, and at what wall-clock cost (§5.3)? Does the execution harness matter, or can a coding-agent session with subagents run the same workflow (§5.4)?

Methodology

Intuition: a keypoint is a unit test whose fixture is a game state, and we set the fixture by patching the running game, not by playing.

Definition — Verifiable keypoint (§4.1)

A verifiable keypoint is a natural-language Hoare-style triple

φ=(P,  a,  Q)\varphi = (P,\; a,\; Q)φ=(P,a,Q)

where PPP is a precondition over game states, aaa is a bounded interaction sequence (the command CCC of a Hoare triple {P} C {Q}\{P\}\,C\,\{Q\}{P}C{Q} specialised to game input), and QQQ is the expected postcondition, subject to (C1) constructibility: PPP describes a directly constructible game state; (C2) boundedness: aaa is a finite, short action sequence; (C3) verifiability: QQQ is unambiguous enough to admit an operational PASS/FAIL verdict.

Definition — Verification unit (§4.1, Fig.3)

The runtime grounding of a keypoint against one implementation is

uk=(sk,  ik,  yk)u_k = (s_k,\; i_k,\; y_k)uk​=(sk​,ik​,yk​)

where sks_ksk​ is an injectable runtime state instantiating PPP from the implementation’s parameter structure, iki_kik​ is an executable instruction grounding aaa, and yky_kyk​ is the concrete expected outcome operationalising QQQ. One keypoint may ground into several units for distinct boundary conditions. A unit is FAIL if the game fails to build or launch, fails to realise sks_ksk​ after retries, fails to complete iki_kik​, or behaves inconsistently with yky_kyk​; otherwise PASS.

The boss-phase keypoint through the pipeline (Fig.3):

  1. Extract — An LLM agent reads the specification and proposes (P, a, Q) triples under C1–C3 (§4.1). For the boss-phase rule, P is 'boss present in its arena, player nearby, quest advanced to the boss phase, combat in phase 2'; a is the short interaction the rule names; Q is the behavior the specification promises for phase 2. A review-and-refine loop sends back any unit whose state is not constructible, whose instruction is ambiguous, or whose outcome does not admit a clear PASS/FAIL (App.D).
  2. Ground into a unit — A worker reads the generated source and maps P onto the implementation's own parameters. For our web-stack example that is Listing 1 (App.B.1): add a BossEnemy entity at (500, 300) in the bossArena scene; set the player's position to (480, 350) and health to 100, push legendary_sword into the inventory; set the quest flag boss_phase to true, combat.bossPhase to 2, combat.timer to 0. The patch need not reproduce in-flight coroutines or animation frames — only logical equivalence with respect to P and Q, because Q is defined over observable behavior (§4.2).
  3. Build, launch, inject — The unit launches its own isolated game instance and applies the patch through the JavaScript runtime. The injection contract asks for exactly two capabilities: control what entities exist in the running scene, and control what values they hold (§4.2).
  4. Interact — The worker executes the bounded script i_k and collects evidence: screenshots, logs, and exposed runtime state (§4.1).
  5. Judge — A vision-language model judges the evidence against y_k, supplemented by programmatic assertions whenever y_k is a predicate over exposed state or logs (§4.1).
  6. Aggregate — A FAIL is a falsifying witness for the specification element it covers and propagates to downstream elements that depend on that behavior; whatever remains is PASS, meaning no executed keypoint exposed a violation, not that the game is proven correct (§4.1).

The judge step is the same LLM-as-a-judge reliance AaaV has, applied to a bounded, pre-positioned observation.

What breaks without each piece.

  • Without state injection, sks_ksk​ must be reached by play and we are back to reachability search — exactly where AaaV-CE fails (§4.2, §5.3).
  • Without bounded interactions (C2), units are not self-contained, cannot run in parallel or be retried in isolation, and the wall-clock advantage disappears (§4.1, §5.3).
  • Without white-box source access, there is no parameter structure to read and no way to construct sks_ksk​ (§4.2, §6).
  • Without falsification-first aggregation, an uncovered element has no verdict — the UNVERIFIED hole that sinks AaaV under our scoring — and PASS would claim a proof a finite, LLM-extracted keypoint set cannot give (§4.1, App.A).
  • Without GGV-Harness, the same workflow inside a coding-agent session takes 1,293–1,594 s instead of 457–536 s and loses runtime isolation and fault recovery (§4.3, Tab.2).
Harness, VeriGame construction, and evaluation protocol

GGV-Harness (§4.3). A natural implementation runs the whole workflow inside a Claude Code or Codex session: a parent agent with task-specific skills dispatches units to built-in subagents and merges the results. We found that substrate fragile: subagent mechanisms give limited parallel scheduling, no explicit concurrency control, and no guaranteed isolation or recovery. GGV-Harness separates orchestration from local reasoning. The Python layer maintains the unit queue, enforces concurrency and rate limits, applies timeout and retry policies, persists checkpoints, and aggregates verdicts. The worker layer is a short-lived LLM agent call scoped to one unit — constructing the injectable state, generating the interaction script, or judging evidence — invoked statelessly and returning structured evidence plus a verdict. Each worker launches its own game instance, so random seeds, timers, browser-level singletons, and mutated game globals cannot leak between units; failed or timed-out units are retried without invalidating the rest of the run.

VeriGame (§5.1, App.E). We source popular titles from the Apple App Store and Steam across seven genres (Action, Adventure, Casual, Puzzle, Simulation, Strategy, Board), filter by popularity and rating, then score each candidate with an LLM judge (GPT-5.4) on a 1–5 scale for textual reconstructability, rule determinism, mechanic diversity, and bounded complexity, keeping games scoring at least 3 on every rubric; the curated set is 100 games. GPT-5.4 with deep search then writes a structured specification (objective, controls, entities, rules, scoring, progression, failure conditions, major mechanics) from public information, abstracting away assets and UI. Human annotators refine each specification for accuracy, completeness, consistency, and evaluability.

Contamination (App.E, p.20). We knew the selected games are popular titles likely present in training corpora, so we anonymize: each game gets an identifier such as Game-042, and every reference to the original name is removed; generation and evaluation see only the identifier and the specification. This protects against the model being told the title. It does not protect against the model recognising the game from a faithful description of its mechanics, and we ran no memorization probe.

Setup (§5.2, §5.3). Games are web-stack (JavaScript, TypeScript, HTML), generated by Claude Code v2.1.72 (Opus 4.6, high effort). Verifiers run under three backends — Codex CLI v0.125.0 (GPT-5.4 xhigh), Claude Code v2.1.72 (Opus 4.6, high effort), Claude Code v2.1.72 (Kimi 2.6 Coding) — five runs per game per method. In GameGen-Verifier the backend is the GGV-Harness worker; AaaV-Direct uses the same backend with the prompt in App.C (empty system prompt); AaaV-CE wraps it in a todo-list harness whose judge forces continuation until every element has a verdict or the retry budget is exhausted. The harness study (§5.4) runs the identical workload — same games, keypoints, retry budget, timeout — under Codex and Claude Code (Opus 4.6).

Human reference (§5.3). Three expert evaluators independently play each generated game and mark the specification elements it fails; the label is the majority vote. Inter-rater agreement: Not reported. Number of specification elements per game and keypoints per game: Not reported.

Main result

Under the Codex backend we reach Acc@5 0.922 and F1@5 0.954 in 443 s per game, against 0.588 / 0.645 in 7,356 s for AaaV-CE and 0.011 / 0.018 in 387 s for AaaV-Direct. Key findings

  • The baselines fail differently: AaaV-Direct stops after a small, easy subset (recall 0.009–0.021); AaaV-CE is precise (0.923–0.968) but cannot verify elements needing sustained gameplay, precise state reachability, or multi-step causal attribution (recall 0.475–0.522). (Tab.1, §5.3)
  • Our recall is 1.000 under Codex and Opus 4.6 (0.962 under Kimi 2.6) with precision 0.892–0.912: the falsification-oriented design means extraction can lose coverage, but an observed keypoint violation is strong evidence of a real failure. (Tab.1, §5.3)
  • Wall-clock time falls by up to 16.6× (443 s vs 7,356 s) because bounded units run in parallel rather than as one long play session. (Tab.1, §5.3)
  • The harness is not optional: the same workflow inside a coding-agent session with subagents takes 1,293 s (Codex) and 1,594 s (Claude Code) versus 457 s and 536 s under GGV-Harness — up to 66.4% less — and only GGV-Harness guarantees concurrency control, runtime isolation, and fault recovery. (Tab.2, §5.4)
  • Web-stack games are the easy injection target because state is mutable JavaScript reachable through the browser runtime; Godot, Unity, and Unreal expose the same two primitives behind their object models, but their generation pipelines are too immature to evaluate. (§4.2, App.B)

Implications

A checker that can construct the state a rule needs never has to play; every rule becomes a cheap, parallel unit, and the trade wins on accuracy as well as cost. We sit beside the AaaV line we replace (WebCompass, WebGen-Bench, UXAgent), the runtime and model-based monitoring tradition of game testing, and the development-time checks of Godogen and OpenGame — none of which construct states (§2). Our injection contract — control which entities exist and what values they hold — is what a program-side setState / dispatch contract provides by construction; a checker built on it skips parameter discovery and can use programmatic assertions instead of a VLM judge for most outcomes. The (P, a, Q) triple is a ready format for agent-written checklist rules, with the same gap — extraction is not guaranteed complete — that differential testing across candidates and mutation-hardened checks (does the set catch a deliberately broken boss-phase rule?) expose. As early evidence for the state-contract framing, quote 0.922 vs 0.588 Acc@5 and 16.6× (Tab.1).

Limitations

We know the scope is narrow: web-stack games only, no validation on Godot, Unity, or Unreal; keypoint extraction is not guaranteed complete; state construction needs white-box access to the parameter structure; and a PASS means no executed keypoint exposed a violation, not proven correctness (§6). We did not report what a reader needs to trust Acc@5 as more than a mean: no variance across the five runs, no inter-rater agreement for the three raters, no PASS/FAIL class balance, no count of specification elements or keypoints per game (Tab.1, §5.3 — Not reported). Most verdicts still come from a vision-language judge over screenshots and logs; programmatic assertions apply only when the outcome is expressible over exposed state, and we did not measure judge error separately from extraction or injection error (§4.1). Everything is pinned to one moment: one generator (Claude Code v2.1.72, Opus 4.6) for all 100 games; backends Codex CLI v0.125.0 (GPT-5.4 xhigh) and Claude Code v2.1.72 (Opus 4.6, Kimi 2.6); specifications written by GPT-5.4, our strongest backend (§5.2, §5.3, App.E). The numbers will age with those versions; we report wall-clock only, not tokens or dollars.

Critiques and Questions

  1. The 16.6× is against a baseline expensive by construction — AaaV-CE loops until every element has a verdict. AaaV-Direct matches on time (387 s vs 443 s) but is useless; the untested middle is a play-tester on a 443 s budget (Tab.1).
  2. AaaV-Direct’s near-zero accuracy is largely a scoring artifact: UNVERIFIED counts as non-agreement (App.A); when it does answer, its precision is 0.667–0.812. Likewise, recall of 1.000 says raters and extractor missed the same elements — raters also judge from play (§5.3), so the reference shares the reachability blind spot the method escapes.
  3. Contamination is mitigated, not removed. Anonymizing titles (App.E, p.20) hides the name, but a specification of a popular title’s mechanics, written by GPT-5.4 from public information, is recognisable to GPT-5.4 and the other backends; an extractor recalling the original could propose keypoints from memory rather than from the specification, and agree with raters who know the game for the same reason. No memorization probe is reported.
  4. PASS/FAIL class balance is not reported, so 0.922 accuracy is hard to read alone; F1 is the safer number, and the per-run spread behind the @5 is unknown.
For the boss-phase keypoint, what do P, a, and Q become in a verification unit, and why does grounding P as a state patch change the cost of verification?
P becomes s_k, the Listing 1 patch: a BossEnemy at (500, 300) in bossArena, the player at (480, 350) with health 100 and legendary_sword, quest flag boss_phase true, combat.bossPhase 2, timer 0. a becomes the executable script i_k; Q becomes the expected outcome y_k judged from screenshots, logs, and exposed state. Reaching that state by play is a reachability search over an exponentially growing state space (Fig.2); constructing it from the source is a configuration step, so the unit is independent, bounded, retryable, and runs in parallel with every other unit (§4.2, §4.3).
