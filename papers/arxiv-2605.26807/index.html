We judge LLM-generated HTML only after a browser has used it and treat the trace as a control state that decides whether a page is rewritten, patched or preserved and whether each re-executed candidate survives; repairing rather than filtering turns 13,786 usable seeds into 63,703 cleared pages and trains a 27B model to 50.6 on HTMLBench-400 and 81.2 on MiniAppBench-Val.

An execution trace, not a screenshot, routes repair and gates training data — the shape of a verify-then-repair harness, and a worked case of boxing in an LLM-as-a-judge.

Motivation

Take the base defense game of Fig. 9. Its first screenshot looks like a game — canvas, HUD, protected zone — but the trace reads “playable loop is incomplete: controls, obstacle checks, and score state are not verified”. In our 97K-prompt corpus only about 15% of Kimi-K2.5 pages are directly usable under the browser gate; the rest fail through inert controls, stalled game logic, broken responsive layouts, or missing content (§1) — failures the single-step screenshot judge of Eq. 1 (a visual model over sampled frames) cannot see, since they appear only after hover, click, scroll, resize, or gameplay. Filtering discards such pages unexamined — 91,484 traced pages shrink to 13,786 High ones (Tab. 5) — and a prompt fed only source or a screenshot cannot choose between rewrite, patch and leave-alone. WebArena, MiniAppBench, WebGen-Bench and FullFront already execute pages; none use the trace as a repair state.

Contribution (what’s new)

The browser trace is a control state, not a score: its band — Low, Mid, High at 40 and 80 — plus a diagnosis fixes which edit family is admissible (rewrite, diagnose-and-patch, preserve), and a candidate replaces the checkpoint or reaches the SFT export only after a fresh execution passes a regression-penalized composite. Forced by Tab. 7: rewrite is the best action below 40 (+14.2) and a 17.0%-catastrophe action from 80 up (−2.7), so one prompt cannot serve both; our 46-point game is Mid and the diagnosis chooses.

Research questions

  1. Does executing a page — viewports, probes, a gameplay rollout — expose failures a screenshot judge misses, with the VLM boxed to visual design?
  2. Does the observed state decide which repair family is useful and which is dangerous?
  3. Does repairing weak pages beat filtering as SFT supervision at natural and matched sizes, and transfer to an external benchmark?

Methodology

Experience. A static pass reads the file; Layers 1–2 render it, change viewports, census the buttons, scan the keyboard, hover; because that evidence says “game”, Layer 3 runs a short task-driven rollout and Layer 4 keeps 8–12 annotated keyframes (Fig. 2, §2.2) — model-based GUI testing with a fixed protocol. Judge. An Analyst VLM sees keyframes and probe results and only describes — observations plus a requirement checklist; a Scorer sees no screenshots and scores from that JSON and the objective metrics (§2.3, D.6.2). Route. The game scores 46: Mid. The diagnosis lists the unverified controls, obstacle checks and score state; a fixed rule controller opens the Mid operator set. Repair and verify. Round 1 is a structural rebuild (+9.5), round 2 game mechanics, round 3 an interaction fix, then visual polish, feature completion and a final bug fix; each round asks for at most two candidates, re-executes them, keeps one only if ScompS_{\mathrm{comp}}Scomp​ beats the checkpoint, and feeds a contrastive keyframe report into the next prompt. The loop runs all eight rounds — 89.9 never reaches the 97 early stop — and exports the best verified checkpoint (Fig. 9).

What breaks without each part: without execution the inert controls are invisible (Eq. 1 vs Eq. 2); without executed keyframes the VLM grades a page that never ran, and without the Analyst/Scorer split and the 20-point cap it could overrule the probes; without bands one prompt rewrites High pages at 17.0% catastrophe or patches Low pages with no stable target (Tab. 7); without ScompS_{\mathrm{comp}}Scomp​ from a fresh run a visual gain hides a broken click handler; without repair the gate keeps 13,786 of 91,484 pages (Tab. 5).

Evaluator, controller, and repair diagnostics
  1. Static pass (§2.4, Tab.14) — Extract the HTML; reject malformed, truncated or trivial pages; record code-quality evidence (size, canvas, script, CSS, SVG, requestAnimationFrame, input types, external resources, static issues).
  2. Layers 1–2: observe and interact (§2.2) — Load, watch motion, change device views, scroll below the fold, press prominent controls, hover, scan keyboard bindings, trigger scroll behaviour. Runs on every page that survives the static pass. Outputs: render success, console errors and JS exceptions, button census (responsive/tested), confirmed responsive keys, latency, frame differences.
  3. Layer 3: deep gameplay (conditional) — Only when early evidence indicates deeper interactivity: a short task-driven rollout so game states, counters, canvas changes and multi-step UI transitions stay visible. An optional browser-use tester agent (D.6.2) follows a task-specific protocol — activate entry points, exercise every mentioned feature, complete one full workflow, report bugs — the agent-as-a-verifier slot of the pipeline.
  4. Layer 4: keyframes — 8–12 annotated keyframes selected from the same run with event context (Fig.2). Mid pages receive an extra diagnostic branch because routing is hardest in that band (§2.4).
  5. Analyst → Scorer (§2.3, D.6.2) — Analyst (sees screenshots and probes, does not score): factual observation, template-like versus distinctive design signals, working/broken lists, and a prompt-grounded requirement audit with done / broken / missing statuses; rule: identical frames after an interaction mean the interaction is broken. Scorer (no screenshots, deterministic decoding): evidence only; broken items penalise more than missing; unresponsive buttons, keyboard failure, gameplay with no state change or timed-out actions cap interaction; reusable templates do not get top visual scores; guardrails clamp scores when probes contradict the text report. Fast mode skips the VLM for regression checks; leaderboard rows use full mode.
  6. Diagnosis D(h) (Tab.15) — Score state (total, five components, band, distance to the 97 target); failed test-case ids, assertion messages, missing requirements, pass-rate change; runtime state (render, console, exceptions, overlays, FPS or frozen motion, responsive failures); interaction state (buttons, keyboard, forms, hover, drag, gameplay changes, latency); visual state (Analyst notes, mobile and desktop keyframes, contrastive feedback); history (strategies tried, accepted and rejected candidates, best checkpoint, preservation list).
  7. Repair prompts (D.6.3) — One template for every strategy: task, current scores, previous attempts, probe evidence, Analyst evidence, requirement checklist, preservation list, current HTML, plus a strategy-specific block. Patch mode returns JSON old_str/new_str patches; rewrite mode returns the full file. Game pages get a probe-driven prompt naming the failing layer — input (canvas not focusable, listeners on the wrong element, missing preventDefault for arrow keys, key state not read in the loop), loop (requestAnimationFrame never called, loop waits for a click, update or draw throws), canvas (zero size, getContext before DOM ready, clearRect without redraw, overlay hides the canvas), overlay (game-over visible on load, start screen cannot be dismissed), or gameplay logic (collision, scoring, state machine, timer, physics).
  8. Contrastive visual feedback (§3.2, D.6.3) — After a candidate is re-run, a VLM compares paired BEFORE/AFTER keyframes at the same interaction state and returns improved / regressed / unchanged lists plus one priority fix, injected into the next prompt next to the deterministic evidence. High pages can additionally get a visual-only diagnosis and a verification call that must return functional_regression = false.

Operator binding inside a set (§3.3): console or probe failures activate bug fixing; broken key or mouse bindings activate playability repair; stable logic with weak presentation activates visual enrichment; game repair is used when the interactive scaffold is worth preserving; in High, verification without editing is a valid controller output. Family profile (Fig. 7): rewrite returns +9.7 with 92% success, 100% safety and 49% support; interaction fix +11.2, 95%, 100%, 9%; other targeted fixes +7.3, 92%, 100%, 42%. Ranked by lift the strategies read fix interaction, fix playability, holistic rewrite, fix game, bug fix, feature complete, visual enrichment — the valuable actions are interaction, playability and rewrite, not polish. State transitions (Tab. 8, within-row percentages): Low → Low 1.8% (278), Mid 44.2% (6,932), High 54.0% (8,476); Mid → Mid 17.9% (11,129), High 82.1% (50,883; Tab. 5 lists 50,881 exports for the same band); High → High 100.0% (13,786). Stopping (Fig. 8, as extracted): Low pages locate their best checkpoint late (R2 23%, 3.5K; R8 16%, 2.5K), Mid pages early (R1 15%, 9.5K; R2 25%, 15.3K), High pages often at input (28%, 3.9K). Retained mean score over rounds (Fig. 5, as extracted): 58.9, 68.5, 79.8, 82.4, with a marked +2.5 gap between peak and current candidate.

Task construction (§4, D.4, Tab. 12–14). 400 frozen items with category, subtype, difficulty (122 easy, 156 medium, 122 hard), prompt, has_interaction (338 true), weighted test cases and ordered browser steps; the six families are collapsed from ten source buckets (apps, UI pages, games, data visualization, creative pages, SVG art, 3D/WebGL, content pages, landing pages, portfolios). Each scored test case is a deterministic browser program — click, type, hover, key press, resize, screenshot-change check, JavaScript assertion, visibility check; the runner executes 16,120 steps over the 6,000 cases. Rules: prompt-grounded and browser-observable; no selectors, class names, frameworks, hidden DOM assumptions, credentials, payments or private services. Functionality is the weighted pass rate over the frozen pool; the files pass a strict schema validator and a quality audit for duplicate evidence, shallow visual checks and cross-template leftovers. Models receive only the prompt under a minimal system instruction (single self-contained HTML, no prose), with a UI-only demo retry suffix for provider safety blocks (D.6.1). Who wrote the test cases, and whether they were reviewed: Not reported.

Contamination control (Tab. 13). An exact normalized prompt match between the 400 benchmark prompts and the 91,484 traced repair records finds zero overlaps. The controller is not trained on HTMLBench (D.5). Nothing beyond exact matching is checked.

Main result

Under one backbone and recipe, Refined beats Raw and Filtered at every scale: HTMLCure-27B-Refined reaches 50.6 on HTMLBench-400 with 45.2% TC pass, above Kimi-K2.6 (49.8 / 43.7) and GPT-5.4 (49.2 / 42.7), and 81.2 on MiniAppBench-Val against 65.9 for 27B-Raw (Tab.4). Key findings

  • The useful action flips with state (Tab.7): Low, holistic rewrite +14.2 (90.0% success, 0.6% catastrophe, n = 35,822); Mid, interaction fix +11.3 (95.4%) over rewrite +8.3 (n = 324,880); High, targeted fix −0.2 at 0.0% success, rewrite −2.7 at 17.0% catastrophe (n = 232,128).
  • Repair, not selection, fills the pool (Tab.5, Tab.8): 54.0% of Low traces (8,476) and 82.1% of Mid traces (50,881) export and Mid supplies 79.9% of the 63,703 pages, yet 68.5% of original High pages (9,440) are rejected at export although 100.0% stay High.
  • Quality survives matched size (Tab.6): at 12,392 examples per route, 27B Refined 49.9 / 43.7 TC pass / 75.1 MiniApp vs Filtered 48.2 / 41.0 / 71.8 and Raw 45.0 / 41.2 / 62.5; at 9B Refined leads HTMLBench (47.5 vs 45.1) but MiniApp ties (55.1 vs 55.2).
  • Filtering raises the total but lowers the deterministic slice at every scale (Tab.4): Raw → Filtered TC pass falls 39.5 → 37.5 (4B), 41.4 → 40.3 (9B), 42.6 → 40.8 (27B); Refined restores 40.9 / 42.1 / 45.2.
  • Export the best verified checkpoint, not the last edit (Fig.3, Fig.5, Fig.8): the retained mean rises 58.9 → 82.4 while the current candidate lags the peak; 28% (3.9K) of High pages are best at input, Low pages still peak in round 8 (16%, 2.5K).

Implications

The transferable pattern: probes decide, the judge describes, the scorer never sees pixels — agent-as-a-verifier with the agent boxed to observation; the frozen prompt-grounded test cases are state-contract verification (a post-interaction state, never a selector). Self-Refine, Self-Debugging, CodeRL, DesignBench and VIBEPASS repair or diagnose from feedback; here the state also gates admissible edits and export. Learn routing and stopping from the 592,830 logged attempts (§8); generate deterministic tests for the corpus so the training gate matches the benchmark gate; explain why Interactivity is at floor for every model.

Limitations

  • We know the evaluator is validated only by construction: no human agreement, fault injection, or correlation with user judgment for the Analyst/Scorer path or the probes; Interactivity sits between 0.9 and 1.4 of 10 for every row of Tab. 4.
  • We know the same evaluator gates the training data and scores HTMLBench-400: the corpus has no frozen test cases, so band and export rest on the Scorer reading the Analyst’s requirement checklist (D.6.2), an LLM judgment whose corpus-side profile we did not report; on the one independent check, MiniAppBench-Val, Refined (81.2) trails GPT-5.4 (87.7), Kimi-K2.6 (85.5) and Qwen3.6-27B (84.3).
  • We did not report who wrote the 6,000 test cases or how they were validated: Tab. 13 gives rules, not authorship, review or agreement; every number is one temperature-0 run without variance; closed rows are provider versions at evaluation time.
  • We know the loop is hand-tuned and single-source: 40 / 80 / 97 thresholds, unreported regression weights and patience rule, an unnamed repair LLM and judge VLM, one generator (Kimi-K2.5), single-file HTML only, probes that cannot cover every interaction (§8).

Critiques and Questions

  1. Contamination is an exact normalized prompt match (zero of 400 against 91,484 traces, Tab. 13) — it rules out reuse, not preference: Refined is what the evaluator scored at or above 80, and the same Analyst/Scorer supplies HTMLBench’s visual points, so part of the 48.1 → 50.6 step over Filtered is learning the judge; the deterministic 40.8 → 45.2 is cleaner evidence. The MiniAppBench “+15.3” is against a Raw route (65.9) that sits below the Qwen3.5-27B row (76.5).
  2. Which VLM judges and which LLM repairs? Neither is named (“Provider API”, Tab. 9), so the 20 visual points and the whole funnel are irreproducible; and the Scorer prompt returns all five dimensions plus a total (D.6.2) while §2.3 says only visual design goes through the VLM — the reconciling clamp is described, never quantified.
  3. The game’s per-round increments (+9.5, +2.2, +1.3, +0.6, +0.6, +0.9, +1.0, +0.1) are far from its +43.9 verified lift, so what the card numbers denote is Unclear; why 9,440 High pages are rejected at export is never stated. Aging: 16 open-weight and 6 closed rows, single-run, open rows 41.7 to 49.8, best total 50.6 of 100 — unsaturated, but discrimination lives almost only in the functionality slice and drifts with provider versions.
The base defense game scores 46 on its first execution. What may the controller do, what may it not do, and why is the exported page the round-8 checkpoint rather than the last edit?
46 is Mid (40–79): the admissible set is Ω_Mid — Rewrite, BugFix, PlayabilityRepair, InteractionTargetedFix, GameRepair, VisualEnrichment — and the diagnosis (unverified controls, obstacle checks, score state) sends round 1 to a structural rebuild, then game and interaction repair; NoOpVerify and pure polish are High-only. Every candidate is re-executed and kept only if S_comp beats the checkpoint, so the export is the best verified checkpoint, not the newest edit (Fig. 5B: the current candidate can lag the peak); all eight rounds ran because 89.9 never reached the 97 early stop.
