We compile each web-generation task into an ICG and score a generated page by how many requirement-induced transitions it executes correctly in a live browser, not by how it looks; across 442 tasks and 14 MLLMs the best model, GPT-5.5, passes only 65.6% of transitions.

The most direct execution-grounded oracle yet for “does the interactive component actually work”, with user-stated and product-level requirements scored separately; the ICG + adaptive agent + dual oracle is the verifier loop a synthesis or repair system would want.

Motivation

Ask an MLLM for a shopping-cart page (checkboxes, price breakdown, Proceed-to-Checkout button). It returns one HTML file whose checkbox toggles on click; is the page usable? In our Fig.7 case one artifact accepts the uncheck on the only checked item, yet Checked Subtotal stays at ¥398 and checkout stays enabled. A page can render every expected control and still be broken: the click “works” while the dependent state does not follow. Earlier benchmarks (ArtifactsBench’s MLLM checklists, FrontendBench’s scripts, WebGen-Bench’s checkpoints, IWR-Bench’s video trajectories) made interaction observable but judge it through local evidence (§1): event-centric checks confirm that an action produced a response but never enumerate which requirement-induced states and transitions must be covered, and a local check passes while the page violates cross-component or cross-step constraints (filter–pagination sync, draft preservation across navigation). Selector-based scripts fail any correct page with unexpected markup. And no prior benchmark separates explicit requirements from implicit requirements (Tab.1).

Contribution (what’s new)

We treat a task’s requirement set as inducing a finite, observable state machine and grade a page by conformance to that machine under browser execution. Each task compiles into an ICG whose states are described behaviorally, whose transitions are user goals, and whose assertions trace to a named requirement. For the cart, “uncheck the last item” is one transition; its checks (checkout disabled, totals zero) map to the implicit requirement “dependent totals synchronize”. That mapping turns a stale total into an attributable, requirement-level defect instead of a local miss.

Research questions

  1. Graded by requirement-induced state-transition conformance instead of local action success, how far are current MLLMs from usable web artifacts?
  2. Which input modality best conveys interactive behavior, and does visual fidelity track behavioral correctness?
  3. Are implicit, product-level constraints a distinct bottleneck, and does ICG scoring catch state defects that checkpoint-style evaluation misses?

Methodology

We follow the cart transition through Alg.1, saying at each design point what breaks without it; background: state-contract verification, model-based GUI testing.

Definition — Interaction Contract Graph and transition (Eq. 3–4)
Gτ=(Sτ, Tτ, Φτ, Mτ)G_\tau = (S_\tau,\ T_\tau,\ \Phi_\tau,\ M_\tau)Gτ​=(Sτ​, Tτ​, Φτ​, Mτ​)

SτS_\tauSτ​ are stable, replayable UI states; TτT_\tauTτ​ user-intent transitions; Φτ\Phi_\tauΦτ​ observable DOM/visual predicates; MτM_\tauMτ​ the coverage mapping from requirements to test items, transitions, and assertions. Each transition tjt_jtj​ (Eq. 4) bundles a source and target state, a natural-language goal, preconditions, DOM assertions, and visual postconditions.

For the cart (Fig.7): source state “one item checked, totals shown”; goal “uncheck the only checked item”; DOM assertion [AFTER] the Proceed-to-Checkout entry is in a disabled state; visual postcondition “checked subtotal is zero and dependent values reflect no checked items”.

States are behavioral, not DOM snapshots, otherwise the contract would match one implementation and a cart built from styled divs would fail for the wrong reason (§3.2).

Transitions are goals executed by an adaptive agent, because a selector script for “uncheck the item” dies on different markup. The agent reads an indexed DOM observation, sees something like [7] <input type=checkbox checked>, and emits Uncheck [7]; indices are regenerated after every action (§4.2, Fig.18), the agent-as-a-verifier pattern.

Transients live on transitions, not in states, or the graph explodes: spinners and debounce become [CHANGE] assertions, while [AFTER] assertions and visual postconditions check the settled outcome (§3.2).

Two oracles, judged conservatively. After a settle delay we freeze the DOM event log and screenshot; GPT-5-mini as an LLM-as-a-judge scores the DOM assertion from the log and the postcondition from the screenshots, and UNCERTAIN never passes (§B.2, §C.1), otherwise ambiguous localization would inflate scores.

Replay, and SKIPPED instead of FAIL. Outcomes are PASS/FAIL/BLOCKED/SKIPPED. Source states are restored by replaying previously passed trajectories; if that fails the transition is SKIPPED (Alg.1 l.3–6), otherwise one upstream bug is charged once per downstream transition.

The mapping M makes results attributable. On the failing cart page both judges return NO (checkout-btn ... disabled:false; subtotal still ¥398): the transition is FAIL, and through MτM_\tauMτ​ the implicit requirement “dependent totals synchronize” is unsatisfied while the explicit “user can uncheck items” still passes. Without M we would know that something failed, not which requirement.

Method details: construction, modalities, execution loop, metrics, Overall, reliability

Contract construction (§3.3, four steps). (1) Anonymous industry practitioners fill our collection templates with domain-grounded requirements, interaction goals, and data assumptions; tasks span 8 domains and 35 scenarios (Fig.3; Productivity Tools 23.76%, Social Interaction 16.97%). (2) We normalize the material into explicit and implicit requirement sets RτR_\tauRτ​. (3) An LLM derives a Test Data Contract (Fig.15; rule 5 forbids leaking implicit requirements into the spec the model sees) and implementation-neutral test items (Fig.16). (4) ICG compilation (Fig.17): stable configurations become states, behaviors become transitions with [CHANGE]/[AFTER] DOM assertions and unprefixed visual postconditions; preconditions only on T1; independent features fan out from a shared source state; compound transitions chain 2–3 operations only to test state interference. We validate every ICG with a ground-truth HTML page generated from the full requirement set and keep a task only if GT page, ICG, and evaluator form a stable executable loop (§3.4). The GT page also supplies the Image/Video specs but is not a reference implementation (§3.1).

Modalities (Tab.6). Text = scenario + explicit requirements + Test Data Contract; Markdown = Text + symbolic layout regions; Sketch = content-stripped wireframe; Image = high-fidelity screenshot with visually inferable explicit requirements removed from the text; Video = interaction demonstration rendered from a validated ICG transition chain. Same task, same contract: 2,210 task–modality instances, 2,276 explicit and 2,995 implicit requirements, 12.4 transitions and 11.9 requirement checks per task on average (Tab.5).

  1. Restore source state — Replay the cache Π of previously passed trajectories to reach s_from. Failure ⇒ SKIPPED (not FAIL), so one upstream bug is not double-counted (Alg.1 l.3–6).
  2. Check preconditions — Capture the pre screenshot; any failed precondition ⇒ FAIL with evidence (Alg.1 l.7–10).
  3. Agent executes the goal — Indexed DOM observation (tag, role, text, value/checked/expanded/disabled/pointer-events, slider values, scroll, selection ranges; custom ARIA/tabindex/contenteditable widgets included; new elements marked via cross-step diffing, §B.1). One action per step from the Fig.18 grammar (Click, Input, Check/Uncheck, Drag, DragRange, SelectText, Upload, LongPress, ClickAt, …) within budget K. Exhausting K ⇒ BLOCKED.
  4. Dual oracle — Wait Δ, capture the post screenshot, freeze the DOM event log. GPT-5-mini judges DOM assertions from the log ([CHANGE] = held at some point; [AFTER] = holds in the final state) and visual postconditions from before/after screenshots. Verdicts YES/NO/UNCERTAIN; only YES passes (§B.2).
  5. Aggregate and record — PASS only if the source was reachable, the agent finished, and all required assertions are YES. On PASS the trajectory joins Π. An evidence bundle (trace, DOM log, snapshots, per-assertion verdicts, replay path) is stored per transition (§B.3).

Deterministic tie-breaks in the DOM judge (§B.2). Non-interactivity is checked as pointer-events: none, then native disabled/aria-disabled, then class tokens; selection as aria-selected/pressed/checked, then class tokens; ambiguous element localization returns UNCERTAIN rather than guessing.

Reliability checks (§A.3, §C.1). On 300 stratified interaction cases, requirement-to-ICG construction reaches 0.86 accuracy and κ=0.78 against the human majority and the functional evaluator 0.84 / κ=0.74, against human–human 0.88 / κ=0.81 (Tab.7). The visual evaluator reaches 0.81 / κ=0.69 versus human–human 0.85 / κ=0.77 (Tab.8). As transition judge, GPT-5-mini detects 95/100 GT-vs-defect pairs versus 97/100 for GPT-5.4 (Tab.10).

Main result

Interactive web generation is far from solved: GPT-5.5 reaches T=65.6 / R=66.3 in its best modality (Video), leaving about a third of transitions and requirement checks unsatisfied; the top Overall scores are GPT-5.5 69.1 and GPT-5.4 66.8 (Tab.2, §5.2). The passing cart artifact in Fig.7 is GPT-5.5’s. Open-weight models are competitive: Kimi-K2.6 reaches Overall 63.3 (T=63.7 on Video) and Qwen3.6-27B 62.5, above Claude Opus 4.7 (61.6) and Gemini 3.1 Pro (61.9) (Tab.2). Key findings

  • Visual quality is not a proxy for behavior (Tab.2, Tab.9, Tab.11): Qwen3.6-35B-A3B scores V=80.8 on Markdown with T=15.5; Sketch has the highest modality-average V (81.4) yet trails Image and Video on every interaction metric; model-average V spans only 68.7–80.6 while T spans 15.5–65.6.
  • Video is the strongest modality, and it specifically helps implicit behavior (Tab.11, §C.2): Video beats Text by 8.8 T, 8.3 R, and 10.6 Ri (53.6 vs 43.0), shrinking the explicit–implicit gap Δ=Re−Ri from 13.5 to 7.7; Image wins only on explicit coverage (Re=62.8), so the temporal channel is what transmits state changes.
  • Video’s advantage concentrates on hard tasks (Tab.13, Fig.8): on the Hard50 / Easy50 splits, Video beats Image by 4.9 T / 6.1 Ri / 4.8 R on Hard50 but only 1.6 / 1.7 / 1.4 on Easy50; Hard50 also shows more Availability (13.9% vs 6.0%) and Feedback-and-Boundary (21.6% vs 17.9%) failures.
  • Failures happen after the control exists (Fig.6, §5.3.5): for GPT-5.5 / Kimi-K2.6, State-and-Logic is 57.2% / 59.7% of failed transitions and Feedback-and-Boundary 24.6% / 23.5%, versus Availability 12.1% / 11.0% and Execution 6.2% / 5.8%; the stale ¥398 cart is the typical failure.
  • ICG scoring catches state corruption that checkpoint-style scoring passes (Tab.4, Tab.14, §C.5): on 25 defects injected into GT-validated pages ICG detects 16/25 (64.0%) versus 8/25 under a broad WebGen-Bench criterion and 1/25 under a strict one; the 13 ICG-only cases are long-range constraints such as record loss under repeated operations, cross-feature side effects, and draft loss across navigation.
  • Scaling has a knee (Fig.5, Tab.2): within Qwen3.5, Overall is flat from 27B (51.7) to 122B-A10B (51.1) and jumps at 397B-A17B (57.6), most under Text and Markdown where state logic must be inferred from thin specs.
Additional results: safety and robustness, state reachability

Safety and robustness are uniformly poor and not fixed by model strength or richer input (Tab.3, Tab.15–16, §5.3.1): GPT-5.5 passes 41.3% of checks and most models cluster at 25–32%, with flat rankings and small cross-modality variation. For GPT-5.5 the weakest rule families are async/interaction robustness (20.5%), DOM-rendering safety (25.5%), and request security (26.4%); missing input constraints pass only 2.9% of 2,956 checks and repeated-click guards 1.8% of 273 (Tab.15). State reachability S sits a few points above T everywhere (Tab.12) (GPT-5.5 Video S=68.4 vs T=65.6; Qwen3.6-35B-A3B Markdown S=20.0 vs T=15.5), so omitting S from Tab.2 does not change rankings.

Implications

Models mostly can expose the control (Availability plus Execution are under a fifth of failures) and cannot keep dependent state coherent: optimize state logic, not layout. The ICG is reusable as a reward or repair signal: implementation-agnostic, localized to a transition and requirement with an evidence bundle, and it keeps SKIPPED/BLOCKED apart from FAIL so a repair loop does not chase downstream symptoms. Per-transition verdicts as RL rewards or structured repair prompts is the obvious next step; we do not attempt it. A demonstration of the target behavior beats a screenshot as a spec for stateful components; rendering demos from a contract is a cheap data route. WebRISE sits downstream of WebGen-Bench, FrontendBench, ArtifactsBench, IWR-Bench, and WebVia; our defect injection is a small instance of mutation-hardened checks.

Limitations

  • Self-contained single-file HTML in a controlled browser: no back end, auth, external APIs, persistence, concurrency, or long sessions. We know we measure front-end conformance, not deployment readiness (Limitations §).
  • Coverage is bounded by what our LLM-generated test items and ICG enumerate; the 9/25 injected defects we missed show the evaluator is not yet exhaustive (§5.3.4, Tab.4).
  • Our judges are LLMs (GPT-5-mini, Gemini-3-Flash-Preview) and we ran one pass per model–task–modality with no variance or CIs; we know prompt sensitivity and API drift make the scores rank orderings (Ethics §), and several Overall gaps are under one point (62.5 vs 62.5 vs 61.9, Tab.2).
  • Contributors come primarily from one region, so “implicit” constraints encode regional conventions (Ethics §); we did not report generation prompts or decoding settings for the evaluated models; code and data come only upon acceptance (§E).
Benchmark checks: task construction, evaluator reliability, contamination, aging

Task construction. Raw materials come from anonymous practitioners; an LLM writes the Test Data Contract, test items, and ICG (Fig.15–17); a task survives only if a GT page generated from the full requirements passes the ICG (§3.3–3.4). We do not report how many tasks that loop discarded, nor which LLM authored the ICGs and GT pages. Construction quality: 0.86 accuracy / κ=0.78 against human majority on 300 post-filter cases (Tab.7).

Evaluator reliability. Functional evaluator 0.84 / κ=0.74 versus human–human 0.88 / κ=0.81 (Tab.7); visual evaluator κ=0.69 versus 0.77 (Tab.8); GPT-5-mini vs GPT-5.4 as judge 95 vs 97 of 100 GT/defect pairs (Tab.10). UNCERTAIN counts as fail (§B.4). Per-model BLOCKED and SKIPPED rates: Not reported.

Contamination. Training-data contamination is not discussed (Not reported). Tasks are freshly authored and unreleased at v1 (§E), which lowers the chance the tasks themselves sit in pretraining data. The sharper risk is spec-to-test leakage: the Image and Video specs are rendered from the GT page / a validated ICG transition chain (§3.1, Tab.6), so under those modalities the model sees the very transitions it is graded on. The judge GPT-5-mini shares a provider with two evaluated models; we do not discuss judge–model affinity.

Aging. Judge prompts are sensitive and API versions drift, so read scores as rank orderings (Ethics §). Gemini-3-Flash-Preview is a preview model; re-scoring later will not reproduce V exactly. We say we release judge prompts, configurations, and per-assertion verdicts (Ethics §), yet code and data are promised only upon acceptance (§E), so at v1 nothing is re-runnable. Single run, no CIs.

Critiques and Questions

  1. Circularity between ICG and GT page. A task survives only when an LLM-generated GT page passes the ICG (§3.4), which filters toward contracts an LLM can already satisfy, and the κ=0.78 construction agreement is measured on 300 post-filter cases (Tab.7). How many tasks were discarded?
  2. Video is rendered from the validated ICG chain (Tab.6), so it shows the model the transitions under test; the +10.6 Ri advantage (Tab.11) may partly be “the test was demonstrated”; a video covering only explicit transitions would separate the readings.
  3. Single runs, κ=0.74, 25 hand-picked defects. T% penalizes BLOCKED and SKIPPED like FAIL (§4.4), Overall mixes V in at one-third weight against the thesis (Eq. 10), the defect baseline re-implements WebGen-Bench’s criteria on 25 defects of undescribed selection (Tab.4); sub-one-point gaps in §5.2 are not rankings.
On the failing cart page of Fig.7 the DOM judge sees checkout-btn with disabled:false and the visual judge sees Checked Subtotal still at ¥398 after the last item is unchecked. What outcome does the transition get, which requirement is marked unsatisfied, and why is the explicit requirement not failed too?
Both assertions return NO, so the transition is FAIL (executable, but a required check is violated). Through the coverage mapping M the failed checks trace to the implicit requirement that dependent totals and checkout availability synchronize, which is marked unsatisfied. The explicit requirement 'the user can uncheck items' is verified by a different check (the checkbox state did change), so it still passes; that is what makes this a state-consistency error rather than a click-execution error (§4.4, §5.3.6).
