Curated byChiyeong Heo

WebRISE compiles each web-generation task into an Interaction Contract Graph (states, user-intent transitions, DOM/visual assertions) and scores a generated page by how many requirement-induced transitions it actually executes correctly in a browser, not by how it looks; across 442 tasks and 14 MLLMs the best model passes only 65.6% of transitions.

This is the most direct benchmark to date for the “does the interactive component actually work” question: an implementation-agnostic, execution-grounded oracle for stateful UI behavior, with explicit vs. implicit (product-level) requirements split out. Its ICG + adaptive-agent + dual-oracle loop is essentially the verifier one would want inside an execution-grounded synthesis/repair loop, and its results show open-weight models (Kimi-K2.6, Qwen3.6-27B) are competitive.

Motivation

I am given a spec (“build a shopping cart page: users can check items, totals update, checkout is disabled when nothing is checked”) and an MLLM hands me a single HTML file. When is that file usable? A page can render every expected control and still be broken: the filter runs but the list does not change, the cart checkbox toggles but the total and the checkout button stay stale (Fig.7). The interaction-aware benchmarks that exist (ArtifactsBench’s dynamic screenshots + MLLM checklists, FrontendBench’s scripts, WebGen-Bench’s navigation-agent checkpoints, IWR-Bench’s video trajectories) all made interaction observable, but they judge it through local evidence. Two things break as a consequence (§1): (i) event-centric evaluation verifies that an action produces a response but never enumerates which requirement-induced states and transitions must be covered; (ii) the state-consistency gap: a local check passes even when the page violates cross-component, cross-view, or cross-step constraints such as filter–pagination synchronization, count updates after deletion, or draft preservation across navigation. Scripts add a further problem: selector-based scripts only run against the implementation the script author had in mind, so a differently-structured but correct page fails. And nobody separated what the user said from what any competent product must also do (Tab.1: no prior benchmark has an implicit-requirement column).

Contribution (what’s new)

The insight is to treat a requirement set as inducing a finite, observable state machine, and to grade a page by conformance to that machine under browser execution. Concretely: each task’s requirements are compiled into an Interaction Contract Graph (ICG), where states are requirement-relevant UI configurations (not DOM snapshots), transitions are user goals (not click sequences), and every transition carries DOM and visual assertions traced back to a named requirement. The form is forced by the failures above. If states were DOM snapshots, the contract could only match one implementation, so states are described behaviorally and a contract-guided agent re-plans each transition on the live page from an indexed DOM observation whose indices are regenerated after every action: no fixed selectors survive. If transient effects (spinners, toasts, debounce) were states, the graph would explode and become unreplayable, so they are pushed into [CHANGE] DOM assertions on the transition, while [AFTER] assertions and visual postconditions check the settled outcome. If a broken upstream transition made every downstream one fail, one bug would be counted ten times, so source states are restored by replaying previously passed trajectories, and unreachable states yield SKIPPED rather than FAIL. And because the mapping M links every assertion to a requirement, the same run yields separate Re% (explicit) and Ri% (implicit) scores. The WebRISE benchmark itself is 442 expert-sourced tasks, each instantiated under five input modalities sharing one ICG.

Research questions

  1. If interaction is graded as requirement-induced state-transition conformance rather than local action success, how far are current MLLMs from usable web artifacts?
  2. Which input modality (Text, Markdown, Sketch, Image, Video) best conveys interactive behavior, and does visual fidelity track behavioral correctness?
  3. Are implicit, product-level constraints a distinct bottleneck from explicit functions?
  4. Does an ICG-based evaluator actually detect state defects that checkpoint-style evaluation misses?

Methodology

Running example (the paper’s Fig.7): a cart page with one checked item. Requirement: unchecking the last item zeroes the totals and disables checkout. The ICG has a state S_k (“one item checked, totals shown”), a transition “uncheck the only checked item” to S_k+1, a DOM assertion [AFTER] the Proceed-to-Checkout control is disabled, and a visual postcondition “checked subtotal shows zero and dependent values reflect no checked items”. The agent, seeing [7] <input type=checkbox checked>, issues Uncheck [7]; after a settle delay the DOM log and the pre/post screenshots go to two LLM judges. The failing page (Fig.7) returns checkout-btn ... disabled:false and a subtotal still at ¥398, so both assertions are NO, the transition is FAIL, and via M the implicit requirement “dependent totals synchronize” is marked unsatisfied, while the explicit “user can uncheck items” is still satisfied. That attribution is the whole point.

Method details: contract construction, execution loop, oracles, metrics

Contract construction (§3.3, four steps). (1) Anonymous industry practitioners fill collection templates with domain-grounded requirements, interaction goals, and data assumptions (8 domains, 35 scenarios, Fig.3; Productivity Tools 23.76%, Commerce 16.97%). (2) Requirements are normalized into explicit + implicit sets R_τ. (3) An LLM derives a Test Data Contract and implementation-neutral test items (prompts in Fig.15–16; rule 5 of the TDC prompt forbids leaking implicit requirements into the spec the model sees). (4) ICG compilation (Fig.17): stable configurations become states, behaviors become transitions with [CHANGE]/[AFTER] DOM assertions and unprefixed visual postconditions; preconditions are allowed only on T1; independent features fan out from a shared source state; compound transitions may chain 2–3 operations only to test state interference. Every ICG is validated by a ground-truth HTML page generated from the full requirement set: a task survives only if GT page, ICG, and evaluator form a stable executable loop (§3.4). The GT page also supplies the Image/Video specs but is not a reference implementation.

Modalities (Tab.6). Text = scenario + explicit requirements + TDC; Markdown = Text + symbolic layout regions; Sketch = low-fidelity wireframe with content stripped; Image = high-fidelity screenshot with visually-inferable explicit requirements removed from the text; Video = interaction demonstration rendered from a validated ICG transition chain. Same task, same contract, 2,210 task–modality instances.

  1. Restore source state — Replay the cache Π of previously passed trajectories to reach s_from. Failure ⇒ SKIPPED (not FAIL), so one upstream bug is not double-counted (Alg.1 l.3–6).
  2. Check preconditions — Capture the pre screenshot; any failed precondition ⇒ FAIL with evidence.
  3. Agent executes the goal — Indexed DOM observation (tag, role, text, value/checked/expanded/disabled/pointer-events, slider values, scroll, selection ranges; custom ARIA/tabindex/contenteditable widgets included; new elements marked via cross-step diffing). One action per step from a grammar of ~30 actions incl. Drag, DragRange, SelectText, Upload, LongPress, ClickAt (Fig.18), within budget K. Exhausting K ⇒ BLOCKED.
  4. Dual oracle — Wait Δ, capture post screenshot, freeze the DOM event log. GPT-5-mini judges DOM assertions from the log ([CHANGE] = held at some point; [AFTER] = holds in final state) and visual postconditions from before/after screenshots. Verdicts YES/NO/UNCERTAIN; only YES passes.
  5. Aggregate and record — PASS only if source reachable, agent finished, and all required assertions YES. On PASS the trajectory is added to Π. An evidence bundle (trace, DOM log, snapshots, per-assertion verdicts, replay path) is stored per transition (§B.3).

Deterministic tie-breaks in the DOM judge (§B.2). Non-interactivity is checked as pointer-events: none → native disabled/aria-disabled → class tokens; selection as aria-selected/pressed/checked → class tokens; ambiguous element localization returns UNCERTAIN rather than guessing.

Main result

Interactive web generation is far from solved: the best model, GPT-5.5, reaches T=65.6 / R=66.3 in its best modality (Video), leaving about a third of required transitions and requirement checks unsatisfied; the top Overall scores are GPT-5.5 69.1 and GPT-5.4 66.8 (Tab.2, §5.2). Open-weight models are competitive: Kimi-K2.6 reaches Overall 63.3 (best open-weight, strong on Image/Video, T=63.7 on Video) and Qwen3.6-27B 62.5, above Claude Opus 4.7 (61.6), Gemini 3.1 Pro (61.9), and Claude Opus 4.6 (58.3) (Tab.2). Overall = mean of T, R, V across modalities; sort on the T columns to see behavior alone.

Key findings

  • Visual quality is not a proxy for behavior (Tab.2, §5.2): Qwen3.6-35B-A3B scores V=80.8 on Markdown while T=15.5 and R=19.2; at the modality level, Sketch has the highest average V (81.4) but trails Image and Video on every interaction metric (Tab.11). Visual scores also cluster tightly (Fig.4) whereas T spans 15–66, so V barely discriminates models.
  • Video is the strongest modality for interaction, and it specifically helps implicit behavior (Tab.11, §C.2): averaged over models, Video vs. Text improves T by 8.8 (54.8 vs 46.0), R by 8.3 (57.2 vs 48.9), and Ri by 10.6 points (53.6 vs 43.0), and shrinks the explicit–implicit gap Δ=Re−Ri from 13.5 to 7.7. Image wins on explicit coverage (Re=62.8) by showing the visible components; the temporal channel is what transmits state changes.
  • Video’s advantage concentrates on hard tasks (Tab.13, Fig.8): on the Hard50 split (lowest model-averaged R) Video beats Image by 4.9 T / 6.1 Ri / 4.8 R, but only 1.6 / 1.7 / 1.4 on Easy50. Hard50 is really hard (T 22–37 vs 69–76 on Easy50) and shows more Availability (13.9% vs 6.0%) and Feedback-and-Boundary (21.6% vs 17.9%) failures, i.e. missing affordances and missing edge-state feedback.
  • Failures happen after the control exists (Fig.6, §5.3.5): for both GPT-5.5 and Kimi-K2.6, State-and-Logic errors are 57.2% / 59.7% of failed transitions and Feedback-and-Boundary 24.6% / 23.5%; Availability is only 12.1% / 11.0% and Execution 6.2% / 5.8%. The bottleneck is maintaining state updates, result logic, validation, and boundary feedback under user actions, not rendering the widget.
  • ICG scoring catches state corruption that checkpoint-style scoring passes (Tab.4, Tab.14, §C.5): on 25 defects injected into GT-validated pages, ICG detects 16/25 (64%) vs. 8/25 under a broad WebGen-Bench criterion (any non-YES) and 1/25 under a strict one (≥1 NO). The 13 ICG-only cases are long-range constraints: record loss under repeated operations (4), cross-feature side effects (5), draft loss across navigation (2), missing explicit-action gating (1), pre/post inconsistency (1). Checkpoints ask “did the target appear done?”; the ICG follows the chain and checks invariants.
  • Scaling has a knee (Fig.5, §5.3.3): within Qwen3.5, Overall is flat from 27B (51.7) to 122B-A10B (51.1) and jumps at 397B-A17B (57.6), with the largest gains under Text and Markdown where layout, logic, and state must all be inferred from thin specs. Note the middle model is a sparse MoE with 10B active parameters, so “flat” partly reflects active-parameter count.
  • Safety and robustness are uniformly poor and not fixed by model strength or richer input (Tab.3, Tab.15–16): GPT-5.5 passes 41.3% of checks, most models 25–32%. For GPT-5.5 the weakest rule families are async/interaction robustness (20.5%), DOM-rendering safety (25.5%), and request security (26.4%); missing input constraints pass only 2.9% of 2,956 checks and repeated-click guards 1.8%.
  • The pipeline’s automatic pieces are near human agreement (Tab.7–8): κ=0.78 for requirement-to-ICG construction and κ=0.74 for the functional evaluator vs. human–human κ=0.81; the visual judge is weaker (κ=0.69 vs 0.77).

Implications

The result that matters for anyone building generators is the decomposition: models mostly can expose the control (Availability + Execution under 20% of failures) and mostly cannot keep dependent state coherent. That points optimization at state logic, not layout. The ICG machinery is reusable as a reward or repair signal: it is implementation-agnostic (no selectors), it localizes failures to a transition and a requirement with an evidence bundle, and it explicitly distinguishes SKIPPED/BLOCKED from FAIL, which is exactly what a repair loop needs to avoid chasing downstream symptoms. Turning ICG transition verdicts into per-transition rewards for RL or into structured repair prompts (the evidence bundle already contains the failed assertion and the contradicting DOM fragment) is the obvious next step; the paper does not attempt it. The Video finding suggests that a demonstration of the target behavior is a far better spec than a screenshot for stateful components; synthetically rendering such demos from a contract (as WebRISE does from the GT page) is a cheap data-generation route. WebRISE sits downstream of WebGen-Bench (checkpoints via navigation agent), FrontendBench (scripted assertions), ArtifactsBench (dynamic screenshots + MLLM checklist), IWR-Bench (video to interactive page), Interaction2Code, and the agentic-verification line of WebVia; it is closest in spirit to model-based GUI testing, applied as a benchmark oracle. Kimi-K2.6 and Qwen3.6-27B beating several proprietary systems, and Kimi-K2.6 nearly matching GPT-5.5 on Video T (63.7 vs 65.6), means open-weight models are a credible base for execution-grounded fine-tuning on this task.

Limitations

  • Self-contained single-file HTML in a controlled browser: no back end, auth, external APIs, persistent DB, concurrency, or long sessions (Limitations §). Scores measure front-end interaction conformance, not deployment readiness.
  • Coverage is bounded by what the LLM-generated test items and ICG enumerate. The paper itself notes the 9/25 missed injected defects show the evaluator is “not yet exhaustive” (§5.3.4).
  • The judges are LLMs: GPT-5-mini for DOM/visual assertions, Gemini-3-Flash-Preview for visual quality; the authors say scores should be read as rank orderings, not absolute values, because of prompt sensitivity and API drift (Ethics §).
  • Contributors come primarily from one region, so “implicit product-level constraints” encode that region’s product conventions (Ethics §).
  • Single run per model–task–modality; no variance, seeds, or confidence intervals are reported anywhere, and several Overall gaps are under 1 point (Qwen3.6-27B 62.5 vs Qwen3.6-Plus 62.5 vs Gemini 3.1 Pro 61.9).
  • Generation prompts, decoding settings, and whether models were allowed multiple attempts or tool use are not reported in the main text (deferred to Sec. A.2 / Appendix D, which lists only the evaluation-side prompts).
  • Code and data are promised “upon acceptance”; nothing is released at v1 (§E).

Critiques and Questions

  1. Circularity between ICG and GT page. Tasks are kept only when a GT page generated from the full requirements passes the ICG (§3.4). This filters out contracts that are hard to satisfy or ambiguous, and the same LLM family that writes the ICG writes the GT. The κ=0.78 construction agreement is reassuring but is measured on a 300-case sample after filtering. Unclear how many tasks were discarded.
  2. The Video modality is rendered from the GT page’s ICG chain. So Video literally shows the model the transitions it will be tested on; its +10.6 Ri advantage may partly be “the test was demonstrated” rather than “temporal evidence is informative”. The Hard50 result (Video helps most where behavior is non-trivial) is consistent with both readings.
  3. T% penalizes BLOCKED and SKIPPED equally with FAIL. Only PASS counts (§4.4). A page whose first transition is unreachable gets near-zero T regardless of the rest. S% would separate these, but the main table (Tab.2) hides S; Tab.12 shows S tracks T within ~5 points, so it is not distorting rankings, but per-model BLOCKED/SKIPPED rates are not reported.
  4. Judge agreement is decent, not high. κ=0.74 for the functional evaluator means a non-trivial fraction of the ~5,495 × 14 × 5 transition verdicts are noisy; with single runs and no CIs, the 1–2 point differences the text discusses (e.g. Qwen3.6-27B vs Qwen3.6-Plus) should not be read as rankings.
  5. The defect-injection comparison is against a re-implementation of WebGen-Bench criteria, not against WebGen-Bench’s own pipeline; 25 injected defects is small, and how they were chosen is not described (selection toward state-consistency defects would favor ICG by construction).
  6. The “scaling knee” is three points on a family that mixes dense and MoE models (27B dense, 122B-A10B, 397B-A17B); active-parameter count is roughly 27B → 10B → 17B, so the curve is not a clean scale sweep.
  7. The Overall score mixes V in at one-third weight, contradicting the paper’s own argument that V is a poor proxy; for the paper’s thesis, T and R alone are the leaderboard.
Why does WebRISE mark a transition SKIPPED instead of FAIL when its source state cannot be reached, and what would go wrong without that distinction?
Source states are restored by replaying previously passed trajectories. If restoration fails, the cause is an upstream defect, not this transition's logic; counting it as FAIL would let one bug be charged once per downstream transition and would blur unreachable states with contract violations. SKIPPED keeps T% attributable to the transition that actually broke (§4.2, §B.3).
A page scores V=80.8 and T=15.5. What does that combination tell you about the model, and which paper finding does it exemplify?
The model reproduces layout and styling well but almost none of the required state transitions execute correctly; this is Qwen3.6-35B-A3B on Markdown (Tab.2) and is the paper's evidence that visual quality is not a proxy for interaction correctness (§5.2).
